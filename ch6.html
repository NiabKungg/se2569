บทที่ 6 — Requirement Engineering

บทที่ตอบข้อสอบเขียนตรง ๆ: "เขียน Functional Requirement และ Non-Functional Requirement ของระบบ" เราจะเรียน RE 3 ขั้น, แยก FR/NFR ด้วย FURPS+, เขียน User Story และเทคนิคที่รุ่นพี่ยืนยันว่าใช้ได้จริงในห้องสอบ

🎯 จุดประสงค์ 📖 บทเรียน 🎯 FR/NFR (FURPS+) 🎯 แนวข้อสอบ 🏋️ โจทย์ซ้อมมือ

🎯 เรียนจบบทนี้ คุณต้องทำสิ่งเหล่านี้ได้

  • อธิบาย 3 ส่วนของ Requirements Engineering: gathering → analysis → specification
  • แยก Problem domain (โลกของปัญหา/ลูกค้า) กับ Solution domain (โลกของซอฟต์แวร์/นักพัฒนา)
  • เข้าใจว่า "Requirements are not simply desires!" — ความอยากที่ถูกปรับด้วยข้อจำกัดโลกจริง
  • แยก FR กับ NFR ได้แม่น + เขียนได้จริง ตามกรอบ FURPS+ จากโจทย์ระบบใดก็ได้ (หัวใจข้อสอบเขียน)
  • เขียน User Story รูปแบบ "As a X, I can Y" พร้อม size points และอธิบาย sizing/velocity
  • อธิบาย Acceptance test: เขียนเมื่อไหร่ ใครทำ ตรวจอะไร

📖 บทเรียน

🗺️ ที่มาที่ไป — ลูกค้าพูดอะไรมา เราแปลเป็นอะไร?

สไลด์ให้ภาพสำคัญ: เราไม่ได้รับ "requirements" จากลูกค้าตรง ๆ — เราได้แค่ "customer problem statement" (คำบ่นเล่าปัญหา) แล้วเรา (นักวิเคราะห์) ต้องวิเคราะห์แปลงมันเป็น requirements และ specification ต่อเอง

สายการผลิต: ลูกค้าเล่าปัญหา (Problem domain) → Requirements (อธิบายปัญหา) → Specification (กำหนดพฤติกรรมระบบ โลกโซลูชัน/Solution domain) → โปรแกรม

อุปมา: ลูกค้าเข้าร้านสร้างบ้านพูดว่า "บ้านผมร้อนอยู่ตลอด" (problem statement) — ไม่ใช่ requirement จนเราวิเคราะห์สาเหตุ (ตึกหันผิดทิศ? ไม่มีฉนวน? หลังคาดูดความร้อน?) แล้วเขียนเป็นความต้องการที่ชัด เช่น "ห้องนั่งเล่นอุณหภูมิไม่เกิน 28°C ตลอดวัน" แล้วสถาปนิกแปลเป็น spec เชิงก่อสร้าง — ซอฟต์แวร์ก็เหมือนกัน ลูกค้าบ่น "ขายของยุ่งมาก" เราต้องแปลเป็นระบบอะไรทำอะไรได้

📐 นิยาม Requirement + 3 ส่วนของ RE

Requirement = ระบุฟังก์ชันธุรกิจที่ผู้ใช้จะทำได้ผ่านระบบในสถานการณ์/บริบทต่าง ๆ และประสบการณ์ที่ผู้ใช้จะได้รับ + ความกังวลอื่นเช่นระบบจัดการทรัพยากร (computing, network) อย่างไร, จัดการและปกป้องข้อมูลผู้ใช้อย่างไร

ระวัง: User requirements มัก high-level, กำกวม (vague) และไม่สมบูรณ์ — มันเป็นเป้าหมายธุรกิจ (business goals) มากกว่าข้อกำหนดเทคนิค เราต้องมองลึกถึงพารามิเตอร์สำคัญในแต่ละ "scenario" แล้วค่อยแปลงเป็น requirement เทคนิคที่ละเอียด

RE มี 3 ส่วน:

  • 1. Requirements gathering (aka elicitation) — ช่วยลูกค้านิยามว่าต้องการอะไร: จะบรรลุอะไร, ระบบจะเข้ากับธุรกิจอย่างไร, ใช้ในชีวิตประจำวันอย่างไร
  • 2. Requirements analysis — การrefine และปรับปรุง requirement ที่เก็บมา
  • 3. Requirements specification — จดเป็นเอกสารอย่างกึ่งทางการหรือทางการ เพื่อความชัด (clarity), ความสม่ำเสมอ (consistency), ความครบถ้วน (completeness)
⚡ "Requirements are not simply desires!" — คำถามคลาสสิก

Requirement ถูกกำหนดจาก 3 แหล่ง:

  • การประเมิน (judgment) เป้าหมายธุรกิจของลูกค้า และอุปสรรคที่ขวางอยู่ตอนนี้
  • เงื่อนไขบนโซลูชันจากข้อจำกัดโลกจริง: กายภาพ (Physical) · สังคม/วัฒนธรรม (Social/Cultural) · กฎหมาย (Legal) · การเงิน (Financial) ฯลฯ
  • ภัยคุกคามจากผู้ไม่หวังดี (Threats created by adversaries)

สรุปหนึ่งบรรทัดที่อาจออก: Requirements = desires ที่ถูกปรับ (adjusted) ด้วยข้อจำกัดโลกจริงและภัยคุกคาม

ตัวอย่าง: อยาก "ประตูบ้านเปิดง่ายที่สุด" (desire) แต่โลกมีคนไม่หวังดี (threat) → requirement จึงกลายเป็น "ปลดล็อกได้เมื่อใช้คีย์ที่ถูกต้อง + พยายามผิดเกิน 3 ครั้งระบบต้องล็อกตัว" (ปรับด้วยข้อจำกัดความปลอดภัย)

1) แยกสลายเป้าหมายธุรกิจ (Decomposition of Business Goals)

📐 2 แนวทาง + ตัวอย่างจากสไลด์

Breadth-first refinement — แผ่กว้างก่อน: Top-level goal → หลาย higher-level goals → หลาย use case → หลาย user story (ทำทุกกิ่งลึก 1 ระดับไล่ไปทีละชั้น)

Depth-first refinement — ลึกหนึ่งกิ่งก่อน: เลือกกิ่งหนึ่งแล้วไล่ลงถึง user story ให้จบกิ่งนั้นก่อน

ตัวอย่าง Safe Home Access: เป้าหมาย "Safe home" แตกเป็นสถานการณ์ Arrive / Stay / Depart / Away → ฟังก์ชัน Unlock, Enter, Lock, Devices → Authenticate → ...

ตัวอย่าง Restaurant Automation: "Operate restaurant" แตกเป็น Manage employees / Manage tables / Manage inventory / Serve customers / Statistics & Planning → Serve customers แตกเป็น Reservations, Occupancy, Seat, Take order, Track order, Payment, Cleanup

📐 Problem Analysis — ก่อนเขียน requirement ต้องหา "สาเหตุ"

สไลด์ตัวอย่าง Traffic Monitoring: ปัญหา = ผู้ใช้ไปทำงานสาย · สาเหตุ A: จราจรไม่แน่นอน · สาเหตุ B: ผู้ใช้ไม่คุ้นเส้นทาง · สาเหตุ C: ผู้ใช้มีนิสัยออกบ้านสาย — ขึ้นกับสาเหตุ โซลูชัน/requirement จะต่างกัน (ระบบพยากรณ์จราจร vs ระบบนำทาง vs ระบบปลุกซ้ำ)

ตัวอย่าง Safe Home Access: ปัญหา = กุญแจกายภาพไม่สะดวก / ถูกบุกรุก → วิเคราะห์สาเหตุ: ลืมล็อกประตู/ปิดเครื่องใช้, ทำกุญแจหาย, ไล่ดูประวัติการเข้าไม่ได้, ควบคุมระยะไกลไม่ได้, ผู้บุกรุกเข้าได้ → System requirements สร้างจากสาเหตุที่เลือก — เทคนิคนี้เองที่ใช้กับข้อสอบ CS-Hospital: อ่านโจทย์ → หาสาเหตุ/ความต้องการเป็นข้อ ๆ → แปลงเป็น FR/NFR

2) Requirements as User Stories

📐 โครง + กฎ 6 ข้อ

รูปแบบ: "As a [user-role], I can [capability], [business-goal]" — เช่น "As a tenant, I can unlock the doors to enter my apartment."

  • เครื่องมือที่ชื่นชอบในagile methods
  • พูดถึงเป้าหมายและความสามารถของผู้ใช้ แทนการพูดถึง feature ของระบบ
  • เขียนโดยลูกค้า/ผู้ใช้ ไม่ใช่นักพัฒนา
  • ทีมประเมินแรงงาน (effort) ที่จะ implement story ทันที
  • Acceptance test เขียนพร้อมตอนที่ story ถูกระบุ (ไม่ใช่รอตอนท้าย!)
  • ระบุ requirement เฉพาะiteration ถัดไป ไม่ใช่ทั้งโปรเจกต์

จากสไลด์: แต่ละ story มี ID + size points (เช่น REQ-2 "As a user, I will be able to unlock the doors using a valid key" = 7 points) · หมายเหตุ: ไม่ใช้ priority — ลำดับความสำคัญให้ที่ตำแหน่งบน to-do list

⚡ Sizing the Problem — 5 ขั้นประมาณงาน
  1. แบ่งปัญหาเป็นส่วนย่อยที่เล็กและคล้ายกัน (small & similar parts)
  2. ประมาณขนาดสัมพัทธ์ของทุกส่วน (Size = 4, 7, 10 points ฯลฯ)
  3. ประมาณขนาดรวม: Total size = ผลรวม points ทุกส่วน
  4. ประมาณความเร็วทำงาน (velocity) — เช่นเราทำได้ 1 point ต่อ 2 วัน
  5. ประมาณระยะเวลางาน: duration = ขนาดรวม ÷ velocity (เหมือน เวลาเดินทาง = ระยะทาง ÷ ความเร็ว)

อุปมาที่สไลด์ใช้: ประมาณเวลาตัดหญ้าคันข้างบ้าน — แบ่งพื้นที่เป็นก้อนเล็ก ๆ ประเมิน "ก้อนนี้ยากกว่าก้อนนั้นกี่เท่า" รวมเป็นคะแนน แล้วเอาคะแนน ÷ ความเร็วที่เคยวัดไว้จริง = เวลา — ถ้าประมาณผิดเพียงก้อนเล็ก ผลกระทบรวมก็น้อย (นั่นคือเหตุผลที่ต้อง "เล็กและคล้ายกัน")

เกร็ดจากสไลด์: ซอฟต์แวร์มองไม่เห็น (unlike hedges) และยังไม่มีตัวตนตอนเริ่มโปรเจกต์ → ประมาณแรกขึ้นกับ ประสบการณ์และจินตนาการ มาก — velocity ต้องปรับจากความคืบหน้าจริง แต่ถ้าประเมินขนาดสัมพัทธ์แม่น คำนวณระยะเวลาใหม่ได้เร็ว

ตัวอย่างอ่านค่าจริง: 1 point = 2 วัน → REQ2 (7 pts) = 14 วัน, REQ6 (3 pts) = 6 วัน ... รวม 102 วัน — to-do list ที่ลูกค้าจัดลำดับ แล้ว developer "ดึงงาน" จากบนลงมาทำใน iteration (tasks pulled by developers)

💡 Tradeoff: ลูกค้ายืดหยุ่น ↔ นักพัฒนามั่นคง

งานที่ถูกดึงเข้า iteration ไปแล้ว ลูกค้าแก้ลำดับไม่ได้อีก (developer มีเป้าหมายมั่นคงจนจบ iteration) · แต่ลูกค้ายังยืดหยุ่นได้กับงานที่เหลือบน to-do list (รองรับตลาดเปลี่ยน) — 2 ขั้นทุกครั้ง: (1) ถอดงานของ iteration หน้าออกจากลิสต์ (2) เลื่อนงานที่เหลือขึ้นบนแล้วให้ลูกค้าจัดลำดับใหม่ได้

3) Requirements Analysis — เจาะ "Business Policies"

📐 ตัวอย่าง REQ-3 ป้องกัน dictionary attack

Requirement บอกว่า "ผู้บุกรุกไม่สามารถ unlock ด้วยการเดาคีย์ได้ (dictionary attack) ระบบต้อง block" — แต่มีรายละเอียดเยอะต้องตัดสินใจ ("business policies"):

  • อะไรแยก "ผู้ใช้กดพลาด" กับ "dictionary attack"? → จำนวนครั้งที่อนุญาตให้ผิด เทียบกับ threshold · threshold ควรเล็ก เช่น 3 ครั้ง — นี่คือ business policy!
  • กุญแจกลไก (mechanical lock) ทำอะไรตอนระบบ "blocked"? ใช้กุญแจจริงได้ไหม?

และ REQ-5 "keypad ติดแสงเมื่อมืด" — ตรวจความมืดคุ้มไหม หรือเปิดติดตลอดดีกว่า?

จำสไลด์: "Requirements analysis ไม่ควร exhaustive จนเว่อร์ แต่ก็ไม่ควรเลี่ยง (avoided)"

ทำไมต้องระบุ business policy ให้ชัด (2 เหตุผล): ① ให้ stakeholder (โดยเฉพาะลูกค้า) มีส่วนตัดสินใจเรื่อง policy ② เห็นล่วงหน้าว่า policy อาจเปลี่ยนในอนาคต → เขียนโค้ดให้ localize จุดเปลี่ยน เปลี่ยนได้เร็ว · เรื่องสำคัญเกินจะปล่อยให้ programmer ตัดสินเองและ hard-code ไม่ได้!

4) 🎯 ประเภท Requirement — หัวใจข้อเขียนตอบ

🎯 FR vs NFR — ทุกปีออกในรูปแบบนี้ ("เขียน FR และ NFR ของระบบ X")

Functional Requirements (FR) = "ระบบต้องทำอะไร" (What the system will do) — ฟังก์ชันงานธุรกิจ พฤติกรรม การตอบสนองต่อ input ในแต่ละบริบท

Non-functional requirements (NFR) = quality requirements = "ทำได้ดีเพียงไหน" (How well) — คุณลักษณะ ข้อจำกัด คุณภาพ จัดหมวดด้วยกรอบ FURPS+:

⚡ สูตรเขียนคำตอบข้อ FR/NFR ในห้องสอบ (3 ขั้น)
  1. อ่านโจทย์วลีต่อวลี — ทุกประโยคในโจทย์ล้วนเป็น "เมล็ด requirement": "เก็บข้อมูลผู้ป่วย" = ฟังก์ชัน, "ส่งต่อผ่าน LINE/Email" = ฟังก์ชัน+ความเชื่อมโยงระบบอื่น
  2. จำแนกลง 2 กลุ่ม: สิ่งที่ระบบ "ทำ" (เก็บ ค้น แสดง ออกรายงาน ส่งต่อ ยืนยันตัวตน จัดการบัญชี) → FR · สิ่งที่บอก "ดีแค่ไหน" (ปลอดภัย ไว น่าเชื่อถือ ใช้ง่าย รองรับคนเยอะ ซ่อมง่าย) → NFR แล้วผูกกับตัวอักษร FURPS+
  3. เขียนเป็นประโยคมาตรฐาน: FR เริ่มด้วย "ระบบต้องสามารถ..." · NFR เริ่มด้วยคุณภาพ+เกณฑ์วัดได้ เช่น "ระบบต้องรองรับผู้ใช้พร้อมกัน 500 คนโดยตอบสนองภายใน 2 วินาที" (ตัวเลขทำให้ NFR น่าเชื่อถือ — ไม่เขียน "ระบบต้องเร็ว" เปล่า ๆ)

→ เฉลยตัวอย่างเต็มรูปแบบของ CS-Hospital อยู่ที่หน้า 🎓 ติว Final

📐 Acceptance Tests + UI Requirements (เกร็ดท้ายบท)

Acceptance tests = วิธีประเมินว่าบรรลุเกณฑ์ความสำเร็จ — requirement ถูกพบเหมือนที่คาด · ลูกค้า conduct ตลอดโปรเจกต์ ไม่ใช่ตอนท้ายอย่างเดียว · acceptance test ระบุว่าระบบจะผ่าน/ตกเมื่อให้ input ใด · ไม่มีทาง guarantee coverage 100% ของทุกสถานการณ์ใช้งาน แต่วิธีเป็นระบบ (systematic) เพิ่มความครอบคลุมคาดหวังได้

แต่ละ requirement อธิบายว่าเมื่อได้ "สถานการณ์" (system inputs) ใด → output/behavior ที่ระบบต้องผลิต — และ "output" แทนความต้องการ/เป้าหมายธุรกิจของผู้ใช้

User interface requirements: อย่าเสียเวลาทำ screenshot หรูหรา สีสันประดับเยอะ มันสกัดสมาธิ · วาดมือ (hand-drawing) บังคับให้ประหยัดและโฟกัสฟีเจอร์สำคัญ · พอฉันทามติว่าดีแล้วค่อยลงแรง prototype จริง

  • FURPS+: ให้ตัวอักษรมาให้เติมชื่อ (โจทย์ชอบถาม F = ? ที่มี security ผูกอยู่)
  • User Story: เขียน story รูปแบบ As a... I can... + อธิบายว่า acceptance test เขียนพร้อม story
  • แนวคิด: "Requirements are desires adjusted to real-world constraints and threats" — เติมคำ/อธิบาย

🏋️ โจทย์ซ้อมมือ (6 ข้อ)

ข้อ 1●○○

จำแนก (แนวข้อสอบตรง): ประโยคต่อไปนี้เป็น FR หรือ NFR (ก) "ระบบต้องออกใบรับรองแพทย์เป็น PDF ให้ดาวน์โหลด" (ข) "ระบบต้องเข้ารหัสข้อมูลผู้ป่วยทั้งหมดขณะส่งผ่านเครือข่าย" (ค) "ระบบต้องโหลดหน้าค้นหาผู้ป่วยภายใน 2 วินาที" (ง) "พยาบาลที่ไม่เคยใช้คอมมาก่อนต้องค้นประวัติผู้ป่วยสำเร็จภายใน 5 นาทีแรกโดยไม่ต้องอ่านคู่มือ"

เฉลย
  1. (ก) FR — ระบบ "ทำ" อะไร (ออกรายงาน PDF)
  2. (ข) NFR — Security (ฝั่ง FURPS ตัว F = Functionality (security))
  3. (ค) NFR — Performance (มีเกณฑ์วัด: 2 วินาที)
  4. (ง) NFR — Usability (มีเกณฑ์วัด: มือใหม่ใช้สำเร็จภายใน 5 นาทีไม่ต้องอ่านคู่มือ)
ข้อ 2●○○

เติม FURPS: (1) _ = Functionality (security) (2) _ = ความง่ายในการใช้ (3) _ = ความน่าเชื่อถือ (4) _ = ประสิทธิภาพ (5) _ = การสนับสนุน/บำรุงรักษา — แล้ว "+" หมายถึงอะไร

เฉลย
  1. (1) Functionality (2) Usability (3) Reliability (4) Performance (5) Supportability
  2. "+": ข้อจำกัด/เรื่องอื่น ๆ นอกห้าตัวหลัก เช่น constraints, design requirements, interface requirements อื่น
ข้อ 3●●○

เขียน User Story: เขียน user story 3 อันสำหรับระบบ CS-Hospital ตามรูปแบบ "As a [role], I can [capability], [business-goal]" — เลือก role ให้หลากหลาย

ตัวอย่างคำตอบ
  1. REQ-1: As a receptionist, I can register a new patient with their personal and medical history, so that the hospital has accurate records for every visit.
  2. REQ-2: As a doctor, I can view a patient's treatment history and lab results before diagnosing, so that I make informed decisions.
  3. REQ-3: As a doctor, I can send diagnosis results to a specialist team via LINE or Email, so that specialist care is not delayed.
  4. สังเกตโครง: role ชัด / capability วัดได้ / business-goal อธิบายทำไม — และตามหลักสไลด์ ต้องเขียน acceptance test คู่กันทันที
ข้อ 4●●●

คำนวณ sizing: โปรเจกต์มี 5 stories ขนาด 4, 7, 3, 6, 10 points ทีมวัด velocity ได้ 1 point = 2 วัน หา total size และระยะเวลาประมาณ แล้วตอบว่าถ้า velocity จริงดีขึ้นเป็น 1 point = 1.5 วัน ระยะเวลาใหม่เป็นเท่าไหร่

เฉลย step-by-step
  1. Total size = 4+7+3+6+10 = 30 points
  2. duration = ขนาด ÷ velocity = 30 × 2 = 60 วัน
  3. velocity ใหม่: 30 × 1.5 = 45 วัน — สังเกตว่าเมื่อ "ขนาดสัมพัทธ์" แม่นแล้ว แค่ปรับ velocity ก็คำนวณ duration ใหม่ได้เร็ว (จุดสำคัญจากสไลด์)
ข้อ 5●●●

เขียนเต็ม (จำลองข้อสอบ ย่อส่วน): ระบบ CS-Clinic เล็ก ๆ: จองคิวแพทย์ออนไลน์ สำหรับคลินิก 2 ชั้น ผู้ป่วยเข้าจองเองผ่านเว็บ เจ้าหน้าที่จัดคิว แพทย์ดูคิวของตน — เขียน FR 4 ข้อ และ NFR 4 ข้อ (ครบ FURPS)

แนวคำตอบ

Functional Requirements:

  1. ระบบต้องสามารถให้ผู้ป่วยลงทะเบียนและจองคิวกับแพทย์ที่ระบุวัน-เวลาได้ (FR)
  2. ระบบต้องสามารถแสดงรายการคิวที่รออยู่แก่เจ้าหน้าที่ และอนุญาตให้ย้าย/เลื่อนคิวได้ (FR)
  3. ระบบต้องสามารถแจ้งเตือนผู้ป่วยทาง SMS/Email เมื่อคิวใกล้ถึง (FR)
  4. ระบบต้องสามารถให้แพทย์ดูคิวของตนเองเฉพาะของตนเองหลังยืนยันตัวตน (FR)

Non-Functional Requirements (FURPS+):

  1. F (Security): ข้อมูลสุขภาพต้องเข้าถึงได้เฉพาะแพทย์ผู้รับผิดชอบและผู้ป่วยเจ้าของข้อมูล (role-based access)
  2. U (Usability): ผู้ป่วยอายุ 60+ ต้องจองคิวสำเร็จภายใน 3 นาทีโดยไม่ต้องอ่านคู่มือ
  3. R (Reliability): ระบบพร้อมใช้งาน 99.5% ในเวลาคลินิกเปิด ไม่สูญหายข้อมูลคิวเมื่อเครือข่ายขาดชั่วคราว
  4. P (Performance): แสดงรายการคิวปัจจุบันภายใน 2 วินาทีเมื่อผู้ใช้พร้อมกัน 100 คน
  5. S (Supportability): รองรับเพิ่มแพทย์ใหม่/แก้ตารางเวลาโดยเจ้าหน้าที่ทำเองได้ ไม่ต้องแก้โค้ด
  6. เทคนิคจากข้อสอบ: อ่านโจทย์วลีต่อวลี — มีตัวเลขในโจทย์ (ขนาดคลินิก 2 ชั้น) ก็นำมาผูก NFR ให้มีเกณฑ์วัดจริง
ข้อ 6●●○

อธิบายแนวคิด: "Requirements are not simply desires" — ข้อความนี้แปลว่าอะไร ยกตัวอย่าง desire → requirement ที่ถูกปรับด้วย constraint/threat 1 เคส

เฉลย
  1. ความหมาย: สิ่งที่ลูกค้า "อยากได้" (desire) ยังไม่ใช่ requirement เพราะ requirement คือ desire ที่ถูกปรับด้วยข้อจำกัดโลกจริง (physical/social/legal/financial) และภัยคุกคามจากผู้ไม่หวังดี
  2. เคส: โรงพยาบาลอยากให้ "ผู้ป่วยเข้าถึงข้อมูลตัวเองได้ทุกเวลาจากทุกที่" (desire) — แต่มีกฎหมายคุ้มครองข้อมูลสุขภาพ (legal constraint) + มีแฮกเกอร์ (threat) → requirement จริงคือ "ผู้ป่วยเข้าถึงข้อมูลตัวเองได้ผ่านระบบยืนยันตัวตนสองชั้น เก็บ log การเข้าถึงทุกครั้ง"
  3. สรุป: requirement ดี = จำกัดขอบเขตให้ implement ได้จริง ไม่ใช่แค่ความปรารถนา
