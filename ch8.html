บทที่ 8 — Software Process Models

รีวิวรุ่นพี่เตือน: "ทำความเข้าใจข้อจำกัดกับลักษณะของ Process Model — งานแบบไหนเหมาะกับ Model ไหน" บทนี้จึงจัดเป็นเทียบคู่ ๆ: ข้อดี/ข้อจำกัด ของ Waterfall, Spiral, Prototyping, RAD, Incremental, Evolutionary, RUP, XP, Scrum

🎯 จุดประสงค์ 📖 บทเรียน 🎯 แนวข้อสอบ 🏋️ โจทย์ซ้อมมือ

🎯 เรียนจบบทนี้ คุณต้องทำสิ่งเหล่านี้ได้

  • เล่าข้อดี/ข้อจำกัดของ Waterfall ได้ 4 ข้อ (ระบุชัดว่า "ออกสอบ")
  • อธิบาย Spiral: วนซ้ำ + risk analysis นำทุกเฟส + สิ่งที่วนในแต่ละรอบ + ใครประเมินจบรอบ
  • อธิบาย Prototyping (RAD Tool) และ RAD: 5 เฟส, ทีมขนาน, 60–90 วัน, ใช้เมื่อไหร่
  • แยก Incremental กับ Evolutionary และต่างจาก Waterfall อย่างไร
  • จำ RUP: 4 เฟส (Inception, Elaboration, Construction, Transition) + core process workflows 7 + supporting 3 + ลักษณะ "use case driven, architecture centric"
  • จำ XP: user stories, KIS, CRC cards, spike solution, refactoring, pair programming, continuous integration + 10 แนวปฏิบัติ
  • จำ Scrum: 3 เฟส, sprint 2–4 สัปดาห์, product backlog, scrum master ทำอะไร, ประโยชน์ 5 ข้อ
  • จับคู่ "งานแบบไหน → Model ไหน" ได้ (แนวข้อสอบที่รุ่นพี่ย้ำ)

📖 บทเรียน

🗺️ ที่มาที่ไป — ทุกโมเดลคือการแก้จุดอ่อนของโมเดลก่อน

อ่านบทนี้เป็น "เรื่องวิวัฒนาการ": Waterfall วินัยดีแต่ช้า ได้ของทีเดียวจบ → Prototyping ทำตัวอย่างให้ผู้ใช้ดูก่อนจับ requirement ให้แม่น → Spiral เอา waterfall+prototype วนซ้ำแล้วเติม Risk Analysis → RAD ย่นเวลาด้วยทีมขนาน + reuse → Incremental/Evolutionary ส่งเป็นก้อน → RUP จัดระเบียบกระบวนการเชิงวัตถุด้วย UML → XP/Scrum คือ Agile เร่ง feedback เป็นรายสัปดาห์

อุปมาประจำบท: สร้างบ้าน — Waterfall = ออกแบบทั้งหมดแล้วก่อจบทีเดียว · Prototyping = สร้าง mockup บ้านตัวอย่างให้เจ้าของดูก่อน · Spiral = สร้างทีละวง วงแรกขอโครงเล็ก ๆ ประเมินเสี่ยงแล้วค่อยขยาย · Incremental = ส่งห้องนอนใช้ก่อนแล้วค่อยก่อห้องอื่น · Agile = ทีมช่างยืนพร้อมกันเช้าทุกวันปรับตาม feedback รายวัน

1) Waterfall Model — รากฐานทุกโมเดล

📐 5 ขั้น (ทบทวนจากบทที่ 1) + เกิดหลัง Feasibility

เริ่มหลัง Feasibility study เมื่อรู้ต้นทุน-ผลประโยชน์แล้ว: Requirements Analysis and Specification (ระบุ+บันทึก requirement แบบใช้ภาษาปลายทาง/ผู้ใช้อ่านรู้เรื่อง) → Design and Specification แบ่ง 2 ซับ: Architectural (high-level) โครงสร้างโมดูล+การจัดองค์ประกอบ และ Detailed design ออกแบบรายโมดูลจากโครง → Coding and Module Testing (ทำโค้ดจริง+ทดสอบก่อนส่งต่อ) → Integration and System Testing (โมดูลที่ทดสอบแล้วมารวม ทดสอบเป็นระบบ) → Delivery and Maintenance

🎯 ข้อดี / ข้อจำกัด ของ Waterfall — จำเป๊ะจากสไลด์ (ออกสอบ)
ข้อดี (Advantages)
  • แต่ละ task เป็นอิสระจากกัน
  • ควบคุมง่าย แม้โครงการใหญ่
  • โครงการจบตามเวลา (finish on time)
ข้อจำกัด (Disadvantages)
  • ต้องออกแบบทุกงานก่อนแล้วค่อย coding
  • เอกสารเยอะมาก เปลืองเวลา
  • ผู้ใช้ต้องรอจนกระบวนการเสร็จหมด
  • ใช้กับเครื่องมือ/เทคโนโลยีใหม่ไม่ได้

เหมาะกับงาน: requirement ชัดเจนคงที่ เทคโนโลยีคุ้นเคย — ไม่เหมาะ: requirement กำกวม/จะเปลี่ยน

2) Spiral Model — น้ำตก+ต้นแบบ+วิเคราะห์ความเสี่ยง

📐 นิยามจากสไลด์

โมเดลที่ใช้ Waterfall + Prototype โดยพัฒนาเป็นเฟสเล็ก ๆ — แต่ละเฟสเล็กถูกทดสอบ ประเมิน และ integrate เข้าโปรเจกต์หลัก

พัฒนาโดย Dr. Barry Boehm ที่ TRW — เป็น enhancement ของ waterfall/rapid prototype โดย risk analysis นำหน้าทุกเฟส (risk analysis preceding each phase) · รวม iterative development เข้ากับความเป็นระเบียบของ waterfall · ส่งมอบ incrementally ได้ทุกวง

วงของ Spiral มีอะไร (จำ 6 คำ): Risk Analysis · Prototype · Design/Validation · Planning · Alternatives · Repeat + แกน: Measure of Cumulative Cost and Progress (วัดต้นทุนสะสม+ความคืบหน้า)

เริ่ม/จบกระบวนการ: เริ่มเมื่อ mission การทำงานจริงปรับปรุงได้ด้วยแรง SE · ตลอดทางต้อง test hypothesis · จบเมื่อวงใด violate hypothesis หรือจบด้วยการติดตั้งผลิตภัณฑ์ใหม่/ที่แก้แล้ว

Requirements ใน spiral: Alternatives/ความไม่แน่นอนต้อง resolve ทันทีที่เจอ · risk-driven ยอมใช้โมเดลอื่นผสมได้จนกว่า high-risk จะยุติ · คนเกี่ยวข้องreview หลังจบทุกวง แล้ววางแผนวงถัดไป

3) Prototyping Model

📐 ใจความสั้น ๆ

ทำต้นแบบง่าย ๆ ให้ผู้ใช้เช็ก requirement ของตัวเอง แล้วแก้ต้นแบบซ้ำ จนเข้าใจ requirement ผู้ใช้จริง · ต่อยอดจาก Waterfall · ไม่ดีสำหรับระบบใหญ่ · เครื่องมือพัฒนาเรียกว่า RAD Tool (Rapid Application Development Tool)

โฟลว์: Requirements → Design → Coding & Module Testing → Integration & System Testing → (มี "Testing" loop กลับมาแก้) → Delivery & Maintenance

4) RAD Model — เร่งสปีด 60–90 วัน

📐 นิยาม + 5 เฟส + เมื่อไหร่ใช้

RAD = Rapid Application Development — โมเดล incremental ที่เน้นรอบพัฒนาสั้นมาก (extremely short development cycle) · ใช้เมื่อ: requirement เข้าใจดีแล้ว (well understood) และscope ถูกจำกัด (constrained) → ทีมสร้างระบบทำงานเต็มรูปแบบในเวลาสั้นมาก (ตามภาพสไลด์: 60–90 วัน) โดยทีมหลายทีมทำขนานกัน

5 เฟส (จำ "B-D-P-A-T"):

  • Business modeling — ข้อมูลไหลในธุรกิจแบบไหน: อะไรขับเคลื่อน process? ข้อมูลไปที่ไหน? ใครประมวลผล?
  • Data modeling — กลั่นเป็น data objects ที่รองรับธุรกิจ
  • Process modeling — แปลง data objects ให้บรรลุ flow ของธุรกิจ: add/modify/delete/retrieve
  • Application generation — ใช้เทคนิค 4GL (ภาษารุ่น 4/สัญลักษณ์กราฟิกที่ลูกค้าอ่านรู้เรื่อง)
  • Testing and turnover — เน้นreuse คอมโพเนนต์ที่ทดสอบแล้ว → เวลาทดสอบรวมลดลง

5) Incremental vs Evolutionary Distribution

📐 คู่เทียบสั้น ๆ

Incremental Distribution Model: ทำanalysis + design ของระบบทั้งหมดก่อน แล้วค่อยพัฒนาแต่ละเฟส · ต่างจาก Waterfall ที่ห้ามหั่นเป็นเฟสเล็ก · แต่ก็ยากเหมือนกันที่จะหั่นโปรเจกต์รวมเป็นเฟสเล็ก

Evolutionary Distribution Model: = Evolutionary (Prototyping) Model + Incremental — พัฒนาระบบหลัก (main system) ก่อน แล้วค่อยเพิ่มส่วนตามรอบ

6) RUP — Rational Unified Process

📐 ภาพรวม

พัฒนาโดย Rational Software Corporation (ต่อมารวมกับ IBM) — methodology นิยมสำหรับระบบเชิงวัตถุใช้ UML · เหมาะกับองค์กร/ธุรกิจขนาดใหญ่ โดยเฉพาะผู้ผลิต/จัดจำหน่ายซอฟต์แวร์ ครอบคลุมทั้งบริหารโครงการและควบคุมคุณภาพ

ลักษณะเด่น (จำประโยคนี้): "use case driven, architecture centric, iterative, incremental" + มี cycles, phases, workflows, risk mitigation, quality control, project management, configuration control

Core Process Workflows 7 กิจกรรม: ① Business Modeling ② Requirement ③ Analysis (เอกสารขอบเขตระบบ → ผลคือ Use Case Diagram & Use Case Specification) ④ Design (ศึกษา Pattern Design + เน้น UI) ⑤ Implementation ⑥ Testing ⑦ Deployment (ติดตั้ง HW/SW/network)

Core Supporting Workflows 3 กิจกรรม: ① Configuration & Change Management ② Project Management ③ Environment

⚡ RUP 4 เฟส (จำ "I-E-C-T")
  • 1. Inception — เริ่มต้น: กำหนดขอบเขต หน้าที่งานหลัก วิสัยทัศน์ ความสามารถพัฒนา · ก่อนวน iteration · มี Business Modeling, Requirement + supporting ทั้งหมด
  • 2. Elaboration — วางแผน/จัดสรรทรัพยากร: ระบุฟังก์ชันระบบใหม่ ทรัพยากรต่อฟังก์ชัน สถาปัตยกรรม · มี BM, Requirement, Analysis & Design, Implementation & Test + Prototype สถาปัตยกรรม
  • 3. Construction — สร้างจริง: กิจกรรมสำคัญคือ Implementation และ Testing
  • 4. Transition — ส่งมอบ: ติดตั้งใช้จริง อบรม ผู้เชี่ยวชาญปรึกษา บำรุงรักษาตามแผน

7) XP — Extreme Programming

📐 วงจร 4 จุด: Planning → Design → Coding → Test
  • Planning: User stories — เล่าหน้าที่/ลักษณะที่ผู้ใช้ต้องการ (คล้าย use case เขียนโดยลูกค้า) · ทีมประเมิน cost เป็นจำนวนสัปดาห์ · release ตาม velocity · acceptance test criteria + iteration plan
  • Design: KIS = Keep It Simple — ใช้ CRC cards (Class Responsibility Collaborator) · ปัญหายากให้ทำ spike solution (โปรตงพร้อมใช้ทันทีเพื่อทดลอง) · Refactoring = ปรับปรุง design ภายหลัง coding
  • Coding: พัฒนาเป็นโมดูลย่อย จบแล้วทดสอบทันที · Pair Programming (สองคนหนึ่งเครื่อง) · รวมต่อเนื่อง = Continuous Integration
  • Test: unit test ทุกชุดรวมกันเป็นชุดใหญ่ Universal Testing Suite → acceptance testing → release software increment → คำนวณ project velocity

8) Scrum

📐 นิยาม + 3 เฟส

Scrum เป็น agile method แบบกว้าง — เน้น การจัดการการพัฒนาแบบ iterative มากกว่าแนวปฏิบัติเฉพาะ

  • เฟส 1 (outline planning): วาง objective ทั่วไป + design สถาปัตยกรรม
  • เฟส 2 (sprint cycles): รอบวนพัฒนา increment ของระบบ — sprint ยาวคงที่ ปกติ 2–4 สัปดาห์ (เทียบ release ของ XP) · เริ่มจาก product backlog (รายการงานทั้งหมด) · เฟส selection ทีมทั้งหมดคุยกับลูกค้าเลือกฟีเจอร์รอบนี้ · ระหว่างทำทีมโดดเดี่ยวจากลูกค้า/องค์กร คุยผ่าน "Scrum master" เท่านั้น · จบ sprint review นำเสนอ stakeholder แล้วเริ่มรอบใหม่
  • เฟส 3 (project closure): ปิดโปรเจกต์ เอกสาร help/manual ประเมินบทเรียน

Scrum master ทำอะไร: facilitator — จัดประชุมรายวัน, ตาม backlog, จด decision, วัดความคืบหน้า, สื่อสารกับลูกค้า/ผู้บริหารนอกทีม · บทบาทสำคัญ = ปกป้องทีมจาก external distractions · ทีมประชุมสั้นทุกวันแชร์ progress/ปัญหา/แผนพรุ่งนี้ → ทุกคนรู้สถานการณ์ ปรับแผนระยะสั้นได้

Scrum benefits (5 ข้อ): ① ผลิตภัณฑ์แตกเป็นชิ้นเล็ก manageable/understandable ② requirement ไม่เสถียรไม่ขวางความคืบหน้า ③ ทีมเห็นทุกอย่าง สื่อสารดีขึ้น ④ ลูกค้าเห็นส่งมอบตรงเวลา + feedback ⑤ เกิดความไว้ใจลูกค้า↔นักพัฒนา + วัฒนธรรมเชิงบวกที่ทุกคนเชื่อว่าโปรเจกต์สำเร็จ

🎯 เทคนิคตอบ "งานแบบไหนเหมาะกับ Model ไหน" (แนวที่รุ่นพี่รีวิว)

โจทย์จะเล่าสถานการณ์ — จับ "คีย์เวิร์ด" ในโจทย์มาเทียบตารางนี้:

🎯 แนวข้อสอบเพิ่มเติมของบทนี้

🎯 มีโอกาสสูง
  • ข้อดี/ข้อจำกัด Waterfall — ให้เขียนตอบ 4+4 ข้อ (จำจากกล่อง match-grid ข้างบน)
  • Spiral: ผู้พัฒนา (Boehm/TRW), นวัตกรรมคือ risk analysis นำหน้าทุกเฟส, วงประกอบด้วยอะไร, ใคร review ท้ายวง
  • RAD: 60–90 วัน, ใช้เมื่อ requirement well-understood + scope constrained, 5 เฟส B-D-P-A-T
  • RUP: 4 เฟส I-E-C-T + 7 core + 3 supporting + "use case driven, architecture centric"
  • XP: KIS, CRC cards, spike solution, refactoring, pair programming, continuous integration, collective ownership, on-site customer
  • Scrum: sprint 2–4 สัปดาห์, product backlog, scrum master ปกป้องทีม, ประโยชน์ requirement ไม่เสถียรไม่ขวางงาน

  1. ข้อดี: ① แต่ละ task อิสระจากกัน ② ควบคุมง่ายแม้โครงการใหญ่ ③ โครงการจบตามเวลา
  2. ข้อจำกัด: ① ต้องออกแบบทุก task แล้วค่อย coding ② เอกสารเยอะ เปลืองเวลา ③ ผู้ใช้รอจนกระบวนการเสร็จหมด ④ ใช้กับเครื่องมือใหม่ไม่ได้
  3. ปิดท้ายเพิ่มคะแนน: เหมาะกับงาน requirement ชัดคงที่ — ไม่เหมาะกับงานที่ requirement จะเปลี่ยนระหว่างทาง
ข้อ 2●○○

เติมคำ: Spiral Model พัฒนาโดย ______ ที่ ______ — โมเดลนี้เป็นการผสม ______ กับ ______ โดยมี ______ นำหน้าทุกเฟส

เฉลย
  1. เติม: พัฒนาโดย Dr. Barry Boehm ที่ TRW
  2. ผสม waterfall/sequential กับ iterative development + prototype โดยมี risk analysis นำหน้าทุกเฟส
  3. ทำให้: ตรวจ requirement + ทดสอบเฟสเล็กได้ ลด risk ป้องกันโปรเจกต์พัง เห็น progress ชัด คุมงบและ timeline ได้
ข้อ 3●●○

จับคู่ Model (เลียนแบบสถานการณ์): (a) ธนาคารต้องการระบบพนักงานเงินสด requirement ชัดเจนตายตัวตามกฎระเบียบ (b) สตาร์ทอัพทำแอปไอเดียใหม่ยังไม่รู้ผู้ใช้อยากได้อะไรจริง (c) องค์กรใหญ่ต้องเปลี่ยนระบบสำคัญ มีความเสี่ยงเรื่อง integration กับระบบเก่าหลายตัว (d) ร้านค้าอยากได้เว็บขายของแบบง่าย scope เล็ก ต้องขึ้นขายใน 2 เดือน

เฉลย
  1. (a) Waterfall — requirement ชัดคงที่ + ควบคุมง่ายตามกฎระเบียบ
  2. (b) Prototyping (หรือ XP/Scrum) — requirement กำกวม ต้องทำต้นแบบให้ผู้ใช้ทดลองแล้วแก้ซ้ำ
  3. (c) Spiral — โครงการใหญ่เสี่ยงสูง ใช้ risk analysis นำทุกวง
  4. (d) RAD — scope จำกัด + requirement เข้าใจดี + ต้องสั้น 60–90 วัน
ข้อ 4●●○

RUP เรียง: เรียง 4 เฟสของ RUP พร้อมบอกว่าแต่ละเฟสกิจกรรมหลักคืออะไร

เฉลย
  1. 1. Inception — เริ่มต้น: ขอบเขต วิสัยทัศน์ หน้าที่หลัก (Business Modeling + Requirement + supporting)
  2. 2. Elaboration — วางแผน/ทรัพยากร: ฟังก์ชันระบบ + สถาปัตยกรรม (อาจทำ prototype สถาปัตยกรรม)
  3. 3. Construction — สร้าง: หัวใจคือ Implementation + Testing
  4. 4. Transition — ส่งมอบ: ติดตั้งใช้จริง อบรม ผู้เชี่ยวชาญดูแล บำรุงรักษาตามแผน
ข้อ 5●●●

จับคู่ XP: (a) สองคนหนึ่งจอ ตรวจงานกัน (b) เขียน test ก่อนเขียนโค้ดจริง (c) ใครก็แก้โค้ดส่วนไหนก็ได้ ไม่มี "เจ้าของโค้ดเฉพาะคน" (d) มีตัวแทนผู้ใช้อยู่กับทีมเต็มเวลา (e) ปรับปรุงโค้ดต่อเนื่องเมื่อเจอจุดที่ดีขึ้นได้ (f) ทำโปรโตทดลองของส่วนที่ยากทันทีเพื่อแก้ปัญหาออกแบบ

เฉลย
  1. (a) Pair programming
  2. (b) Test-first development (TDD)
  3. (c) Collective ownership
  4. (d) On-site customer
  5. (e) Refactoring
  6. (f) Spike solution — (เสริม: จบ task รวมระบบทันที+test ผ่านหมด = Continuous integration)
ข้อ 6●●●

เขียนตอบโยง Final: โปรเจกต์เทอมของคุณเป็นเว็บแอป 4 คน ทำ 8 สัปดาห์ — ถ้าให้เลือก Scrum อธิบายวิธีจัดทีม + sprint + backlog + บทบาท Scrum master ว่าจะทำอย่างไร (พร้อมยกประโยชน์ 2 ข้อที่ตรงกับโปรเจกต์)

แนวคำตอบ
  1. เฟส 1 outline planning: ทีมวาง objective + ออกแบบสถาปัตยกรรมรวมครั้งแรก (เช่น web + database กลาง)
  2. Sprint cycles: 8 สัปดาห์ ÷ sprint 2 สัปดาห์ = 4 รอบ · แต่ละรอบดึงงานจาก product backlog มาทำ increment ที่ใช้ได้ (เช่น sprint 1 = ระบบล็อกอิน+ลงทะเบียน)
  3. Selection + isolation: เริ่ม sprint ทีมคุยกับลูกค้า (อาจารย์) เลือกฟีเจอร์รอบนั้น ระหว่างทำตั้งใจทำให้สำเร็จโดยไม่เปลี่ยนความต้องการกลางทาง
  4. Scrum master: หมุนเวียนหรือตั้ง 1 คน — จัด stand-up รายวัน ตาม backlog จด decision ปกป้องทีมจากสิ่งรบกวนภายนอก
  5. Review: จบ sprint นำเสนอ stakeholder รับ feedback เข้า backlog รอบถัดไป
  6. ประโยชน์ที่ตรงโปรเจกต์: ① requirement อาจารย์ปรับกลางเทอมไม่ทำให้งานตัน (unstable requirements ไม่ขวาง progress) ② ทุกคนเห็นสถานะทุกวัน → สื่อสารดี ไม่มีคนตกงาน และส่งได้ตรงรอบ + ได้ feedback จากการสาธิตจริงทุก 2 สัปดาห์
