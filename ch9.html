บทที่ 9 — Uses Cases

ข้อสอบเขียนตรง ๆ: "เขียน Use case diagram" — เราจะเรียนอ่านโจทย์หา actor/use case, วาด diagram ให้ถูกกฎ, แยก «include» กับ «extend», กับดัก Login ที่อาจารย์เตือนใน video, และโครงเขียน Use Case รายละเอียดแบบ UC-1

🎯 เรียนจบบทนี้ คุณต้องทำสิ่งเหล่านี้ได้

📖 บทเรียน

🗺️ ที่มาที่ไป — จาก requirement สู่ "เรื่องเล่าของการใช้งาน"

บทที่ 6 เขียน requirement เป็น user story — บทนี้อธิบายการทำงานให้ชัดขึ้นอีกชั้น: Use case ใช้สำหรับ Functional Requirements Analysis and Specification — เป็นการบรรยาย step-by-step ว่าผู้ใช้จะใช้ระบบอย่างไรเพื่อบรรลุเป้าหมายธุรกิจ

3 องค์ประกอบหลัก: ① Environmental agents / actors ที่จะทำงานร่วมกับระบบ ② Use case diagram แสดงความสัมพันธ์ actor ↔ use case ③ Use case scenarios/scripts — ลำดับการทำงานร่วมกันระหว่าง actor นอกระบบ กับ ระบบที่จะสร้าง (system-to-be)

อุปมา: use case = สคริปต์ละคร — actor คือนักแสดง, use case คือฉาก (มีชื่อเป็นกริยา เช่น "เช่าหนังสือ"), scenario คือบทพูดทีละจังหวะ พร้อมฉบับ "ยังไงถ้าพลาด" (extensions)

1) Actor มีกี่แบบ? — 🎯 จำ 4 ชื่อนี้

ชนิดนิยามตัวอย่าง (Safe Home)
Initiating actor (aka primary actor / user)เป็นผู้เริ่ม use case เพื่อบรรลุเป้าหมายTenant เริ่ม "Unlock"
Participating actor (aka secondary actor)ร่วมใน use case แต่ไม่ได้เริ่ม — มีซับ 2 ชนิดLockDevice, Database
— Supporting actorช่วยระบบให้จบ use case ได้LockDevice ปลดล็อกจริง, LightSwitch เปิดไฟ
— Offstage actorร่วมแบบผ่าน ๆ — ไม่เริ่ม ไม่ช่วย แต่อาจถูกแจ้งเรื่องมัน (เช่นเพื่อบันทึกรายการ)Police ที่ถูก notify ตอนแฮกเกอร์ยิง alarm
💡 สังเกตจากสไลด์ที่อาจารย์ขีดเส้นใต้

"บ้าน" และ "ประตู" ไม่ได้ปรากฏเป็น actor! — เพราะ actor ต้องเป็นสิ่งภายนอกระบบที่มีปฏิสัมพันธ์กับมัน (คน หรือระบบ/อุปกรณ์ภายนอก) ไม่ใช่วัตถุในโลกปัญหา — ประตูเป็นสิ่งที่ LockDevice ควบคุม เป็นส่วนหนึ่งของโลกกายภาพ ไม่ใช่คู่สนทนาของระบบ

3) 🎯 Use Case Diagram — วาดถูกกฎ (ข้อสอบเขียน)

📐 กฎการวาด (เช็คลิสต์ก่อนส่งกระดาษ)
  • Actor วาดเป็นตัวคน stick figure — อยู่นอก system boundary เสมอ
  • Use case วาดเป็นวงรี (ellipse) ชื่อเป็น verb phrase (กริยา+นาม: Unlock, AddUser — ไม่ใช่คำนามเปล่า ๆ เช่น "Door")
  • System boundary กรอบใหญ่ครอบ use cases ทั้งหมด มีชื่อระบบ
  • เส้นเชื่อม actor↔use case (ความสัมพันธ์) · «initiate» จาก actor ผู้เริ่ม · «include»/«extend» เป็นเส้นประหัวลูกศร
  • แยก Base use cases (ตัวหลัก) กับ Subroutine use cases (ตัวย่อยถูกเรียก)

4) 🎯 DRY + «include» vs «extend» — ตาราง 4 คำถามที่ออกสอบเป๊ะ

💡 DRY Use Cases — ตัดซ้ำด้วย Subroutine Use Case

ถ้าหลาย use case มีขั้นตอนซ้ำ ๆ เหมือนกัน (เช่น "ยืนยันตัวตน") อย่าเขียนซ้ำทุกตัว — หั่นออกมา parametrized เป็น subroutine use case แล้วใช้ «include» เรียก (หลัก DRY: Don't Repeat Yourself)

คำถามIncluded use case («include»)Extending use case («extend»)
Subroutine use case นี้ optional ไหม?No — ต้องมีทุกครั้งYes — เกิดเมื่อเงื่อนไขเกิด
Base use case complete ไหมโดยไม่มีตัวนี้?No — ขาดแล้วไม่ครบYes — ฐานจบได้เอง
การ execute เป็น conditional ไหม?No — เกิดเสมอYes — เกิดเมื่อเงื่อนไข
เปลี่ยน พฤติกรรมของ base ไหม?NoYes
📐 จำง่าย: «include» = จำเป็นทุกครั้ง (subroutine) / «extend» = เป็นทางเลือกเมื่อเกิดเหตุ

ตัวอย่าง «extend» จากสไลด์: ManageAccount เป็น optional extension ของ InspectAccessHistory และ SetDevicePrefs — ปกติดูประวัติก็จบ ถ้าจำเป็นถึงจะโผล่มาจัดการบัญชีเพิ่ม

🎯 กับดัก Login (BAD vs GOOD) — อาจารย์เน้นใน video ว่าข้อสอบชอบลักไก่
BAD — วาด Login เป็น ellipse ใหญ่แล้วให้ AddUser, SetDevicePrefs "ต่อ" มันเป็นเส้นปกติ ทำให้ diagram พัวพัน Login ทุกเส้น อ่านไม่รู้เรื่อง
GOOD — ทำ Login เป็น subroutine «include» (AuthenticateUser / Login) ให้ use cases ที่ต้องยืนยันตัวตนเรียกใช้ — หรือถ้า login เป็นแค่เงื่อนไขก่อนใช้ ก็ยุบเป็น precondition เลย

หลักคิด: Login ไม่ใช่ "เป้าหมายธุรกิจ" ที่ผู้ใช้อยากทำ (ไม่มีใคร "อยาก login") — มันเป็นกลไกกลาง จึงควรเป็น subroutine เท่านั้น

5) Generalization — ทำให้ diagram ไม่บวม

📐 2 แบบ

Actor generalization: Resident (abstract, ทั่วไปกว่า) ← Tenant, Landlord (particular) — ความสัมพันธ์ที่ Tenant/Landlord มีร่วมกันย้ายขึ้น Resident ได้

Use case generalization: UC9 ManageUsers (abstract กว่า) ← UC3 AddUser, UC4 RemoveUser — ตัวแทนย่อยสืบทอดพฤติกรรมและเพิ่มเอง

ลูกศรชี้จาก "particular" ไปหา "more general" — อุปมา: แผนผังตระกูล ยิ่งบนยิ่งกลาง

6) Traceability Matrix — ตารางความสอดคล้อง REQ ↔ UC

📐 3 ประโยชน์ (จำให้ได้)
  • ตรวจว่าrequirement ทุกข้อถูกครอบคลุมโดย use cases (ไม่มี REQ ล่ม)
  • ตรวจว่าไม่มี use case ไหนโผล่มาไร้เหตุผล (ไม่ได้เกิดจาก REQ ไหนเลย = ตัดทิ้ง)
  • จัดลำดับความสำคัญงาน (prioritize work on use cases) — จากสไลด์: นับ priority weight (PW) ของ REQ ที่ use case รับผิดชอบ แถว Max PW / Total PW ช่วยเรียงว่าตัวไหนทำก่อน

7) 🎯 โครงเขียน Use Case รายละเอียด (Schema for Detailed Use Cases)

Use Case UC-#:        ชื่อ / identifier [verb phrase — กริยา+นาม]
Related Requirements:  รายการ REQ ที่ use case นี้รองรับ
Initiating Actor:     actor ผู้เริ่มปฏิสัมพันธ์เพื่อบรรลุเป้าหมาย
Actor's Goal:         คำอธิบายเป้าหมายของ initiating actor
Participating Actors: actors ที่ช่วยบรรลุเป้าหมาย / ต้องรู้ผลลัพธ์
Preconditions:        สถานะที่ต้องจริง "ก่อน" เริ่ม (assumed state)
Postconditions:       สิ่งที่ต้องจริง "หลัง" จบ (สำเร็จหรือยกเลิก)
Flow of Events — Main Success Scenario:
  → 1. initiating actor ส่ง action/stimulus เข้าระบบ   (ลูกศร → = ทางเข้าระบบ)
     2. system ตอบสนอง / ส่งข้อความถึง participating actor  ( ← = จากระบบออก)
  → 3. ...
Flow of Events — Extensions (Alternate Scenarios):
     What could go wrong? — จดจุดผิดพลาดของขั้นใดขั้นหนึ่ง + วิธีจัดการ
  → 1a. เช่น actor ใส่ข้อมูลผิด
     2a. เช่น ไฟดับ, network fail, ข้อมูลที่ขอไม่มี
⚡ ตัวอย่างเต็ม UC-1 Unlock + UC-7 AuthenticateUser (จากสไลด์ — เลียนแบบในข้อสอบได้เลย)
Use Case UC-1:        Unlock
Related Requirements: REQ1, REQ3, REQ4, REQ5
Initiating Actor:     Tenant หรือ Landlord
Actor's Goal:         ปลดล็อกแล้วเข้าบ้าน ไฟส่องสว่างอัตโนมัติ
Participating Actors: LockDevice, LightSwitch, Timer
Preconditions:        • เซตคีย์ที่ถูกต้องใน DB ไม่ว่าง
                      • ระบบแสดงเมนูตรงประตูมีตัวเลือก Lock/Unlock
Postconditions:       Timer เริมนับถอยหลัง auto-lock จาก autoLockInterval
Main Success Scenario:
  → 1. Tenant/Landlord มาถึงประตู เลือกเมนู "Unlock"

8) System Sequence Diagram (SSD) และ Activity Diagram

📐 Activity Diagram (สรุปองค์ประกอบ)

จากสไลด์: Initial node → Select "Unlock" → Enter Key → Verify Key → decision [authorized] → Signal Success → Open Lock & Lit Light → Start Autolock Timer → activity final node · กิ่ง [not authorized] → Notify Intrusion → Sound Alarm → merge — องค์ประกอบ: initial/final node, action, decision + guard condition [..], merge

💡 Limitations ของ Use Cases (+User Stories ด้วย) และ UI requirements

① บ่อยครั้งผู้ใช้ใช้ระบบแทนผู้รับประโยชน์จริง (พนักงานธนาคารแทนลูกค้า) — จะคุยเป้าหมายใครดี? คำตอบตามสไลด์: ควรพิจารณาทั้งสองฝ่าย ไม่งั้นได้ภาพบางส่วน · และระบบอัตโนมัติมักตัดคนกลางออกให้ผู้รับประโยชน์จริงคุยกับระบบเอง หรือคนกลางกลายเป็น supporting actor

② UI requirements: อย่าเสียเวลาทำ mockup สวย ๆ สีสันเยอะ — วาดมือบังคับให้โฟกัสฟีเจอร์สำคัญ (สไลด์เดินเรื่อง keypad 3 รอบ: มีปุ่ม Unlock เพิ่มเพื่อแก้ตัวพิมพ์ผิด → เพิ่ม display เลขที่กดเพื่อช่วยจำ vs ระวังแฮกเกอร์อ่าน → ชั่งน้ำหนัก cost/ความกะบัง/ความชื้น/ข้อมูลรั่ว)

③ Security & abuse cases: ระบุความเสี่ยงร้ายแรง — risk 3 ระดับ: Intolerable / ALARP (as low as reasonably practical) / Acceptable · ตัวอย่าง abuse sequence: ใส่คีย์ผิดถึง max รอหมดเวลา ใส่ผิดอีก — ต้องมี counter-measure (block + alarm)

🎯 แนวข้อสอบของบทนี้

🎯 "เขียน Use case diagram" — ออกเขียนตอบทุกปีล่าสุด
  • สิ่งที่กรรมการให้คะแนน: actor ถูกต้องไม่หลุดใคร (ผู้ใช้/ระบบภายนอกเช่น LINE, Email), use case เป็นกริยา, boundary มี, ความสัมพันธ์ «include» ใช้ถูกต้อง
  • ตาราง «include» vs «extend» 4 คำถาม — จำ No/Yes ทั้งแถว
  • กับดัก Login: อย่าวาด Login พัวพันทุก use case — ทำเป็น subroutine «include» หรือยุบเป็น precondition
  • โครง Use Case รายละเอียด 8 หัวข้อ + main scenario สลับ → / ← + extensions เลข x.y
  • ชนิด actor 4 แบบ + ตัวอย่าง offstage (Police ถูกแจ้ง)
  • Traceability matrix 3 ประโยชน์

🏋️ โจทย์ซ้อมมือ (6 ข้อ)

ข้อ 1●○○

จำแนก actor (แนวข้อสอบ): ระบบ CS-Hospital มี: พยาบาลกดลงทะเบียนผู้ป่วย / ระบบ LINE Notify รับข้อความแจ้งเตือน / หัวหน้าแพทย์ได้รับสำเนารายงานโดยไม่มีส่วนร่วมโดยตรง / ระบบคลังยาตอบคำขอตรวจสต๊อก — ใครคือ initiating, supporting, offstage?

เฉลย
  1. พยาบาล = Initiating actor — เริ่ม use case ลงทะเบียนผู้ป่วย
  2. ระบบ LINE Notify = participating — ถ้ามันส่งการแจ้งออกไปทำงานแทนระบบถือเป็น Supporting actor
  3. หัวหน้าแพทย์ที่แค่ได้รับสำเนา = Offstage actor — ไม่เริ่ม ไม่ช่วย แต่ถูกแจ้ง (เพื่อบันทึก/รับรู้)
  4. ระบบคลังยาที่ตอบคำขอ = Supporting actor (ระบบภายนอกช่วยให้ use case สำเร็จ)
ข้อ 2●○○

ตาราง 4 คำถาม: เติมตารางเทียบ «include» กับ «extend»: optional? / base complete โดยไม่มีมัน? / conditional? / เปลี่ยนพฤติกรรม base?

เฉลย
  1. «include»: ตอบ No ทั้ง 4 — จำเป็น ฐานไม่ครบถ้าขาด เกิดเสมอ ไม่เปลี่ยนพฤติกรรมฐาน
  2. «extend»: ตอบ Yes ทั้ง 4 — ตัวเลือก ฐานจบเองได้ เกิดเมื่อเงื่อนไข เปลี่ยนพฤติกรรมฐานได้
  3. จำ: include = "ต้องวิ่งทุกครั้ง" (subroutine) · extend = "โผล่เฉพาะบางเคส" (ส่วนขยาย)

  1. (ก) initiating actors: Nurse/Staff (ลงทะเบียนผู้ป่วย), Doctor (ค้นประวัติ ออกใบรับรอง ส่งต่อผลวินิจฉัย), อาจมี Admin (จัดการบัญชีบุคลากร)

Use Case UC-4: SendDiagnosisToSpecialist
Related Requirements: ส่งต่อผลการรักษา/วินิจฉัยให้ทีมแพทย์เฉพาะทางผ่าน LINE/Email

Preconditions: Doctor ยืนยันตัวตนแล้ว · มีผลวินิจฉัยบันทึกในระบบแล้ว
Postconditions: ระบบบันทึกว่าส่งสำเร็จ + เวลา และ Specialist Team ได้รับข้อความ

  → 1. Doctor เลือกผลวินิจฉัยและกด "ส่งต่อเฉพาะทาง" แล้วเลือกทีมปลายทาง
     2. System แสดงสรุปให้ยืนยัน
  → 3. Doctor ยืนยันส่ง
     4. System ส่งข้อความผ่าน LINE API / Email Server และบันทึก log การส่ง

      2. ถ้าทุกช่องทางล้ม → System แจ้ง Doctor ให้ลองใหม่และเก็บงานไว้ในคิวรอส่ง
  1. สังเกตสูตร: ขั้นสลับ → / ← · extension อ้างเลขขั้นต้นทาง (4a) · pre/post เป็นสิ่ง "เช็กได้"
