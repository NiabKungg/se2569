บทที่ 5 — Software Project Management

รู้วิธีสร้างซอฟต์แวร์อย่างเดียวไม่พอ — ต้องจัดการโครงการให้เสร็จตามเวลา ตามงบ ตามคุณภาพ เราจะเรียนวางแผนโครงการ, Milestone/Deliverable, WBS, ตาราง Gantt (ทำโจทย์คำนวณได้!) และ PERT vs CPM

🎯 จุดประสงค์ 📖 บทเรียน 🎯 แนวข้อสอบ 🏋️ โจทย์ซ้อมมือ

🎯 เรียนจบบทนี้ คุณต้องทำสิ่งเหล่านี้ได้

  • บอกได้ว่าทำไมพัฒนาซอฟต์แวร์ยาก (5 เหตุผล) และทำไมต้องมี Project Management
  • แยก Milestone (จุดสิ้นสุดของ activity) กับ Deliverable (ผลงานที่ส่งให้ลูกค้า) ได้
  • จำประเภทแผนโครงการ 5 แบบ (Quality / Validation / Configuration management / Maintenance / Staff development plan)
  • วาด Gantt chart จากตารางงาน+ความยาวงานได้ แบบโจทย์ในสไลด์ และบอกข้อจำกัดของ Gantt
  • แยก PERT (เน้นเวลา, ใช้ AOA) กับ CPM (เน้นต้นทุน) และวาด network diagram จากตารางความสัมพันธ์งาน
  • จำ 5 หน้าที่ของ Management: Planning, Organizing, Staffing, Directing, Controlling

📖 บทเรียน

🗺️ ที่มาที่ไป — ทำไมงานซอฟต์แวร์ "บริหารยาก"

สไลด์เปิดว่า "Why the SW Development is Difficult?" — เพราะ:

① ผู้ใช้ไม่รู้ requirement ของตัวเอง · ② requirementเปลี่ยนตลอด · ③ การจัด "คนถูกคนกับงานถูกงาน" (right man in the right job) ยาก · ④ การสื่อสารในทีมยิ่งคนเยอะยิ่งยุ่ง · ⑤ เทคโนโลยีเปลี่ยนเร็ว

อุปมา: สร้างบ้านก็มีนายช่างคอยคุมตารางงาน งบ ทีมช่าง คุณภาพวัสดุ — โปรเจกต์ซอฟต์แวร์ก็ต้องมี "นายหน้าบ้าน" แต่ยากกว่า เพราะ "วัสดุ" ของเรา (requirement) เปลี่ยนระหว่างก่อสร้างตลอดเวลา! นี่คือเหตุผลที่ Project Management = "การนำความรู้ ทักษะ เครื่องมือ และเทคนิคมาใช้กับกิจกรรมโครงการให้เป็นไปตาม requirement ของโครงการ"

📐 ควบคุม 3 อย่าง + คุณลักษณะโครงการ 4 ด้าน

Writing projects ต้องควบคุม 3 อย่าง: Quality (คุณภาพผลงาน) · Cost (ต้นทุน) · Delivery (ส่งมอบทันเวลา)

คุณลักษณะโครงการที่ต้องดู (Project Characteristics): Time · Task · Cost · Quality

Management 4 ด้านรอบโครงการ (จากภาพสไลด์): Risk, Scope, Supply, Communication, Organization — ล้อมกลุ่ม Time, Cost, Quality ไว้ตรงกลาง

1) ประเภทแผนโครงการ (Types of Project Plan) — 5 แบบ

แผนอธิบาย (คีย์เวิร์ด)
Quality planอธิบายขั้นตอนและมาตรฐานคุณภาพ (quality procedures and standards) ที่จะใช้ในโครงการ
Validation planอธิบาย approach, ทรัพยากร (resources) และตารางเวลา (schedule) ที่ใช้validate ระบบ
Configuration management planอธิบายขั้นตอนและโครงสร้างการจัดการ configuration ที่จะใช้
Maintenance planพยากรณ์ความต้องการบำรุงรักษาของระบบ, ต้นทุนและแรงงาน (effort) ที่ต้องใช้ — ← ตัวนี้สำคัญกับข้อสอบ Final ที่ถามแผน Maintenance!
Staff development planอธิบายว่าทักษะและประสบการณ์ของสมาชิกทีมจะถูกพัฒนาอย่างไร
📐 โครงสร้าง Project Plan (7 หัวข้อ) + Milestone vs Deliverable

โครงสร้างแผน: Introduction · Project organisation · Risk analysis · Hardware & software resource requirements · Work breakdown · Project schedule · Monitoring and reporting mechanisms

Milestone = จุดสิ้นสุดของ process activity (จุดหมายปลายทางของขั้นตอน เช่น "จบ feasibility report")

Deliverable = ผลงานโครงการที่ส่งมอบให้ลูกค้า (project results delivered to customers)

ตัวอย่างจากสไลด์ (RE process): กิจกรรม Feasibility study → milestone "Feasibility report" · Requirements analysis → "Requirements definition" · Prototype development → "Evaluation report" · Design study → "Architectural design" · จบด้วย "Requirements specification"

อุปมา: Milestone = เส้นชัยย่อย ๆ ในมาราธอน (จุดที่บอกว่าถึง กม.ที่ 10 แล้ว) · Deliverable = รางวัล/หลักฐานที่มอบให้ผู้สนับสนุนเมื่อวิ่งถึงจุดสำคัญ

2) Project Scheduling — ปัญหาคลาสสิกที่อาจารย์ชอบถาม

📐 วิธีทำ + ปัญหา (จำประโยคของ Brooks!)

วิธีทำ scheduling: แบ่งโปรเจกต์เป็น tasks → ประมาณเวลา+ทรัพยากรของแต่ละ task → จัด task ให้ทำพร้อมกัน (concurrently) ใช้คนคุ้มค่าที่สุด → ลด task dependency (ลดการรอคอยระหว่างงาน) → ลงตาราง (แต่จริง ๆ ขึ้นกับ intuition และประสบการณ์ของ project manager)

ปัญหาของ scheduling (4 ข้อ):

  • ประมาณความยากของปัญหาและต้นทุนยากมาก
  • Productivity ไม่ได้แปรผันตรงกับจำนวนคนที่ทำงานเดียวกัน
  • "Adding people to a late project makes it later" — เพิ่มคนให้โปรเจกต์ที่ล่าอยู่แล้วยิ่งทำให้ล่ากว่าเดิม (เพราะ communication overhead — คนใหม่ต้องให้เวลาเรียนรู้ คนเก่าต้องให้เวลาสอน สื่อสารยิ่งยุ่ง)
  • สิ่งไม่คาดคิดมักเกิดเสมอ — วางแผนต้องเผื่อ contingency (เผื่อเวลาเผื่องบ) เสมอ
📐 Project Life Cycle (4 ระยะ) + Management Functions (5 ข้อ)

Project Life Cycle: Initiation (กำหนด scope, ขนาด, task) → Planning (กำหนดกิจกรรม, ต้นทุน, เวลา, risk) → Execution (ทีมทำงานตาม schedule, ผู้อำนวยการคุมให้ตามแผน) → Closing (ทำใน maintenance process — ผลเป็น succeed หรือ fail)

Management Functions (จำคำ 5 ตัว P-O-S-D-C):

  • Planning — ตัดสิน objectives, resources, goals + กำหนด flow ของข้อมูล/คน/สินค้า
  • Organizing — เส้นทางอำนาจและความรับผิดชอบที่ชัดเจน (สร้างโครงสร้างได้ดีเมื่อ goal ชัดและ planning ดี)
  • Staffing — จ้างคนตามโครงสร้างองค์กร: recruiting, compensating, developing, promoting
  • Directing — นำทางลูกน้องให้เข้าใจโครงสร้างและเป้าหมาย + ฝึกอบรมวิศวกรหน้าใหม่
  • Controlling — วัดผลและแก้ไขกิจกรรมให้บรรลุเป้าหมาย (วัด performance เทียบแผน + corrective action)
⚡ Software Pricing — ปัจจัยกระทบราคา 5 ตัว (จับคู่ได้)
  • Market opportunity — ยอมราคาต่ำเพื่อเปิดตลาดใหม่ หวังกำไรระยะยาว
  • Cost estimate uncertainty — ไม่มั่นใจต้นทุน → เพิ่มราคาด้วย contingency
  • Contractual terms — ลูกค้ายอมให้ developer กุม source code ไปใช้ต่อ → ราคาถูกลงได้
  • Requirements volatility — requirement จะเปลี่ยน → ตัดราคาเพื่อชนะงาน แล้วคิดแพงตอนขอเปลี่ยนทีหลัง
  • Financial health — บริษัทกำลังยาก → ตัดราคาเพื่อรักษา cash flow (รอดดีกว่ากำไร)

3) Project Control มี 3 เครื่องมือ: WBS · Gantt · PERT และ CPM

3.1) WBS — Work Breakdown Structure

📐 หั่นงานใหญ่เป็นทวี

WBS = หั่นงานซอฟต์แวร์ทั้งโครงการเป็นกิ่ง ๆ ลงลึกเรื่อย ๆ — ราก: Software Development → แตก 5 กิ่ง: Requirement Definition / Design / Development / Integration Testing / Project Management → กิ่ง Requirement แตกเป็น Old System Analysis, Requirement Analysis, Software Requirement · Design แตกเป็น External Design, Internal Design · Development → Coding, Module Testing · Integration Testing → Integrate Testing, Implement · Project Management → Change Management, Cost Management, Supply Management ฯลฯ

อุปมา: รายการซื้อของเข้าครัวงานเลี้ยง — "ทำอาหารงานเลี้ยง" หั่นเป็น ซื้อของ/เตรียมวัตถุดิบ/ปรุง/จัดโต๊ะ แล้วแตกซ้ำ เช่น "ซื้อของ" → ผัก/เนื้อ/เครื่องปรุง — หั่นละเอียดพอให้ "ประเมินเวลา+มอบหมายคน" ได้

3.2) Gantt Chart — ตารางแท่ง (พร้อมโจทย์จากสไลด์ทำ step-by-step)

📐 ความรู้พื้นฐาน

พัฒนาโดย Henry L. Gantt ปี 1917 เพื่อใช้ scheduling โครงการ · ข้อดี: เห็นชัดว่างานไหนเริ่มเมื่อไหร่-จบเมื่อไหร่ · ข้อจำกัด 3 ข้อ (ออกสอบ!): (1) ไม่แสดงความสัมพันธ์ระหว่างงาน (dependency) ชัดเจน (2) ไม่บอกผลกระทบถ้างานล่าช้า (3) ไม่เหมาะกับโครงการใหญ่ที่มีหลาย subsystem/ซับซ้อน

⚡ ตัวอย่างโจทย์จากสไลด์ — วาด Gantt ทีละขั้น

โจทย์: งาน A–J มีข้อมูลดังนี้ (งาน | งานที่ต้องเสร็จก่อน | เวลาสัปดาห์): A(−,3) B(−,5) C(B,3) D(A,C,4) E(D,8) F(C,2) G(F,4) H(F,2) I(B,5) J(E,G,H,3)

  1. หางานที่เริ่มได้ทันที: งานที่ "ต้องเสร็จก่อน = −" คือ A และ B → เริ่มสัปดาห์ 0: A วิ่ง 0–3, B วิ่ง 0–5
  2. ไล่งานที่อยู่หลัง B: C (หลัง B เสร็จที่สัปดาห์ 5) → 5–8 · I (หลัง B) → 5–10
  3. งาน D รอสองตัว (A, C): เริ่มได้เมื่อทั้งคู่จบ = จบช้าสุดคือ C ที่ 8 → D วิ่ง 8–12
  4. งาน E รอ D: → 12–20 (งานยาวสุด!) · ส่วน F รอ C → 8–10
  5. งาน G, H รอ F: G → 10–14 · H → 10–12
  6. งาน J รอ E, G, H: จบช้าสุดคือ E ที่ 20 → J วิ่ง 20–23 → โครงการจบสัปดาห์ที่ 23
  7. หา Critical Path (เส้นทางวิกฤต) — เส้นทางที่ถ้าล่าแม้แต่งานเดียว โครงการทั้งงานล่า: B(5) → C(3) → D(4) → E(8) → J(3) = 23 สัปดาห์ — ตรงกับเวลาจบรวมพอดี แสดงว่าเป็นเส้นทางยาวสุด

3.3) PERT และ CPM — เครือข่ายงาน (Network Diagram)

📐 เทียบคู่ (ออกสอบจับคู่/เติมคำ)

PERT (Program Evaluation and Review Technique): เน้น development time (เวลา) · เหมาะกับโครงการใหญ่ · วาดด้วย Activity On Arrow (AOA) — ลูกศร = งาน

CPM (Critical Path Method): เน้น development cost (ต้นทุน)

จุดประสงค์การใช้ PERT (4 ข้อ): ① Project Planning — คำนวณเวลาที่ควรใช้ งานเริ่ม/จบเมื่อไหร่ งานไหน critical · ② Project Control — ควบคุมตาม schedule · ③ Resource — ต้นทุน ทีม เครื่องมือ · ④ Project Management — งานไหนควรย่นเวลาพัฒนา

⚡ ตัวอย่างโจทย์ที่ 2 จากสไลด์ — วาด network AOA step-by-step

โจทย์: งาน A(−) B(−) C(A) D(B) E(C,D) — วาดเครือข่าย AOA ให้ถูก

  1. หางานที่ไม่มีงานก่อนหน้า: A และ B → วาดลูกศร A และ B ออกจากจุดเริ่ม (START)
  2. งานที่รอ A: C → วาดลูกศร C ต่อท้าย A (จุดท้ายของ A คือจุดต้นของ C)
  3. งานที่รอ B: D → วาดลูกศร D ต่อท้าย B
  4. งาน E รอ C และ D: สองลูกศร (จากท้าย C และท้าย D) ต้องมาบรรจบจุดเดียวกันก่อน แล้วลูกศร E ออกจากจุดนั้นไปจุดจบ — จุดบรรจบคือวิธี AOA เขียน "ต้องรอหลายงาน" โดยไม่ต้องเขียนประโยคใด ๆ
  5. อ่านเครือข่ายได้ว่า: เส้นทางยาวสุด (critical path) คือเส้นที่มีงานมากสุด/รวมเวลามากสุด — ทาง A→C→E หรือ B→D→E ขึ้นกับระยะเวลาแต่ละงาน ถ้าโจทย์ให้เวลาให้เทียบผลรวม

🏋️ โจทย์ซ้อมมือ (6 ข้อ)

ข้อ 1●○○

เติมคำ: ______ เป็นจุดสิ้นสุดของ process activity / ______ เป็นผลงานโครงการที่ส่งมอบให้ลูกค้า และให้ยกตัวอย่าง milestone ในกระบวนการ RE

เฉลย
  1. ช่องแรก: Milestones — จุดสิ้นสุดของ activity
  2. ช่องสอง: Deliverables — ผลงานส่งให้ลูกค้า
  3. ตัวอย่าง milestone ใน RE: Feasibility report, Requirements definition, Evaluation report, Architectural design, Requirements specification
ข้อ 2●○○

เติมคำ (คลาสสิก): PERT เน้นการพัฒนาด้าน ______ เหมาะกับโครงการ ______ ใช้วิธีวาดแบบ ______ / CPM เน้นการพัฒนาด้าน ______

เฉลย
  1. PERT: เน้น development time (เวลา) เหมาะกับโครงการใหญ่ วาดแบบ Activity On Arrow (AOA)
  2. CPM: เน้น development cost (ต้นทุน)
  3. จำ: PERT = เวลา Time (อักษร T ซ้อนกับ "Time"), CPM = Cost (อักษร C ซ้อนกับ Cost)
ข้อ 3●●○

วิเคราะห์: ทีมโครงการล่าช้า 2 สัปดาห์ ผู้จัดการตัดสินใจ "ดึงคนใหม่ 5 คนเข้าช่วยเดี๋ยวก็เสร็จ" — ถูกหรือผิด อธิบายด้วยหลักการ scheduling

เฉลย
  1. ผิด — ตรงประโยคคลาสสิก: "Adding people to a late project makes it later"
  2. เพราะ communication overhead: คน 5 คนใหม่ต้องเรียนรู้บริบทงาน คนเก่าต้องแบ่งเวลาสอน/สื่อสาร จำนวนช่องทางสื่อสารโตแบบ n(n−1)/2 งานยิ่งล่ากว่าเดิม
  3. ทางที่ดีกว่า: ทบทวนแผน (revise estimates) ปรับ scope/ลำดับงาน และอย่าลืมว่าแผนต้องมี contingency อยู่แล้ว ("The unexpected always happens")
ข้อ 4●●●

คำนวณ (เลียนแบบโจทย์สไลด์): งาน P(−,2) Q(−,4) R(P,3) S(Q,6) T(R,S,1) — หาเวลาเริ่ม-จบของแต่ละงาน ระยะเวลารวมโครงการ และ critical path

เฉลย step-by-step
  1. งานไร้เงื่อนไข: P → 0–2 · Q → 0–4
  2. R รอ P: → 2–5 · S รอ Q: → 4–10
  3. T รอ R และ S: เริ่มเมื่อทั้งคู่จบ = จบช้าสุดคือ S ที่สัปดาห์ 10 → T วิ่ง 10–11
  4. เวลารวมโครงการ = 11 สัปดาห์
  5. critical path: เทียบสองเส้นทาง Q→S→T = 4+6+1 = 11 สัปดาห์ (ยาวสุด) ส่วน P→R→T = 2+3+1 = 6 สัปดาห์ → Q→S→T คือ critical path — งาน P, R มีเผื่อเวลา (float) 5 สัปดาห์
ข้อ 5●●●

วาด network: จากตารางงาน: A(−) B(−) C(−) D(A) E(B,C) F(D,E) — วาด AOA network และบอกว่างานใดต้องรองานอะไร

เฉลย
  1. START แตก 3 ลูกศร: A, B, C (ไม่มีงานก่อนหน้า)
  2. D ต่อจากจุดท้ายของ A
  3. E รอสองงาน: จุดท้ายของ B และจุดท้ายของ C ต้องบรรจบจุดเดียวกัน แล้วลูกศร E ออกจากจุดนั้น
  4. F รอสองงาน: จุดท้าย D บรรจบกับจุดท้าย E แล้ว F วิ่งไป END
  5. สังเกต: งานที่ "รอหลายงาน" คือ E และ F — ใน AOA จะใช้จุดบรรจบ (event node) แทนคำพูด "รอทั้งคู่พร้อมกัน"
ข้อ 6●●○

โยงข้อสอบเขียน: ถ้าข้อสอบให้เขียน "แผนบริหารโปรเจกต์ที่คุณทำ" ควรเอาสาระไหนจากบทนี้มาใส่บ้างให้ได้คะแนนเต็ม

แนวคำตอบ (โครง)
  1. โครงสร้างแผน 7 หัวข้อ: Introduction / Project organisation / Risk analysis / HW-SW resources / Work breakdown / Schedule / Monitoring และ reporting
  2. WBS: หั่นงานโปรเจกต์เป็นกิจกรรมย่อยมีผลลัพธ์ (เช่น requirements, design, coding, testing, นำส่ง)
  3. ตารางเวลา: ใช้ Gantt แสดงเวลาเริ่ม-จบแต่ละงาน + ระบุ milestone/deliverable สำคัญ
  4. ควบคุม 3 อย่าง: Quality / Cost / Delivery พร้อมเผื่อ contingency
  5. ระบุแผนเสริมที่เกี่ยวกับ Final: Validation plan (วิธีทดสอบ) + Maintenance plan (คาดการณ์งานบำรุงรักษา ต้นทุน แรงงาน) — สองแผนนี้ตอบโจทย์ "จะทดสอบและวางแผน maintenance อย่างไร" พอดี → ดูเฉลยเต็มที่หน้าติว Final
