1️⃣ ช่วงที่ 2ก — ความรู้ข้อจับคู่: Software Testing

📚 พื้นฐานที่ต้องรู้ก่อนจับคู่

ทำไมต้องทดสอบเป็นระบบ? เพราะทุกคนที่เขียนโปรแกรม "ทดสอบ" อยู่แล้วโดยธรรมชาติ — คำถามคือทำแบบสุ่ม ๆ หรือมีแผน เป้าหมายคือลอง input ที่ "วิกฤต" ให้มากที่สุดในเวลาที่มี จำคำพูดดังของ Dijkstra: "Testing shows the presence, not the absence of bugs" — การทดสอบพิสูจน์ได้แค่ว่า "มีบั๊ก" ไม่เคยพิสูจน์ได้ว่า "ไม่มีบั๊กเหลืออยู่"

Test case = การเลือก input หนึ่งชุด + ผลที่คาดว่าจะได้ (expected result) — จำว่าต้องมี "คำตอบที่คาดหวัง" เสมอ ไม่งั้นไม่ใช่ test case

White-box vs Black-box = สองมุมมองใหญ่: White-box มองข้างในโค้ด (โดยนักพัฒนา) · Black-box มองแค่หน้าตาการใช้งานตาม spec (โดยลูกค้า)

ระดับทำอะไรใครทำถ้าเป็นระบบ CS-Hospital ตัวอย่างคือ…
Unit testทดสอบโมดูลเดียว แบบโดดเดี่ยว เทียบกับ unit specificationนักพัฒนา (White-box)ทดสอบฟังก์ชันตรวจว่าเลข HN ผู้ป่วยต้องเป็นตัวเลข 7 หลักพอดี ป้อนผิดรูปแบบต้องปฏิเสธ
Integration testนำโมดูลที่ผ่าน unit test มาต่อกัน ทดสอบว่าทำงานร่วมกันได้นักพัฒนาหน้าลงทะเบียนผู้ป่วยส่งข้อมูลเข้าฐานข้อมูลจริงได้ และหน้าค้นหาดึงข้อมูลชุดเดียวกันมาแสดงได้
Function testยืนยันว่าFunctional Requirements ถูกตอบสนองครบทีม QAไล่เช็กทีละข้อ: เก็บประวัติได้ / ออกใบรับรองได้ / ส่งต่อผ่าน LINE-Email ได้
Quality testยืนยันNon-functional Requirements (คุณภาพ)ทีม QAค้นหาประวัติต้องเสร็จใน 2 วินาที, ทดสอบว่าแพทย์นอกเขตเข้าถึงข้อมูลไม่ได้ (ความปลอดภัย)
System testทดสอบระบบสมบูรณ์ทั้งหมด เทียบ System Specificationทีมรวมระบบรัน flow เต็ม: รับผู้ป่วยใหม่ → บันทึกผลรักษา → ออกรายงาน → ส่งต่อเฉพาะทาง จบทั้งสาย
Acceptance testลูกค้าทดสอบและยอมรับว่าตรงความต้องการลูกค้า (Black-box)สาธิตให้ตัวแทนโรงพยาบาลใช้กับเคสผู้ป่วยจำลอง แล้วเซ็นรับมอบ (sign-off)
Installation testติดตั้งและทดสอบในสภาพแวดล้อมจริงของผู้ใช้ทีมติดตั้ง + ผู้ใช้ติดตั้งบนเซิร์ฟเวอร์และเครือข่ายของโรงพยาบาลจริง ทดลองใช้ 1 วันก่อนเปิดใช้เต็มระบบ
🎯 คีย์เวิร์ดที่โจทย์จับคู่ชอบใช้ — เห็นคำนี้ = คำตอบนั้น
  • "โดดเดี่ยว / แยกทดสอบแต่ละโมดูล" → Unit test
  • "รวม/ต่อโมดูลเข้าด้วยกัน" → Integration test
  • "Functional Requirements" → Function test
  • "Non-functional / คุณภาพ / ความเร็ว-ความปลอดภัย" → Quality test
  • "ระบบสมบูรณ์ / System Specification" → System test
  • "ลูกค้า / ผู้ใช้ยอมรับ / sign-off" → Acceptance test
  • "ติดตั้ง / สภาพแวดล้อมจริงของผู้ใช้" → Installation test
📚 เกร็ดเทคนิคที่บางปีถามร่วมด้วย (อ่านผ่อน ๆ พอเข้าใจแนวคิด)
  • Equivalence testing — แบ่ง input เป็นกลุ่มที่ "คาดว่าทำงานเหมือนกัน" แล้วหยิบตัวแทนกลุ่มละ 1 ค่า · กฎนับกลุ่ม: กำหนดเป็นช่วง (เช่น 1–120) = 1 valid + 2 invalid · กำหนดค่าเดียว (13 หลักพอดี) = 1+2 · กำหนดเป็นเซต (9 หรือ 10 หลัก) = 1+1 · boolean = 1+1
  • Boundary testing — จับเฉพาะ "ขอบ" ที่คนเขียนโค้ดพลาดบ่อย: 0, ค่าน้อยสุด/มากสุด, ช่องว่าง, null, สับสน > กับ ≥
  • State-based testing — นิยามสถานะของระบบ (เช่น ล็อกประตูมี Locked / Accepting / Unlocked / Blocked) แล้วทดสอบให้ครบทุกสถานะ + ทุก transition ที่ถูกกฎ

🏋️ ฝึกจับคู่ Testing — เลียนแบบข้อสอบจริง

2️⃣ ช่วงที่ 2ข — ความรู้ข้อจับคู่: Software Maintenance

📚 พื้นฐานที่ต้องรู้ก่อนจับคู่

นิยาม: Software Maintenance = การแก้ไข/ปรับปรุงระบบซอฟต์แวร์หลังส่งมอบแล้ว เพื่อ ① แก้ข้อผิดพลาด (correct faults) ② ปรับปรุงประสิทธิภาพหรือคุณลักษณะอื่น (improve performance) ③ ปรับตัวกับสิ่งแวดล้อมที่เปลี่ยน (adapt to changed environment)

ทำไมเรื่องนี้สำคัญ? เพราะซอฟต์แวร์ "ไม่จบ" ตอนส่งมอบ — ต้นทุนบำรุงรักษาสะสมหลายปีมักแพงกว่าค่าสร้างครั้งแรก (เหมือนค่ารถ: ซื้อครั้งเดียวแต่ค่าน้ำมัน-ซ่อมบำรุงจ่ายต่ออีก 10 ปี)

ประเภทสัดส่วนคีย์เวิร์ดในโจทย์ตัวอย่างในระบบ CS-Hospital
Corrective21%"พัง / ผิดพลาด / bug / แก้ error"ระบบคิดค่ารักษาผิดในเงื่อนไขเฉพาะ ทีมเข้าไปแก้โค้ด
Adaptive25%"OS / DB / browser / แพลตฟอร์ม / environment ใหม่"โรงพยาบาลอัปเกรดฐานข้อมูลรุ่นใหม่ ทีมปรับระบบให้รองรับ
Perfective50% — เยอะสุด"อยากได้เพิ่ม / เพิ่มฟังก์ชัน / ปรับให้ดีขึ้น / ตามความต้องการใหม่"ผู้ใช้ขอรายงานสถิติผู้ป่วยรายเดือนเพิ่ม — ทำใหม่ให้
Preventive4% — น้อยสุด"refactor / ปรับโครงสร้าง / เพิ่มเอกสาร / กันปัญหาอนาคต"แยกกฎธุรกิจออกเป็นโมดูล + เขียนเอกสารเพิ่ม เพื่อให้แก้ง่ายขึ้นในอนาคต
🎯 3 กับดักลักไก่ของข้อจับคู่ Maintenance
  • เห็นคำ "เปลี่ยน OS/DB/เครื่องใหม่" = Adaptive — อย่าสับสนกับ Corrective เพราะระบบ "ยังไม่พัง" แค่สิ่งแวดล้อมเปลี่ยน
  • "เพิ่มฟังก์ชันใหม่ / ทำให้ใช้ง่ายขึ้น" = Perfective เสมอ (และเป็นกลุ่มใหญ่สุด 50% — โจทย์ชอบถาม "แบบไหนพบมากที่สุด")
  • Preventive คือการแก้ "ข้างใน" ที่ผู้ใช้ไม่เห็นผลอะไรเลย (โครงสร้างโค้ด/เอกสาร) — ถ้าโจทย์บอกว่าผู้ใช้ได้อะไรใหม่ แปลว่าไม่ใช่ Preventive

🏋️ ฝึกจับคู่ Maintenance — เลียนแบบข้อสอบจริง

D) Refactor โค้ด + อัปเดตเอกสารชั้นใน เพื่อให้แก้ง่ายในอนาคต

1→A (แก้ error) · 2→B (สภาพแวดล้อม/แพลตฟอร์มเปลี่ยน) · 3→C (requirement ผู้ใช้ใหม่) · 4→D (เพิ่ม maintainability)

ท่องตัวเลขให้ขึ้นใจ: Corrective 21 · Adaptive 25 · Perfective 50 · Preventive 4

✍️ ช่วงที่ 3 · ข้อเขียนข้อ 1 — เขียน FR และ NFR ของระบบ

📚 รู้ก่อนเขียน — FR กับ NFR ต่างกันอย่างไร

Functional Requirement (FR) = สิ่งที่ระบบ "ต้องทำอะไร" (What the system will do) — ฟังก์ชัน งาน พฤติกรรมที่ผู้ใช้จะได้ใช้ เช่น เก็บข้อมูล ค้นหา ออกรายงาน ส่งต่อผล

Non-Functional Requirement (NFR) = ระบบ "ทำได้ดีแค่ไหน" (How well) — คุณภาพและข้อจำกัด เช่น ปลอดภัยแค่ไหน เร็วแค่ไหน ทนผู้ใช้กี่คน ใช้ง่ายแค่ไหน — จัดหมวดด้วยกรอบ FURPS+ ตามตารางนี้:

ตัวอักษรย่อมาจากถามตัวเองว่า…ตัวอย่างประโยคของ CS-Hospital
FFunctionality (รวม Security)ระบบปกป้องอะไรได้ไหม"เข้ารหัสข้อมูลขณะส่ง เข้าถึงได้เฉพาะแพทย์ผู้รับผิดชอบ"
UUsabilityคนไม่เก่งคอมใช้ได้ไหม"พยาบาลมือใหม่ลงทะเบียนจบใน 5 นาที ไม่ต้องอ่านคู่มือ"
RReliabilityพังบ่อยไหม ข้อมูลหายไหม"พร้อมใช้ ≥ 99.5% ไม่สูญข้อมูลเมื่อเน็ตหลุดชั่วคราว"
PPerformanceเร็วแค่ไหน ทนกี่คน"ค้นประวัติภายใน 2 วินาที ที่ผู้ใช้พร้อมกัน 200 คน"
SSupportabilityต่อยอด/ดูแลง่ายไหม"เพิ่มแพทย์ใหม่ได้โดยผู้ดูแลระบบ ไม่ต้องแก้โค้ด"
+ข้อจำกัดอื่น ๆมีเงื่อนไขพิเศษไหม"ใช้ได้ทั้งคอมและมือถือ (responsive)"

กติกาการเขียนให้ได้คะแนน: ประโยค FR เริ่มด้วย "ระบบต้องสามารถ…" · ประโยค NFR ต้องมีตัวเลขเกณฑ์วัด เสมอ (เขียนแค่ "ระบบต้องเร็ว" = ได้คะแนนน้อย)

⚡ สูตรตอบ 3 ขั้น — ใช้ได้กับทุกระบบ
  1. อ่านโจทย์วลีต่อวลี — ทุกประโยคในโจทย์คือ "เมล็ด requirement": "เก็บข้อมูลผู้ป่วย" = ฟังก์ชัน, "ส่งต่อผ่าน LINE/Email" = ฟังก์ชัน + ช่องทาง
  2. จำแนกลง 2 กลุ่ม: สิ่งที่ระบบ "ทำ" (เก็บ ค้น แสดง ออกรายงาน ส่งต่อ ยืนยันตัวตน) → FR · สิ่งที่บอก "ดีแค่ไหน" → NFR แล้วผูกกับ FURPS+
  3. เขียนเป็นประโยคมาตรฐาน: FR = "ระบบต้องสามารถ…" · NFR = คุณภาพ + เกณฑ์วัด เช่น "ตอบสนองภายใน 2 วินาทีเมื่อผู้ใช้พร้อมกัน 500 คน"
เฉลยเต็มคำตอบตัวอย่างสำหรับ CS-Hospital

Functional Requirements (FR):

  1. FR-1 ระบบต้องสามารถบันทึกและจัดเก็บข้อมูลผู้ป่วย ประวัติการรักษา ผลการรักษา และผลจากห้องปฏิบัติการ (Lab results) และให้ค้นดึงย้อนหลังได้
  2. FR-2 ระบบต้องสามารถบันทึกและจัดการข้อมูลบุคลากรทางการแพทย์ (แพทย์ พยาบาล นักวิชาการ) พร้อมสิทธิ์การเข้าถึงของแต่ละบทบาท
  3. FR-3 ระบบต้องสามารถสร้างและพิมพ์/ออกรายงาน เช่น ใบรับรองแพทย์ และประวัติการรักษาของผู้ป่วย
  4. FR-4 ระบบต้องสามารถส่งต่อผลการรักษาหรือผลวินิจฉัยไปยังทีมแพทย์ผู้เชี่ยวชาญ/ทีมโรคเฉพาะทางผ่านช่องทางออนไลน์ (LINE หรือ Email) และบันทึกสถานะการส่ง
  5. FR-5 (เสริมได้คะแนน) ระบบต้องสามารถยืนยันตัวตนผู้ใช้ (ล็อกอิน) และแยกสิทธิ์ตามบทบาท เช่น แพทย์/พยาบาล/เจ้าหน้าที่

Non-Functional Requirements (NFR — จัดตาม FURPS+):

  1. NFR-1 Security (F) ข้อมูลผู้ป่วยเป็นความลับทางการแพทย์ ระบบต้องเข้ารหัสข้อมูลขณะส่ง (HTTPS) และเข้าถึงข้อมูลผู้ป่วยได้เฉพาะบุคลากรที่รับผิดชอบ (role-based access) พร้อมบันทึก log การเข้าถึงทุกครั้ง
  2. NFR-2 Usability (U) พยาบาล/เจ้าหน้าที่ที่ไม่เชี่ยวชาญคอมพิวเตอร์ต้องลงทะเบียนผู้ป่วยใหม่สำเร็จภายใน 5 นาทีโดยไม่ต้องอ่านคู่มือ (รองรับภาษาไทย หน้าจอเรียงตามลำดับงานจริง)
  3. NFR-3 Reliability (R) ระบบต้องพร้อมใช้งานตลอดเวลาบริการ (availability ≥ 99.5%) และไม่สูญหายข้อมูลการรักษาแม้เครือข่าย/เครื่องล่มชั่วคราว (backup อัตโนมัติทุกวัน)
  4. NFR-4 Performance (P) ระบบต้องแสดงผลการค้นหาประวัติผู้ป่วยภายใน 2 วินาที เมื่อมีผู้ใช้พร้อมกัน 100 คน และรองรับผู้ใช้พร้อมกันอย่างน้อย 200 คนในเวลาเปิดบริการ
  5. NFR-5 Supportability (S) ระบบต้องเพิ่มแพทย์/ทีมเฉพาะทางใหม่และแก้แบบฟอร์มรายงานได้โดยผู้ดูแลระบบ โดยไม่ต้องแก้โค้ด (รองรับการบำรุงรักษาและขยายในอนาคต)
  6. NFR-6 (เสริม "+") ระบบต้องใช้งานได้ทั้งคอมพิวเตอร์และมือถือ (responsive) เพราะบุคลากรเดินตรวจผู้ป่วยต้องเปิดด้วยแท็บเล็ตได้
💡 ทำไมเฉลยนี้ "ชนะ" — 3 จุดที่กรรมการมองหา
  1. ครอบโจทย์ทุกบุลลี: FR-1 จากบุลลี ①, FR-2 จาก ②, FR-3 จาก ③, FR-4 จาก ④ — ไม่มีบุลลีตกหล่น (กรรมการติ๊กตรงนี้)
  2. NFR มีเกณฑ์วัดจริง: "2 วินาที", "99.5%", "200 คน" — NFR ที่เขียน "ต้องเร็ว/ต้องปลอดภัย" แบบลอย ๆ ได้คะแนนน้อย
  3. อ้าง FURPS+ ให้เห็น: ติดชื่อหมวดไว้ให้กรรมการเห็นว่าเรามีกรอบวิชาการ

🎨 ข้อเขียนข้อ 2 — เขียน Use case diagram ของ CS-Hospital

📚 รู้ก่อนวาด — Use case คืออะไร ประกอบด้วยอะไร

Use case = การบรรยายทีละขั้นว่า "ใคร ใช้ระบบทำอะไร เพื่อบรรลุเป้าหมายอะไร" — ใช้กับการวิเคราะห์และเขียน Functional Requirements โดยมี 3 องค์ประกอบ: ① Actors (ผู้เกี่ยวข้องภายนอกระบบ) · ② Use case diagram (ภาพความสัมพันธ์) · ③ Scenarios (บทสนทนาทีละขั้น)

Actor มี 4 ชนิด — ต้องแยกให้ออกก่อนวาด:

ชนิดหน้าที่ตัวอย่างใน CS-Hospital
Initiating (primary)เริ่มการใช้ use case เพื่อบรรลุเป้าหมายพยาบาล/เจ้าหน้าที่, แพทย์, Admin
Participating (secondary)ร่วมด้วยแต่ไม่ได้เริ่มฐานข้อมูลผู้ป่วย
— Supportingช่วยให้ use case สำเร็จLINE API, Email Server
— Offstageไม่เริ่ม ไม่ช่วย แต่ถูกแจ้งผลหัวหน้าแพทย์ที่ได้รับสำเนารายงาน

ตาราง 4 คำถาม «include» vs «extend» (ออกสอบบ่อยมาก):

คำถาม«include»«extend»

Base use case สมบูรณ์โดยไม่มีมัน?NoYes

กับดัก Login (อาจารย์เน้นใน video): อย่าวาด Login เป็นวงรีใหญ่แล้วให้ทุก use case เส้นต่อเข้าหา (BAD) — ให้ทำเป็น subroutine «include» เรียกใช้ (GOOD) หรือยุบเป็น precondition เลย เพราะ Login ไม่ใช่เป้าหมายธุรกิจที่ใคร "อยากทำ"

⚡ ขั้นวาด 4 จังหวะ (ใช้ได้กับทุกระบบ)
  1. หา initiating actors — ใคร "กดใช้" ระบบ? อ่านโจทย์: พยาบาล/เจ้าหน้าที่ (ลงทะเบียน บันทึกผล), แพทย์ (วินิจฉัย ออกใบรับรอง ส่งต่อ), ผู้ดูแลระบบ (จัดการบุคลากร)
  2. หา participating actors — ระบบภายนอกใดช่วย? LINE API, Email Server, (Database ก็เป็น participating ได้)
  3. ตั้งชื่อ use case เป็นกริยา — RegisterPatient, RecordTreatmentResult, IssueMedicalCertificate, SendDiagnosisToSpecialist, ManageMedicalStaff (+ AuthenticateUser เป็น subroutine)
  4. วาด: actor นอกกรอบ, ellipse ในกรอบ (system boundary ชื่อระบบ), «include» จาก use case ที่ต้องยืนยันตัวตน
🎯 ข้อห้ามพลาดในข้อนี้
  • ห้ามให้ actor อยู่ในกรอบระบบ (actor คือสิ่งนอกระบบเสมอ)
  • ห้ามตั้งชื่อ use case เป็นคำนาม ("Patient", "Report") — ต้องมีกริยา
  • ห้ามวาด "ห้องผู้ป่วย/อุปกรณ์" เป็น actor — มันไม่ได้ปฏิสัมพันธ์กับระบบ
  • Login ทำเป็น subroutine «include» หรือยุบเป็น precondition — ไม่ใช่วงรีศูนย์กลางที่ทุกอย่างต่อเส้นตรง

🗃️ ข้อเขียนข้อ 3 — เขียน Schema ของ CS-Hospital

📚 รู้ก่อนวาด — Schema คืออะไร อ่านสัญลักษณ์ยังไง

Schema ในบริบทข้อสอบนี้ = แผนผังฐานข้อมูล (Entity-Relationship diagram) ที่บอกว่าระบบเก็บข้อมูลอะไรบ้าง และข้อมูลเหล่านั้นเชื่อมโยงกันอย่างไร

ศัพท์ 4 คำที่ต้องเข้าใจ: Entity = ตารางเก็บข้อมูล (สิ่งที่เรา "เก็บของ") · Attribute = คอลัมน์ในตาราง · PK (Primary Key) = หมายเลขประจำตัวไม่ซ้ำของแถว เช่น patient_id · FK (Foreign Key) = คอลัมน์ที่ชี้ไปยัง PK ของตารางอื่น (ทำให้สองตารางเชื่อมกัน)

สัญลักษณ์ crow's foot (เท้าอีก้า) บอก "จำนวน" ของความสัมพันธ์:

สัญลักษณ์ความหมายตัวอย่าง
ขีด | |exactly one — หนึ่งเดียวการจอง 1 ครั้ง มีแพทย์ 1 คน
อีก้า <one or more — หนึ่งขึ้นไปผู้ป่วย 1 คน มีประวัติรักษาอย่างน้อย 1 ครั้ง
วงกลม+ขีด ○|zero or one — ศูนย์หรือหนึ่งการรักษาอาจยังไม่มีใบเสร็จ
วงกลม+อีก้า ○<zero or more — ศูนย์หรือหลายการรักษาอาจยังไม่มีผลแล็บ
⚡ สูตรอ่านโจทย์หา Schema 4 ขั้น
  1. ขั้น 1 หา entity: อ่านโจทย์ทีละวลี — "สิ่งที่ต้องเก็บข้อมูล" = entity เช่น ผู้ป่วย, บุคลากร, การรักษา, ผลแล็บ, การส่งต่อ
  2. ขั้น 2 กำหนด attribute + PK: ให้ทุกตารางมี PK ของตัวเอง (patient_id, staff_id, record_id…)
  3. ขั้น 3 หาความสัมพันธ์: ถามว่า "หนึ่งอัน เชื่อมกับอีกฝั่งกี่อัน" — ผู้ป่วย 1 : การรักษาหลายครั้ง (1:N) ฯลฯ
  4. ขั้น 4 ใส่สัญลักษณ์จำนวน: ฝั่ง "หลาย" วาดปีกอีก้า, ฝั่ง "หนึ่ง" วาดขีด พร้อม FK เชื่อม
📐 ข้อความอธิบายที่ควรพิมพ์กำกับภาพ (ทำให้คะแนนเต็ม)
  • Patient 1:N TreatmentRecord — ผู้ป่วยหนึ่งคนมีประวัติรักษาหลายครั้ง
  • MedicalStaff 1:N TreatmentRecord — บุคลากรหนึ่งคนดูแลการรักษาหลายรายการ
  • TreatmentRecord 1:N LabResult — การรักษาหนึ่งครั้งอาจมีผลแล็บหลายผล (เลือด/ปัสสาวะ)
  • TreatmentRecord 1:N Certificate / 1:N Referral — ออกใบรับรอง/ส่งต่อเฉพาะทางผูกกับการรักษาครั้งนั้น
  • ระบุ PK (ขีดเส้นใต้/ตัวหนา) และ FK ทุกตาราง — กรรมการมองหาตรงนี้

🏛️ ข้อเขียนข้อ 4 — เขียนสถาปัตยกรรมซอฟต์แวร์ของ CS-Hospital

📚 รู้ก่อนวาด — สถาปัตยกรรมคืออะไร และเลือกสไตล์ไหนตอบ

นิยาม: Software Architecture = ชุดการตัดสินใจระดับสูงที่กำหนดโครงสร้างของระบบ — มี "ส่วนย่อย" อะไรบ้าง และ "เชื่อมกัน" อย่างไร — ทำตั้งแต่เนิ่น ๆ แก้ยากมากทีหลัง และไม่ใช่ phase ของการพัฒนา (เป็นการตัดสินใจที่เกิดต่อเนื่อง)

สำหรับระบบเว็บแบบ CS-Hospital เลือกผสม 3 สไตล์นี้ตอบ (ตามหลัก "ระบบจริงผสมหลายสไตล์"):

สไตล์หน้าตาเป็นอย่างไรทำไมเหมาะกับ CS-Hospital
Client/ServerClient = triggering process (ริเริ่มส่งคำขอ) · Server = reactive process (คอยฟังและตอบ) · คุยกันผ่าน Connectorเว็บแอปโดยธรรมชาติคือ browser (client) ร้องขอ ไปยัง web server
Layered (Multi-Tiered)แบ่ง 3 ชั้น: UI Layer → Application Logic Layer → Technical Services Layer — ชั้นบนใช้บริการชั้นล่างแยกหน้าจอ/กฎธุรกิจ/ฐานข้อมูลออกจากกัน แก้ทีละชั้นไม่กระทบกัน (maintain ง่าย — separation of concerns)
Central Repositoryมีคลังข้อมูลกลาง (ฐานข้อมูลเดียว) ที่ทุก subsystem อ่าน/เขียนผ่านทุกแผนกต้องเห็นข้อมูลผู้ป่วย "ชุดเดียวกัน" ไม่ใช่คนละสำเนา

วิธีตอบให้เต็ม: เปิดด้วยนิยาม 1 ประโยค → วาดไดอะแกรม → ตั้งชื่อสไตล์กำกับชัด ๆ → ปิดด้วยเหตุผลที่เลือก (กรรมการมองหาชื่อสไตล์ + เหตุผล)

🧪 ข้อเขียนข้อ 5 — "จากโปรเจกต์ที่ทำ จะทดสอบระบบอย่างไร"

📚 รู้ก่อนเขียน — Verification กับ Validation (คู่คำที่อาจารย์รัก)

ประโยคคลาสสิกของ Barry Boehm ที่แยกสองมุมมอง:

  • Verification ถามว่า "Are we building the product right?" — เราสร้างสินค้าถูกวิธีไหม (ตรง spec ไหม) — มุมมองนักพัฒนา มองข้างใน → ทำผ่าน Unit + System testing
  • Validation ถามว่า "Are we building the right product?" — เราสร้างสินค้าที่ถูกไหม (ตรงใจผู้ใช้ไหม) — มุมมองลูกค้า มองข้างนอก → ทำผ่าน Acceptance testing

วิธีจำ: ตำแหน่งคำ "right" สลับกัน — product RIGHT = ถูกวิธี = Verification · RIGHT product = ของที่ใช่ = Validation

และลำดับการทดสอบ 7 ระดับ (Unit → Integration → Function → Quality → System → Acceptance → Installation) อ่านซ้ำได้จาก ส่วน 1ก ข้างบน — ข้อนี้จะเอามาเรียงเป็นแผน

⚡ โครงคำตอบ 5 ขั้น (เดินจากบทที่ 4 + 10)
  1. เริ่มจาก requirement: ทุก FR/NFR ที่เขียนไว้มี acceptance test คู่กัน (เขียน test ก่อนพัฒนา — TDD)
  2. Verification — Unit testing (white box): นักพัฒนาทดสอบแต่ละโมดูลแบบโดดเดี่ยว (เช่น ฟังก์ชันคำนวณคิว, ตรวจรูปแบบเลขบัตร) ด้วย input ปกติ + ขอบ (boundary) + invalid ตาม equivalence classes ใช้ mock object แทน DB/บริการ LINE ขณะทดสอบ
  3. Verification — Integration + System testing: ต่อโมดูลแบบ bottom-up/sandwich แล้วทดสอบระบบสมบูรณ์เทียบ System Spec (เช่น flow ลงทะเบียน→บันทึกผล→ออกรายงาน ทั้งสาย)
  4. Function test ครอบ FR + Quality test ครอบ NFR: เช่น performance test ค้นประวัติ < 2 วินาทีที่ 200 ผู้ใช้ / security test แพทย์นอกเขตเข้าไม่ได้ / reliability test ถอด network แล้วข้อมูลไม่หาย
  5. Validation — Acceptance testing โดยลูกค้า: สาธิตให้โรงพยาบาลทดลองใช้กับเคสจริงจำลอง แล้ว sign-off; ต่อด้วย Installation test ในเครื่องบริการของโรงพยาบาลจริงก่อนเปิดใช้
ตัวอย่างtest case 1 ชุดที่ควรเขียนโชว์ในข้อนี้
Test-case ID: TC-01  | Use Case Tested: RegisterPatient (main scenario)
Pass/fail: ผ่านเมื่อบันทึกผู้ป่วยใหม่ด้วยข้อมูลครบสำเร็จ และปฏิเสธข้อมูลไม่ครบ/รูปแบบผิด
Input: ชื่อ-สกุล, HN, เบอร์โทร 9-10 หลัก
Step 1 กรอกข้อมูลครบถูกต้อง → บันทึกสำเร็จ + สร้าง HN ใหม่ (pass)
Step 2 ทิ้งช่องชื่อว่าง → ระบบตรวจและแจ้ง "กรุณากรอกชื่อ" ไม่ crash (boundary/invalid)
Step 3 เบอร์โทร 8 หลัก → ปฏิเสธพร้อมข้อความเกณฑ์ (equivalence: ผิดรูปแบบ)
Step 4 ค้น HN ที่เพิ่งสร้าง → พบข้อมูลตรงทุกช่อง (verify persistence)

โชว์เทคนิค: มี expected result ทุก step + กล่าวถึง equivalence/boundary — เชื่อมคำศัพท์บทที่ 10 ให้กรรมการเห็น

🔧 ข้อเขียนข้อ 6 — "จะวางแผน Maintenance อย่างไร"

📚 รู้ก่อนเขียน — 4 ประเภท + กระบวนการ 5 ขั้น

4 ประเภท (อ่านซ้ำจาก ส่วน 1ข): Corrective 21% แก้บั๊ก · Adaptive 25% ตามสิ่งแวดล้อมใหม่ · Perfective 50% ตามความต้องการใหม่ของผู้ใช้ · Preventive 4% เพิ่ม maintainability

กระบวนการทำ maintenance มาตรฐาน 5 ขั้น — ข้อนี้ให้เดินตามโครงนี้:

⚡ โครงคำตอบ: เดิน 5 ขั้น + ครอบ 4 ประเภท + มีตัวชี้วัด
  1. รับคำขอ (Change requests): เปิดช่องทางเดียว (ระบบ ticket) ให้โรงพยาบาลแจ้ง — แยกประเภท: fault repair / platform adaptation / enhancement พร้อมระดับด่วน (เคสกระทบการรักษาผู้ป่วย = ฉุกเฉิน)
  2. Impact analysis: ตรวจทุกคำขอว่ากระทบโมดูล/ตารางใด (เช่นแก้ตาราง Patient กระทบรายงาน+ส่งต่อเฉพาะทาง) ประเมินความเสี่ยง-เวลา-ทรัพยากร ก่อนตกลงทำ
  3. Release planning: รวมงานเป็นรอบ (เช่นรายเดือน) เลือกเวลา release นอกชั่วโมงบริการ แจ้งล่วงหน้า + สำรองข้อมูลก่อนอัปเดตเสมอ
  4. Change implementation: แก้บนสำเนา รัน test suite เดิมทั้งหมด (unit→system) ให้ผ่าน ก่อนขึ้นจริง + อัปเดตเอกสาร/โครงสร้าง (preventive ไปด้วยในตัว)
  5. System release + ติดตาม: ปล่อยเวอร์ชัน แจ้งผู้ใช้ แล้ววัดตัวชี้วัด 4 ตัว: จำนวนคำขอ corrective ต่อเดือน / เวลาเฉลี่ย impact analysis / เวลาเฉลี่ย implement / คำขอค้าง — ถ้าโตต่อเนื่อง = maintainability ถดถอย ต้องจัด refactoring ทันที

ปิดท้าย 1 บรรทัดได้คะแนนเพิ่ม: "แผนนี้แตกจาก Maintenance plan หนึ่งใน Types of Project Plan และครอบ maintenance 4 ประเภท: Corrective (SLA แก้บั๊กด่วนเคสการรักษา) / Adaptive (ติดตาม OS/Browser/DB ทุกไตรมาส) / Perfective (backlog ฟีเจอร์ใหม่จากผู้ใช้) / Preventive (จองเวลา refactoring + ดูแลเอกสาร)"

🏋️ ฝึกข้ามบท 8 ข้อ — เลียนแบบข้อสอบจริง

ข้อ 1●●○

ดัดแปลง (CS-Pizza ปี 67): ระบบ CS-Pizza: ลูกค้าสั่งพิซซ่าออนไลน์ เลือกเมนู/ขนาด เช็คสถานะออเดอร์ จ่ายเงินออนไลน์ ร้านจัดส่ง — เขียน FR 4 ข้อ + NFR 4 ข้อ (FURPS) ใน 6 นาที

แนวคำตอบ
  1. FR-1: ระบบต้องสามารถให้ลูกค้าเลือกเมนู/ขนาดและสร้างออเดอร์ได้
  2. FR-2: ระบบต้องสามารถแสดงสถานะออเดอร์แบบเรียลไทม์ (รับออเดอร์→กำลังทำ→กำลังจัดส่ง)
  3. FR-3: ระบบต้องสามารถรับการชำระเงินออนไลน์และออกใบเสร็จ
  4. FR-4: ระบบต้องสามารถส่งออเดอร์ถึงพนักงานส่งพร้อมที่อยู่
  5. NFR-P: ยืนยันการชำระเงินภายใน 3 วินาที รองรับออเดอร์พร้อมกันช่วงค่ำ 500 ออเดอร์/ชม.
  6. NFR-U: ลูกค้าใหม่สั่งสำเร็จภายใน 2 นาทีไม่ต้องสมัครสมาชิก
  7. NFR-R: ออเดอร์ไม่หายแม้ payment gateway ล่มชั่วคราว (มีคิวรอ)
  8. NFR-F(Security): ข้อมูลบัตร/PromptPay เข้ารหัส พนักงานไม่เห็นเลขบัตร
ข้อ 2●●○

Use case CS-Pizza: ระบุ initiating actors + 4 use cases + participating actor ที่มาจากโจทย์

แนวคำตอบ
  1. Initiating: Customer (สั่ง/จ่าย/ดูสถานะ), Staff/Manager (จัดการเมนู/ออเดอร์), DeliveryPerson (รับรายการส่ง)
  2. Use cases: PlaceOrder · TrackOrderStatus · MakePayment · ManageMenu · AssignDelivery
  3. Participating: Payment Gateway (supporting — ตรวจชำระเงินจริง), Database, (แผนที่/GPS ถ้ามีติดตาม)
ข้อ 3●●●

Schema CS-Pizza: วาด ER ของ Customer, Order, OrderItem, MenuItem, Payment — กำหนด PK/FK + ความสัมพันธ์

แนวคำตอบ
  1. Order แยก OrderItem ได้แต้ม: ออเดอร์ 1 ใบมีรายการพิซซ่าหลายรายการ (M:N แก้ด้วยตารางกลาง OrderItem)
  2. Customer 1:N Order — ลูกค้า 1 สั่งได้หลายครั้ง
  3. MenuItem 1:N OrderItem — เมนู 1 รายการโผล่หลายออเดอร์
  4. Order 1:1 Payment — ออเดอร์หนึ่งจ่ายครั้งเดียว (หรือ 1:N ถ้ายอมให้จ่ายซ้ำครั้งละบางส่วน)
  5. PK: customer_id / order_id / orderitem_id / menuitem_id / payment_id + FK ผูกทุกความสัมพันธ์
ข้อ 4●●○

จับคู่ศัพท์ข้ามบท: (1) triggering process (2) reactive process (3) risk analysis นำทุกเฟส (4) use case driven + architecture centric (5) pair programming (6) crow's foot (7) dictionary attack (8) Adding people to a late project… — ให้ชื่อศัพท์ที่หมายถึง

เฉลย
  1. (1) Client (Client/Server)
  2. (2) Server
  3. (3) Spiral Model
  4. (4) RUP (Rational Unified Process)
  5. (5) XP — Extreme Programming
  6. (6) ER Schema / สัญลักษณ์ความสัมพันธ์ "หลายตัว"
  7. (7) เดาคีย์จนเข้า — กันด้วย block หลัง N ครั้ง (NFR Security)
  8. (8) "makes it later" — Brooks / scheduling problem (บทที่ 5)
ข้อ 5●●●

รวมทุกบท: โปรเจกต์กลุ่มคุณทำแอปจองสนามกีฬา — เขียนแผน 1 หน้า: (1) โมเดลกระบวนการที่เลือก+เหตุผล (2) สถาปัตยกรรม (3) ทดสอบอย่างไร (4) maintenance plan

แนวคำตอบ (โครง)
  1. โมเดล: Scrum — ทีมเล็ก requirement เปลี่ยนตาม feedback ผู้ใช้, sprint 2 สัปดาห์, product backlog จัดโดย "ลูกค้า" (ตัวแทนผู้ใช้จริง)
  2. สถาปัตยกรรม: Client/Server + Layered (mobile app → API server 3 ชั้น → central DB) + บริการแจ้งเตือนภายนอก (supporting)
  3. ทดสอบ: unit (white-box, ขอบเวลาจองเต็ม) → integration (bottom-up) → function/quality (ตรวจ FR + ทดสอบ 200 ผู้ใช้พร้อมกัน) → acceptance โดยผู้จัดการสนาม → installation บน hosting จริง
  4. Maintenance: ticket รับคำขอ → impact analysis → release รายเดือน → implement+regression test → release+วัด 4 ตัวชี้วัด; ครอบ 4 ประเภท (แก้บั๊ก SLA / ปรับแพลตฟอร์มรายไตรมาส / backlog ฟีเจอร์ / refactoring ประจำ)
ข้อ 6●●○

จับคู่ผสม (ยกระดับ): ประโยคต่อไปนี้พูดถึงคุณภาพใด (บทที่ 3): (a) ระบบทน input เพี้ยนไม่พัง (b) ผ่าน spec ทุกข้อ (c) โอกาสทำงานตามคาดต่อเนื่อง 90 วัน (d) ทุกขั้นตอนพัฒนาถูกจดบันทึก

เฉลย
  1. (a) Robustness
  2. (b) Correctness
  3. (c) Reliability (คีย์: probability + time interval)
  4. (d) Visibility (คีย์: documented steps + current status — ทั้ง internal และ external)
ข้อ 7●●●

Verification หรือ Validation? ตัดสินแต่ละข้อ: (a) QA รัน test suite 1,200 เคสตาม spec (b) สาธิตระบบให้คณะกรรมการโรงพยาบาลแล้วรับ sign-off (c) เทียบโค้ดกับ detailed design ทีละโมดูล (d) เก็บ feedback ผู้ใช้นำร่องว่า workflow ตรงการทำงานจริงไหม

เฉลย
  1. (a) Verification — เทียบกับ spec (มุมนักพัฒนา)
  2. (b) Validation — acceptance testing โดยลูกค้า (มุมลูกค้า)
  3. (c) Verification — ตรวจ internal implementation
  4. (d) Validation — ตรวจว่า "ใช่ของที่โลกต้องการ" จริงไหม
ข้อ 8●●●

จับคู่ process model กับโจทย์รวม: (a) ธนาคารระบบคิดดอกเบี้ย requirement ตายตัวตามกฎหมาย (b) โรงพยาบาลใหญ่เปลี่ยนระบบทั้งโรง เสี่ยงสูง (c) สตาร์ทอัพ MVP ให้ผู้ใช้ทดลองก่อน (d) ร้านเล็กขอเว็บขายของ scope แคบ งานด่วน 60 วัน (e) องค์กรใหญ่ระบบ OOP มาตรฐาน UML 4 เฟส

เฉลย
  1. (a) Waterfall — requirement ชัดคงที่ ควบคุมง่าย
  2. (b) Spiral — risk analysis ทุกวง ลดโอกาสพัง
  3. (c) Prototyping หรือ Scrum/XP — ให้ผู้ใช้เห็นเร็ว feedback ซ้ำ
  4. (d) RAD — requirement ชัด + scope จำกัด + 60–90 วัน
  5. (e) RUP — use case driven, architecture centric, 4 เฟส I-E-C-T
