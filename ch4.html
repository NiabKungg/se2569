📖 บทเรียน

🗺️ ที่มาที่ไป — จากบทที่ 1 สู่ "ใบสั่งงานจริง"

บทที่ 1 บอกภาพรวมว่ามีกระบวนการพัฒนาซอฟต์แวร์ บทนี้จะแกะว่า "กระบวนการ" นั้นประกอบด้วยงานอะไรบ้าง — สไลด์วาดเป็นวงล้อ: Feasibility study เริ่มต้น → Requirements → ออกแบบ 3 ระดับ → เขียนโค้ด → รวมระบบ → ตรวจสอบ → ใช้งาน → บำรุงรักษา โดยมี 3 งานครอบทั้งวง: Project Management, Documentation, Validation

อุปมา: เหมือนสร้างบ้าน — สำรวจดินว่าคุ้มสร้างไหม (Feasibility) → ถามเจ้าของบ้านว่าต้องการห้องอะไร (Requirements) → วาดแบบทั้งบ้าน (Architectural) และแบบห้องเล็ก ๆ (Detailed) → ก่ออิทีละห้อง (Coding) → ต่อท่อน้ำไฟทั้งบ้าน (Integration) → ตรวจว่าสร้างตามแบบไหม (Verification) → เจ้าของบ้านลองอยู่จริงแล้วยอมรับไหม (Validation/Acceptance) → อยู่จริง (Production) → ซ่อมเปลี่ยนตลอดชีวิตบ้าน (Maintenance)

1) ภาพรวม 13 งาน

2) แกะทีละงาน — พร้อมผลผลิต (product) ของแต่ละงาน

งานทำอะไร (ภาษาคน)ผลผลิต (Product)
1. Feasibility studyตัดสินว่าโปรเจกต์ควรทำต่อไหม — ระบบอาจไม่จำเป็น แพงเกิน หรือเสี่ยงเกิน · วิธีหนึ่งคือ cost-benefit analysis: ประมาณต้นทุนระบบใหม่ (รวม HW ใหม่ด้วย) เทียบกับเงินที่จะประหยัดได้การตัดสินใจทำ/ไม่ทำ + ตัวเลขต้นทุน-ผลประโยชน์
2. Requirements engineering
(specification)		ช่วงเริ่มโปรเจกต์ นักพัฒนาหาว่าผู้ใช้ (client/customer) ต้องการให้ซอฟต์แวร์ทำอะไร แล้วบันทึกให้ชัดที่สุดRequirements specification
3. User interface designซอฟต์แวร์ส่วนใหญ่มี GUI ต้องออกแบบอย่างระวังให้ใช้ง่ายการออกแบบหน้าจอ/UI
4. Architectural design
(large-scale)		ระบบใหญ่จนเขียนเป็นโปรแกรมเดียวไม่ไหว — ต้องสร้างจากโมดูล/คอมโพเนนต์ · งานนี้ "หั่น" ระบบทั้งหมดเป็นโมดูลง่าย ๆ หลายชิ้นArchitectural design + module specifications
5. Detailed designออกแบบรายละเอียดของแต่ละโมดูลจริงจังDetailed design ของทุกโมดูล
6. Programming (coding)แปลง detailed design เป็นคำสั่งภาษาโปรแกรม — อาจมีให้เลือกหลายภาษา ต้องเลือกหนึ่งCode
7. System integrationเอาคอมโพเนนต์ย่อยที่ทำเสร็จแล้วมารวมกัน (เรียกอีกอย่างว่า "the build")ระบบที่สมบูรณ์ (complete system)
8. Verificationดูหัวข้อ 3 ด้านล่าง — ตรวจว่าสร้างสินค้าถูกวิธีหรือไม่Test results ที่ยืนยันระบบตรง spec
9. Validationดูหัวข้อ 3 ด้านล่าง — ตรวจว่าสร้างสินค้าที่ถูกหรือไม่เอกสาร sign-off / รายการ fault
10. Productionนำระบบไปใช้งานจริง (บางตำราเรียกสับสนว่า implementation) — ผู้ใช้อาจต้องได้รับการอบรมระบบที่ใช้งานจริง + ผู้ใช้ที่ผ่านอบรม
11. Maintenanceพอใช้ไปแล้ว ซอฟต์แวร์แทบแน่นอนว่าจะต้องแก้หรือเพิ่มความสามารถ — มักยาวไปอีกหลายปีหลังสร้างครั้งแรกModified software (ซอฟต์แวร์ที่ถูกแก้แล้ว)
12. Documentationเอกสารสำหรับ 2 กลุ่ม — ผู้ใช้: วิธีติดตั้ง/ติดตั้งใหม่/ใช้งาน (กระดาษยังต้องการ, help system สำหรับซอฟต์แวร์ general) เน้น "what" มุมนอก ไม่ใช่ "how" · นักพัฒนา: spec, architectural design, detailed design, code, comments, test schedules, test results, project plan — เพื่อพัฒนาต่อและ maintainเอกสารคู่มือผู้ใช้ + เอกสารชุดนักพัฒนา
13. Project managementใครบางคนต้องสร้างและดูแลแผน แก้ปัญหา มอบงานให้คน และตรวจว่าทำเสร็จหรือยังแผนโครงการ + การควบคุมความคืบหน้า

3) Verification vs Validation — 🎯 คู่คำที่ออกสอบสม่ำเสมอ

🎯 จำสองประโยคของ Barry Boehm ให้ขึ้นใจ (ข้อสอบชอบเติมคำ)

Verification ตอบคำถาม: "Are we building the product right?" — เรากำลังสร้างสินค้าถูกวิธีอยู่หรือเปล่า (ถูกตาม spec)

Validation ตอบคำถาม: "Are we building the right product?" — เรากำลังสร้างสินค้าที่ถูกอยู่หรือเปล่า (ตรงกับความต้องการผู้ใช้จริง)

สังเกตตำแหน่งคำ "right": ซ้ายสลับ — product right (สร้างถูกวิธี) = Verification · right product (สินค้าที่ใช่) = Validation

📐 เจาะลึก Verification — 2 ประเภท

Unit testing: ทดสอบแต่ละโมดูลแบบโดดเดี่ยว (in isolation) — inputs 3 อย่าง: (1) unit specification (2) unit code (3) รายการผลทดสอบที่คาดหวัง · products = test results · ยืนยันว่าพฤติกรรมของโค้ดตรงกับ unit specification

System testing (integration testing): เชื่อมโมดูลเข้าด้วยกันแล้วทดสอบทั้งระบบ — inputs: system specification + โค้ดระบบทั้งหมด · ผลลัพธ์ = ซอฟต์แวร์สมบูรณ์ที่ผ่านการทดสอบ ยืนยันว่าระบบตรง spec

📐 เจาะลึก Validation — Acceptance testing

Acceptance testing เกิดท้ายโปรเจกต์ เมื่อระบบถือว่าเสร็จ — สาธิต (demonstrate) ให้ลูกค้าดู แล้วลูกค้ารับรองว่าน่าพอใจ

inputs: ลูกค้า + ซอฟต์แวร์ที่ดูเหมือนเสร็จสมบูรณ์ · products: เอกสาร sign-off + ระบบที่รับรองแล้ว หรือ รายการ fault ที่ต้องแก้ · ผลลัพธ์: ระบบ "ตรงกับ requirement ของลูกค้า" หรือ "ไม่ตรง"

บริบทรีวิวข้อสอบ: โจทย์มิดเทอมเคยให้เติม "สามารถแก้ไขซอฟต์แวร์ได้แบบ static ______" — จำสั้น ๆ: แก้ไข static (เอกสาร/review โดยไม่รันระบบ) จะช่วยเรื่อง Validation ฝั่งมองงานให้ครบ; แก้ dynamic (รันระบบจริง) ฝั่ง Verification — ถ้าข้อสอบให้เลือก validation/verification ให้อ่านประโยค: พูดถึงผู้ใช้/ความต้องการ → Validation, พูดถึง spec/โค้ด/internal → Verification

🎯 แนวข้อสอบของบทนี้

🎯 ออกจริงจากรีวิวรุ่นพี่ + เติมคำคลาสสิก
  • เติมคำ Verification/Validation: "Are we building the product right?" → Verification · "Are we building the right product?" → Validation · หรือให้ประโยคมาให้เลือกคำ
  • เขียนตอบเชื่อมข้อใหญ่: ข้อ Final "จะทดสอบระบบอย่างไร" — โครงคำตอบ: Verification (unit → system testing) ตามด้วย Validation (acceptance testing กับลูกค้า) → ดูเฉลยเต็มที่หน้า ติว Final
  • จับคู่งานกับผลผลิต: เช่น Architectural design → architectural design + module specifications · Requirements → requirements specification · Integration → complete system
  • Documentation: ผู้ใช้ได้อะไร (คู่มือ what) / นักพัฒนาได้อะไร (spec, design, code, test results — how)

🏋️ โจทย์ซ้อมมือ (6 ข้อ)

ข้อ 1●○○

เติมคำ (แนวข้อสอบ): (1) "Are we building the product ______?" — Verification (2) "Are we building the ______ product?" — Validation เติมคำที่หายและบอกว่าใครเป็นคน "ตัดสิน"

เฉลย
  1. (1) เติม "right" → สร้างสินค้าถูกวิธีหรือไม่ — ตัดสินโดยมุมมองนักพัฒนา (เทียบกับ spec/internal)
  2. (2) เติม "right" → สร้างสินค้าที่ถูกหรือไม่ — ตัดสินโดยมุมมองลูกค้า/ผู้ใช้ (external)
  3. ทริคจำ: ตำแหน่งคำ right สลับกัน — product right = Verification (ถูกวิธี), right product = Valitation... ให้จำแบบนี้: Verification = ตรง spec ไหม / Validation = ตรงใจไหม
ข้อ 2●○○

จำแนกสถานการณ์: (a) QA ทีมวิ่ง JUnit ทดสอบฟังก์ชันคำนวณค่าส่งทีละโมดูลแบบโดดเดี่ยว (b) สาธิตระบบทั้งหมดให้เจ้าของร้านดู แล้วเจ้าของร้านลงนามรับมอบ (c) เชื่อมโมดูลสั่งซื้อ+ครัว+จัดส่งแล้วทดสอบ flow สมบูรณ์

เฉลย
  1. (a) Verification — Unit testing (โมดูลเดี่ยว in isolation, inputs: unit spec + code + expected results)
  2. (b) Validation — Acceptance testing (ท้ายโปรเจกต์, demonstrate ให้ลูกค้า, ผลลัพธ์คือ sign-off หรือรายการ fault)
  3. (c) Verification — System/Integration testing (โมดูลต่อกันแล้วทดสอบทั้งระบบเทียบ system specification)
ข้อ 3●●○

เรียงงาน: เรียงลำดับงานต่อไปนี้: System integration / Feasibility study / Detailed design / Maintenance / Requirements engineering / Programming / Architectural design / Production / Verification

เฉลย
  1. 1. Feasibility study — คุ้มทำไหมก่อนเริ่ม
  2. 2. Requirements engineering — ผู้ใช้ต้องการอะไร → requirements specification
  3. 3. Architectural design — หั่นระบบเป็นโมดูล
  4. 4. Detailed design — ออกแบบรายโมดูล
  5. 5. Programming — โค้ด
  6. 6. System integration — รวมโมดูล → complete system
  7. 7. Verification — ทดสอบว่าตรง spec
  8. 8. Production — ใช้งานจริง + อบรม
  9. 9. Maintenance — แก้/เพิ่มต่อหลายปี
ข้อ 4●●○

ตาราง: Unit testing มี inputs อะไร 3 อย่าง และ system testing มี inputs อะไรบ้าง ต่างกันตรงไหน?

เฉลย
  1. Unit testing inputs: (1) unit specification (2) unit code (3) list of expected test results — products: test results
  2. System testing inputs: system specification + code ของระบบสมบูรณ์
  3. ต่างกัน: unit = ระดับโมดูลเดียวโดดเดี่ยว / system = ระดับระบบหลังต่อโมดูลแล้ว — ทั้งคู่เป็น Verification 2 ประเภท
ข้อ 5●●●

เทียบเอกสาร: Documentation สำหรับผู้ใช้กับสำหรับนักพัฒนา มีเนื้อหาอะไรบ้าง และต่างกันในเรื่อง "what vs how" อย่างไร

เฉลย
  1. เอกสารผู้ใช้: วิธีติดตั้ง ติดตั้งใหม่ ใช้งาน — กระดาษยังต้องการ ซอฟต์แวร์ general มักมี help system — เน้น "what" (มุมนอก/external view) ไม่ใช่ "how" (กลไกข้างใน)
  2. เอกสารนักพัฒนา: specification, architectural design, detailed design, code, comments ในโค้ด, test schedules, test results, project plan — เพื่อพัฒนาต่อและทำ maintenance
  3. สรุปหนึ่งบรรทัด: ผู้ใช้เอา "what" (ใช้ยังไง) นักพัฒนาเอา "how" (ข้างในทำงานยังไง)
ข้อ 6●●●

วิเคราะห์เคส (โยงข้อสอบ Final): ทีม A สร้างแอปสั่งอาหาร ทดสอบทุกโมดูลผ่านหมด (ตรง spec 100%) แต่พอส่งมอบ ลูกค้าบอกว่า "ผมอยากได้ปุ่มเรียกพนักงาน ไม่ใช่แชตบอท" — ทีม A ตกตรงไหน ใช้คำว่า Verification หรือ Validation อธิบาย

เฉลย
  1. ผ่าน Verification: โค้ดตรง spec ทุกข้อ (building the product right ผ่าน) — ระบบทดสอบสมบูรณ์ ไม่พัง
  2. ตก Validation: สิ่งที่สร้างไม่ใช่ "right product" ของลูกค้า — spec เองแพ้ทางความต้องการจริงของผู้ใช้
  3. บทเรียน: Validation ไม่ใช่ทำตอนท้ายอย่างเดียว — ต้อง validate ความเข้าใจ requirement ตั้งแต่ต้น (acceptance test เขียนไว้ตั้งแต่ตอนเขียน requirement — เชื่อมบทที่ 6) ไม่งั้น "ทดสอบสมบูรณ์แต่ไม่ใช่ของที่ต้องการ"
