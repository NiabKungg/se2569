บทที่ 1 — Introduction to Software Engineering

ทำไมโลกต้องมี "วิศวกรรมซอฟต์แวร์"? เราจะเริ่มจากวิกฤตซอฟต์แวร์ (Software Crisis) ที่บีบให้เกิดสาขานี้ แล้วรู้จักประเภทซอฟต์แวร์ทั้ง 8 แบบ (หัวข้อจับคู่ข้อสอบ!), มุมมองของ SE และวงจรชีวิตซอฟต์แวร์ (SDLC)

🎯 จุดประสงค์ 📖 บทเรียน 🎯 แนวข้อสอบ 🏋️ โจทย์ซ้อมมือ

🎯 เรียนจบบทนี้ คุณต้องทำสิ่งเหล่านี้ได้

  • เล่าที่มาของ SE ได้: 1968 การประชุม NATO ตั้งคำว่า "Software Engineering" เพื่อแก้ Software Crisis
  • จำ 8 Laws of Software Evolution (ทฤษฎีการวิวัฒนาการของซอฟต์แวร์) คร่าว ๆ แล้วอธิบายได้ว่าแต่ละกฎหมายพูดถึงอะไร
  • จำแนกประเภทซอฟต์แวร์ทั้ง 8 แบบ จากชื่อโปรแกรมที่โจทย์ให้มา (แนวจับคู่ข้อสอบเป๊ะ ๆ)
  • อธิบาย SE View ได้: Methodology / Technique / Environment + Project Management + Software Development
  • เรียงลำดับ SDLC ได้ และบอกกิจกรรมหลัก 4 อย่างของ Software Process ได้ (Specification → Development → Validation → Evolution)
  • บอกสัดส่วนต้นทุนได้: พัฒนา 60% ทดสอบ 40% และทำไมแก้ bug ยิ่งช้ายิ่งแพง

📖 บทเรียน

🗺️ ที่มาที่ไป — ทำไมต้องมีวิชานี้ (อ่านเป็นเรื่องเล่าก่อน)

ลองนึกภาพว่า "สร้างแอปบันทึกรายรับรายจ่ายส่วนตัว" กับ "สร้างระบบโอนเงินของธนาคารทั้งประเทศ" — งานสองแบบนี้ต่างกันคนละเรื่องเลย งานแรกคนเดียวนั่งเขียนคืนเดียวจบ แก้ผิดก็แก้เลยไม่กระทบใคร แต่งานที่สองต้องมีทีมหลายสิบคน โค้ดหลายล้านบรรทัด ผิดแค่บรรทัดเดียวเงินหายเป็นล้าน และต้องใช้งานจริงทุกวัน 20 ปี ต้องซ่อม ต้องเพิ่มฟีเจอร์ตลอดเวลา

ปัญหาคือ: ในยุคทศวรรษ 1960 โลกพยายามสร้างซอฟต์แวร์ใหญ่ ๆ แบบที่สองด้วยวิธีเดียวกับงานแรก — คนเก่งเขียนเอง ไม่มีแผน ไม่มีวินัย — ผลคือโครงการล้มเป็นแถบ งบบานปลาย ส่งไม่ทัน เรียกวิกฤตนี้ว่า Software Crisis (วิกฤตซอฟต์แวร์)

ทางแก้: ปี 1968 ที่ประชุม NATO จึงเสนอคำว่า "Software Engineering" — ยืมวิธีคิดแบบ "วิศวกรรม" (ที่คนสร้างสะพาน/เครื่องบินใช้อยู่) มาใช้สร้างซอฟต์แวร์ คือมีแผน มีหลักการ มีการทดสอบ มีการจัดการทีม อย่างเป็นระบบ ต่อมาปี 1975 คำนี้ถูกนิยามอย่างชัดเจนในการประชุม ICSE (International Conference on Software Engineering)

อุปมาที่ควรจำ: Software Engineering = สถาปนิก-วิศวกรที่ออกแบบบ้านใหญ่ ไม่ใช่ช่างไม้ที่เต๊าะแต๊ะตามใจ ส่วน Programming คืองานของช่างตีไม้ตามแบบที่วิศวกรเขียนไว้ — สไลด์อาจารย์สรุปว่า "SE คือศิลปะการเข้าใจปัญหาธุรกิจ คิดวิธีแก้ และออกแบบ blueprint ของคำตอบ ส่วนการเขียนโปรแกรมคืองานฝีมือที่ implement blueprint นั้น"

📖 ศัพท์พื้นฐานที่สอนใช้ทั้งเทอม (Notations)

SE = Software Engineering (วิชานี้) · SEng = Software Engineer (คนทำงาน) · SW = Software · HW = Hardware · SP = Software Project

Hardware = เครื่องคอมพิวเตอร์/อุปกรณ์อิเล็กทรอนิกส์ที่ มองเห็นและจับต้องได้

Software = โปรแกรมทุกชนิดที่ติดตั้งลงบน Hardware เพื่อให้มัน "ทำงาน" ได้ — ซอฟต์แวร์อาจสร้างเพื่อลูกค้าเฉพาะราย (Custom) หรือสร้างขายตลาดหลวง (Generic เช่น MS-Office)

Engineering = การนำหลักวิทยาศาสตร์และวิธีการทางวิทยาศาสตร์ มาใช้สร้างสิ่งที่เป็นประโยชน์ (โครงสร้าง, เครื่องจักร) เช่น วิศวกรรมโยธา วิศวกรรมไฟฟ้า — ซอฟต์แวร์ก็เป็นสาขาวิศวกรรมหนึ่ง

นิยาม SE แบบที่อาจออกเติมคำ: "Software Engineering is a computer science's field deals with the building of so large or so complex software systems by teams of engineers" — จุดสำคัญคือ 2 คำ: ใหญ่/ซับซ้อน และ ทำงานเป็นทีม

1) Software Crisis — วิกฤตซอฟต์แวร์เปลี่ยนหน้าไปตามยุค

📐 4 ยุคของวิกฤต — ทีละยุคมีปัญหาคนละแบบ

วิกฤตซอฟต์แวร์ไม่ได้จบในปี 1968 ไปเลย — มันเปลี่ยนหน้าตาไปตามเทคโนโลยี สไลด์อาจารย์แบ่งเป็น 4 ยุค:

  • 1970 — ปัญหาเรื่อง Size: อยากสร้างซอฟต์แวร์ขนาดใหญ่ แต่ไม่รู้วิธีพัฒนา "โปรแกรมใหญ่" — แก้ด้วยการหาวิธีพัฒนาซอฟต์แวร์ขนาดใหญ่
  • 1980 — ปัญหาเรื่อง Quantity: ต้องการคนทำงาน IT จำนวนมากแต่คนไม่พอ (Backlog งานค้างเยอะ ผู้เชี่ยวชาญด้าน Information Processing ไม่มี)
  • 1990 — ปัญหาเรื่อง Quality: ซอฟต์แวร์ใหญ่แล้วแต่ใช้งานยาก แก้ด้วยการออกแบบ User Interface ให้ใช้ง่าย
  • 1990 (ต่อ) — ปัญหาเรื่อง Interface: โปรแกรมและข้อมูลของแต่ละระบบคุยกันไม่ได้ — ต้องทำให้โปรแกรมต่าง ๆ ทำงานร่วมกันได้ (interoperability)

2) 8 Laws of Software Evolution — ทฤษฎีการวิวัฒนาการของซอฟต์แวร์

💡 อุปมาก่อนจำ — ซอฟต์แวร์เหมือนสิ่งมีชีวิต ไม่ใช่ของชิ้นเดียวจบ

ซอฟต์แวร์ที่ใช้งานจริงไม่เคย "เสร็จสมบูรณ์" จริง ๆ — เหมือนรถที่ซื้อมาแล้วต้องเปลี่ยนยาง ถ่ายน้ำมัน เพิ่มอุปกรณ์ เพราะโลกเปลี่ยน ผู้ใช้เปลี่ยน กฎหมายเปลี่ยน เลฮ์แมน (Lehman) เสนอกฎหมาย 8 ข้ออธิบายพฤติกรรมนี้ — ไม่ต้องท่องคำแปลเป๊ะ ให้จำแนวคิดว่าข้อไหนพูดถึงอะไร (เพราะข้อสอบมักจับคู่ชื่อกับคำอธิบาย)

กฎ (Law)ปีพูดถึงอะไร (คำอธิบายแบบคนไทยอ่านรู้เรื่อง)
Law of Continuing Change1974ซอฟต์แวร์ต้องเปลี่ยน/วิวัฒนาการต่อเนื่องตลอดเวลา ไม่งั้นจะใช้ไม่ได้และแพงขึ้นเรื่อย ๆ — เหมือนมือถือที่ต้องอัปเดต OS ไม่งั้นแอปใหม่ ๆ ใช้ไม่ได้
Law of Increasing Complexity1974ถ้าเพิ่มฟีเจอร์โดยไม่บริหาร ความซับซ้อนจะเพิ่มขึ้นเรื่อย ๆ — ต้อง "คุม" การเพิ่มของความซับซ้อน (งานช่างเติมห้องบ้านใหม่ไม่วางแผน สายไฟน้ำประปาจะเละ)
Law of Self-regulation1974กระบวนการพัฒนาซอฟต์แวร์มีลักษณะ self-regulating — ปรับตัวตามสภาพแวดล้อมแบบการแจกแจงปกติ (normal distribution)
Law of Conservation of Organizational Stability1980องค์กรที่พัฒนามักคงสถานะเดิม — วงจรชีวิตผลิตภัณฑ์ควรคงเสถียรภาพ
Law of Conservation of Familiarity1980การเปลี่ยนแปลงต้องคงความคุ้นเคยของผู้ใช้ — ซอฟต์แวร์โตได้ปกติ แต่อย่าเปลี่ยนจนคนใช้งง (จำ: ต้องให้ผู้ใช้ "คุ้น" กับ SW ที่ทำงานด้วย การเติบโตควรเป็นแบบปกติ)
Law of Continuing Growth1980ฟังก์ชัน/รายละเอียดของซอฟต์แวร์ต้องเพิ่มขึ้นเรื่อย ๆ อย่างค่อยเป็นค่อยไป เพื่อรักษาความพึงพอใจของผู้ใช้
Law of Declining Quality1996คุณภาพจะ "ลดลง" ถ้าไม่ดูแลรักษาดี — คุณภาพจะไม่ลด ก็ต่อเมื่อบำรุงรักษาอย่างดีตามสภาพแวดล้อมและมี Feedback System (หมายเหตุ: ข้อความในสไลด์เขียนไว้ทั้งสองมุม ให้จำว่ากฎนี้เกี่ยวกับคุณภาพกับการบำรุงรักษา)
Feedback System Law1996การวิวัฒนาการเป็นระบบหลายลูป/หลายระดับ — feedback loop นำไปสู่การปรับปรุงที่ดีขึ้น (เหมือนทำข้อสอบเก่าแล้วเก็บ feedback ไปแก้ทุกรอบ)

3) ประเภทซอฟต์แวร์ 8 แบบ — 🎯 หัวข้อจับคู่ข้อสอบที่ชัดที่สุดของบทนี้

🎯 ออกสอบแน่ — โจทย์จะตั้งชื่อโปรแกรมมาให้จับว่าเป็นประเภทไหน (บางชื่อไม่เคยได้ยินมาก่อน!)

ทริคคือ อย่าจำชื่อโปรแกรม — จำ "คุณสมบัติเด่น" ของแต่ละประเภทแทน เพราะโจทย์จะเอาโปรแกรมที่ไม่รู้จักมา แต่คำอธิบายจะเผยว่ามันทำอะไร ลองฝึกจากตารางนี้:

ประเภทเด่นที่อะไร (คีย์เวิร์ด)ตัวอย่างโปรแกรม
1. System Software"เขียนไว้บริการโปรแกรมอื่น" — ใช้หนัก ผู้ใช้หลายคน มี scheduling, resource sharing, process managementOperating System (Windows, Linux), device driver, compiler, editor, file management
2. Application Software"แก้ปัญหาเฉพาะเรื่อง/ระบบธุรกิจ" — มี 3 ส่วน: Data gathering → Analysis → Control/Outputระบบบัญชีร้านค้า, ระบบจัดการผู้ป่วย (CS-Hospital!), โปรแกรมพยากรณ์อากาศ
3. Engineering & Scientific SW"number crunching" = คำนวณเลขหนัก ๆ ด้วยอัลกอริทึม — จำโดยคำว่า astronomy/volcanology, CAD, simulation, real-timeโปรแกรมจำลองการระเบิดภูเขาไฟ, ซอฟต์แวร์ดาราศาสตร์, AutoCAD, MATLAB
4. Embedded Software"ฝังในสินค้าอุตสาหกรรม ทำได้เฉพาะฟังก์ชันที่จำกัด" — อยู่ในเครื่องใช้ ไม่ใช่เครื่องคอมทั่วไปแผงปุ่มไมโครเวฟ, ระบบควบคุมน้ำมัน/เครื่องยนต์ในรถยนต์, ระบบในเครื่องซักผ้า
5. Product-line Software"ขายตลาดหลวง/mass market" — ใช้ได้ทุกคน ไม่ได้ทำให้ลูกค้ารายเดียวWord Processor (Word), Spreadsheet (Excel), โปรแกรมบัญชีการเงิน, Database system สำเร็จรูป
6. Web-based Software"WebApps" — หน้าเว็บ + คำสั่งที่รันได้ เช่น HTML, CGI, Java (ใช้ผ่าน browser)เว็บธนาคาร, Gmail, Shopee web, ระบบลงทะเบียนออนไลน์
7. AI Software"ใช้อัลกอริทึมไม่ใช่เชิงตัวเลข (non-numerical) แก้ปัญหาซับซ้อน" — จำคำว่า expert system, knowledge-based, neural network, pattern recognitionระบบแนะนำวินิจฉัยโรค, จำแนกใบหน้า/เสียงพูด, แชตบอท
8. Mobile Application"ทำเฉพาะอุปกรณ์ไร้สายขนาดเล็ก (สมาร์ตโฟน/แท็บเล็ต)" — แบ่ง 3 ชนิด: web-based / native / hybridLINE, Grab, TikTok, แอปธนาคารบนมือถือ
💡 ทริคจับคู่แบบไม่สะดุด

เจอโจทย์ตั้งชื่อแปลก ๆ ให้ถามตัวเอง 4 คำถาม: (1) มันบริการโปรแกรมอื่นหรือเปล่า? → System · (2) มันฝังอยู่ในเครื่องใช้/รถยนต์? → Embedded · (3) มันคำนวณเลขหนัก/จำลองระบบ? → Engineering & Scientific · (4) มันเรียนรู้/จำแนกรูปแบบ? → AI — ถ้าไม่เข้า 4 ข้อนี้ ก็ดูว่าขายตลาดหลวง (Product-line), ใช้ผ่านเว็บ (Web-based), ใช้บนมือถือ (Mobile) หรือทำงานธุรกิจเฉพาะเรื่อง (Application)

4) SE View — มองวิชานี้ผ่านแผนที่ใหญ่ 5 ส่วน

สไลด์วาดแผนที่ใหญ่ให้เห็นว่า "การทำ SE" ประกอบด้วยอะไรบ้าง — ตรงกลางคืองานพัฒนาซอฟต์แวร์ ล้อมรอบด้วยการจัดการโครงการ และเสาหลัก 3 ต้น:

5) SDLC — วงจรชีวิตซอฟต์แวร์ (Software Life Cycle)

📐 นิยามสั้น ๆ

Software Process = กิจกรรมทั้งหมดที่ใช้ "สร้างหรือวิวัฒนาการ" ซอฟต์แวร์ เป้าหมายคือผลิตซอฟต์แวร์ที่มี high quality, reliable, predictable, efficient

Software Life Cycle (Software Model) = โมเดลที่จับกิจกรรมเหล่านั้นมาเรียงเป็นวงจร — มีหลายแบบ: Waterfall, Spiral, Prototyping, Incremental Distribution, Evolutionary Distribution (บทที่ 8 จะลงลึกทีละแบบ)

กิจกรรมหลัก 4 อย่าง (Software Process Activities) — จำสั้น ๆ ว่า "S-D-V-E":

  • 01 Specification — ระบบต้องทำอะไรให้ตรงกับความต้องการ (กำหนดข้อกำหนด)
  • 02 Development — ผลิตระบบซอฟต์แวร์จริง
  • 03 Validation — ตรวจว่าซอฟต์แวร์ตรงกับความต้องการของผู้ใช้หรือไม่
  • 04 Evolution — เปลี่ยนซอฟต์แวร์ตามความต้องการที่เปลี่ยนไป

6) ต้นทุนของซอฟต์แวร์ — เงินไปไหนบ้าง

⚡ ตัวเลขที่อาจออกเติมคำ

ต้นทุนซอฟต์แวร์ = พัฒนา (Developing) 60% + ทดสอบ (Testing) 40% — และต้นทุนแปรผันตาม (1) ประเภทระบบที่จะพัฒนา (2) ความต้องการของระบบ (3) โมเดลที่ใช้พัฒนา

เกร็ดที่อาจารย์ย้ำในบทถัด ๆ: กราฟต้นทุนแก้ fault จะยิ่งแพงมากขึ้นเรื่อย ๆ ตามระยะ — แก้ตอน Requirements ถูกที่สุด แก้ตอน Maintenance แพงที่สุด (จำภาพบันไดเลื่อนขึ้น) — เพราะยิ่งพบช้า bug ยิ่งแพร่กระจายไปทั่ว design/code/เอกสาร และอาจถึงมือผู้ใช้แล้ว

🏋️ โจทย์ซ้อมมือ (6 ข้อ)

ลองทำเองก่อน แล้วค่อยกดเปิดคำใบ้ → เฉลยทีละขั้น เมื่อทำได้แล้วติ๊ก ✓ เพื่อบันทึกความคืบหน้า

ข้อ 1●○○

จับคู่ (แนวข้อสอบจริง): โปรแกรมต่อไปนี้เป็นซอฟต์แวร์ประเภทใด? (a) ระบบควบคุมฉีดน้ำมันเข้าเครื่องยนต์รถยนต์ (b) MATLAB โปรแกรมจำลองการทดลองฟิสิกส์ (c) โปรแกรมจำแนกว่าภาพนี้มีแมวหรือหมา (d) Microsoft Excel

คำใบ้ + เฉลย

ใช้ทริค 4 คำถาม: ฝังในเครื่องใช้/รถ? คำนวณเลขหนัก/จำลอง? เรียนรู้/จำแนกรูปแบบ? ขายตลาดหลวง?

  1. (a) "ควบคุมน้ำมันเข้าเครื่องยนต์" = ฝังในสินค้า ทำเฉพาะฟังก์ชันที่จำกัด → Embedded Software (สไลด์ใช้ตัวอย่าง "fuel control" พอดี)
  2. (b) "จำลองการทดลอง/คำนวณเลขหนัก (number crunching)" → Engineering & Scientific Software
  3. (c) "จำแนกรูปภาพ (pattern recognition)" ด้วยอัลกอริทึม non-numerical → AI Software
  4. (d) ขายตลาดหลวงให้ทุกคนใช้ ไม่ได้ทำให้ลูกค้ารายเดียว → Product-line Software
ข้อ 2●○○

จับคู่: จับศัพท์ต่อไปนี้เข้าคู่กับนิยาม: (1) Methodology (2) Technique (3) Environment (4) Tool — ตัวเลือก: (ก) CASE Tool, Programming Language (ข) Waterfall Model, Spiral Model (ค) PC, OS, Internet, Client-Server (ง) สิ่งที่พัฒนามาสนับสนุนการใช้ techniques/methods/methodologies

เฉลย
  1. (1)→(ข) Methodology = วิธี/โมเดลการพัฒนาซอฟต์แวร์ เช่น Waterfall, Spiral, Structured, OO Model
  2. (2)→(ก) Technique = เทคนิค Planning และ Design/Development เช่น OOP, Algorithm, Programming Language, CASE Tool
  3. (3)→(ค) Environment = เครื่องมือสิ่งแวดล้อมการพัฒนา เช่น PC, OS, Internet, Client-Servers
  4. (4)→(ง) Tool = ถูกพัฒนาขึ้นเพื่อสนับสนุนการใช้ technique/method/methodology (เขียนสไลด์: "Tool is developed to support the application of techniques, methods, and methodologies")
ข้อ 3●●○

เรียงลำดับ: เรียง 5 ขั้นของ Waterfall ให้ถูกต้อง: Integration & System Testing / Delivery & Maintenance / Requirements Analysis and Specification / Coding and Module Testing / Design and Specification

เฉลย
  1. ขั้น 1 Requirements Analysis and Specification — หาว่าผู้ใช้ต้องการอะไร
  2. ขั้น 2 Design and Specification — ออกแบบระบบที่ตอบสนองความต้องการ
  3. ขั้น 3 Coding and Module Testing — เขียนโค้ดและทดสอบรายโมดูล
  4. ขั้น 4 Integration and System Testing — รวมโมดูลและทดสอบทั้งระบบ
  5. ขั้น 5 Delivery and Maintenance — ส่งมอบและบำรุงรักษา
ข้อ 4●●○

อธิบายสั้น: Software Process Activities มี 4 กิจกรรมอะไรบ้าง และกิจกรรมไหนที่เกิด "หลังส่งมอบระบบไปแล้ว"?

เฉลย
  1. Specification — กำหนดว่าระบบต้องทำอะไรเพื่อตอบสนองความต้องการ
  2. Development — ผลิตระบบซอฟต์แวร์
  3. Validation — ตรวจว่าซอฟต์แวร์ตรงกับความต้องการผู้ใช้
  4. Evolution — เปลี่ยนซอฟต์แวร์ตามความต้องการที่เปลี่ยนไป ← กิจกรรมนี้คือสิ่งที่เกิดหลังส่งมอบ (และจะกลายเป็น "Maintenance" ในบทที่ 11)
ข้อ 5●●●

ต่อยอด: "ปีนี้บริษัทต้องเก็บคนทำงาน IT เพิ่ม 50 อัตรา แต่หาคนไม่ได้เลย งานกองไว้เยอะ" — สถานการณ์นี้ตรงกับ Software Crisis ยุคใด และปัญหาเรียกว่าอะไร?

เฉลย
  1. มองคีย์เวิร์ด "หาคนไม่ได้ + งานกอง" = ปัญหาจำนวนคน ไม่ใช่ปัญหาขนาดโปรแกรมหรือคุณภาพ
  2. จับยุค 1980 — ปัญหาเรื่อง Quantity เพราะเกิด Backlog (งานค้างสะสม) และขาดผู้เชี่ยวชาญด้าน Information Processing
  3. ต่างจากยุคอื่น: 1970 = Size (โปรแกรมใหญ่เกินวิธีเดิม) · 1990 = Quality (UI ใช้ยาก) · 1990-E = Interface (ระบบคุยกันไม่ได้)
ข้อ 6●●●

วิเคราะห์: เพื่อนบอกว่า "เขียนโปรแกรมเก็บข้อมูลการฝึกซ้อมส่วนตัว เขียนเองใช้เอง ไม่ต้องใช้ Software Engineering หรอก" — เพื่อนพูดถูกหรือไม่ เพราะอะไร (ใช้นิยาม SE)

เฉลย
  1. นิยาม SE ทำงานกับซอฟต์แวร์ที่ "so large or so complex" และ "by teams of engineers"
  2. นำมาวิเคราะห์ โปรแกรมของเพื่อน: เล็ก (ไม่ใหญ่) ซับซ้อนต่ำ (ไม่ซับซ้อน) ทำคนเดียว (ไม่ใช่ทีม) → จริง ๆ ไม่ต้องใช้ SE เต็มรูป
  3. แต่ ถ้าวันหนึ่งขยายเป็นแอปขายให้คนอื่นใช้ มีทีม มีผู้ใช้จำนวนมาก ต้องบำรุงรักษายาว ๆ — นั่นแหละคือเมื่อ SE เข้ามาจำเป็น (และระลึกถึง Software Crisis: โปรเจกต์ใหญ่ที่ไม่มีวินัยจะล้ม)
