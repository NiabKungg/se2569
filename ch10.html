บทที่ 10 — Software Testing

หัวข้อจับคู่ข้อสอบที่รุ่นพี่ยืนยันว่าออกชัวร์: ประเภทการทดสอบ 7 ระดับ Unit → Integration → Function → Quality → System → Acceptance → Installation บวก Black-box/White-box และเทคนิค Equivalence, Boundary, Control-flow, State-based

🎯 จุดประสงค์ 📚 7 ระดับการทดสอบ 🧪 เทคนิคออกแบบเทส 🎯 แนวข้อสอบ 🏋️ โจทย์ซ้อมมือ

🎯 เรียนจบบทนี้ คุณต้องทำสิ่งเหล่านี้ได้

  • จำคำพูด Dijkstra: "Testing shows the presence, not the absence of bugs" — ทดสอบพบว่ามี bug ไม่ใช่ว่าไม่มี bug
  • แยก fault/defect/bug (สิ่งผิดพลาดในระบบ) และนิยาม test case / test
  • เรียงและจับคู่ 7 ระดับการทดสอบ กับคำอธิบาย+ใครทำ — แนวจับคู่ข้อสอบตรง ๆ
  • แยก Black-box (ดูจาก spec, ฝั่งลูกค้า) กับ White-box (ดูโค้ด, ฝั่งนักพัฒนา)
  • อธิบายเทคนิค 4 แบบ: Equivalence / Boundary / Control-flow / State-based + เขียน equivalence classes จากโจทย์ได้
  • อ่าน state diagram (Locked/Accepting/Unlocked/Blocked) และบอก transition ได้
  • อธิบาย mock objects (test driver vs test stub), fixture, และวงจร unit test 3 ขั้น (set up → act → verify)
  • เทียบ integration แบบ big bang / bottom-up / top-down / sandwich และ vertical

📖 บทเรียน

🗺️ ที่มาที่ไป — ทำไมต้องมี "วิทยาการทดสอบ"

ทุกคนที่พัฒนาซอฟต์แวร์ต้องทดสอบอยู่แล้ว — หลีกเลี่ยงไม่ได้ คำถามคือทำแบบสุ่ม ๆ (random trial-and-error) หรืออย่างเป็นระบบมีแผน? เป้าหมาย: ลอง "critical input combinations" ให้มากที่สุดในเวลา/ทรัพยากรที่มี — สูงสุด coverage ของ input space เท่าที่จะทำได้โดยทดสอบ "highest-priority" ก่อน

ทำไม testing ยาก: ระบบจริงจังทดสอบไม่ครบได้ — ตัวอย่างสไลด์: รหัส 4 หลัก มี 10,000 ชุด + ยังต้องเช็ก 3 หลัก 2 หลัก ครึ่ง ๆ กลาง ๆ จะ timeout reset รึเปล่า? คู่ของกันชุดล้นๆ? — เลยตั้งเป้า: หา fault ให้ได้เร็วและถูกที่สุด ทำได้เพราะเราเชื่อว่า "correct behavior บน critical test cases แทนพฤติกรรมของส่วนที่ไม่ได้ทดสอบได้"

Tradeoff หัวใจ: ทดสอบให้ครอบคลุมมาก ๆ (high coverage) แต่ต้นทุนจำกัด — จึงต้องมีเทคนิค "งัด" เคสที่ไล่ bug ได้มากที่สุดก่อน

📐 ศัพท์พื้นฐาน + TDD

"Testing shows the presence, not the absence of bugs." — Edsger W. Dijkstra (จำให้ขึ้นใจ — อาจออกอ้าง/เติมคำ)

Fault (aka defect, bug) = องค์ประกอบ HW/SW ที่ผิดพลาดซึ่งทำให้ระบบ fail ได้

Test-Driven Development (TDD): ทุกขั้นของการพัฒนาต้องเริ่มด้วยแผนว่าจะ verify ยังไง — ห้ามสร้าง artifact ใด (requirement, UML diagram, โค้ด) ถ้าไม่รู้ว่าจะทดสอบมันอย่างไร

Test case = การเลือก input data เฉพาะสำหรับทดสอบ + ผลที่คาดว่าจะได้ (expected output/behavior) — สังเกตว่าต้องมี "expected" เสมอ ไม่งั้นไม่ใช่ test case

Test = กลุ่ม test cases จำกัดชุดหนึ่ง

White-box = เอาโครงสร้างในโปรแกรมมาใช้ (สมมติมีโค้ดให้อ่าน) · Black-box = สำรวจ input space ของฟังก์ชันจากinterface specification (ไม่สนโค้ดข้างใน)

1) 🎯 Logical Organization of Testing — 7 ระดับ (หัวใจข้อจับคู่)

ระดับทำอะไรใคร/อะไรตรวจ
Unit testทดสอบโมดูล/คอมโพเนนต์เดี่ยว แบบโดดเดี่ยว เทียบ unit specificationdeveloper — white box
Integration testนำโมดูลที่ผ่าน unit test มาต่อกัน ทดสอบการทำงานร่วมกันdeveloper
Function testยืนยันว่าFunctional requirements ถูกตอบสนองทีม/QA บนระบบรวม
Quality testยืนยันNon-functional requirements (คุณภาพ เช่น speed, security)ทีม/QA
System testทดสอบระบบสมบูรณ์เทียบ System Specificationทีมรวม (ต้องทำงานกับช่างล็อก/ช่างไฟ ฯลฯ ถ้ามี HW)
Acceptance testลูกค้าทดสอบยอมรับว่า requirement ทั้งหมดตอบสนอง (black box)customer
Installation testทดสอบในสภาพแวดล้อมจริงของผู้ใช้ ("platform" จริง)ผู้ใช้ + ทีมติดตั้ง
⚡ ตัวอย่าง Acceptance tests ของ Safe Home (black box — ดูพฤติกรรมนอก)
  • ใช้คีย์ถูกต้องของ tenant ปัจจุบัน กับประตูห้องตัวเอง → pass
  • ใช้คีย์ถูกต้องของ tenant ปัจจุบัน กับประตูห้องคนอื่น → fail
  • ใช้คีย์ invalid กับห้องไหนก็ได้ → fail
  • ใช้คีย์ของ tenant ที่ถูกถอนแล้ว กับห้องเดิม → fail
  • ใช้คีย์ของ tenant ที่เพิ่มสด ๆ กับห้องตัวเอง → pass

อ่านได้ว่า acceptance test มักมาเป็น "สถานการณ์ input → คาดผล pass/fail" — เขียนได้ตั้งแต่ตอนเขียน requirement (บทที่ 6!)

📐 Test Coverage

Test coverage = วัดว่า spec หรือโค้ดของโปรแกรมถูก exercise โดยทดสอบมากแค่ไหน · Specification testing = ครอบคลุม input space (big picture — เช่น acceptance tests) · Code coverage = วัดว่าองค์ประกอบของ source code ถูกทดสอบเท่าไหร่ (implementation details — unit tests)

2) 🧪 เทคนิคออกแบบเทสที่ "Critical" — 4 แบบ

📐 Heuristics: เคสบางตัว "วิกฤต" กว่าใคร

Test cases ควรถูกจัดลำดับ — บางเทสมีโอกาสจับ fault สูงกว่า เพราะมนุษย์มักผิดซ้ำ ๆ รูปแบบเดิม · สำหรับ black-box: equivalence testing, boundary testing · สำหรับ white-box: control-flow testing, state-based testing — ใช้เดี่ยวหรือผสมกันได้

2.1) Equivalence Testing (black-box)

📐 หั่น input space เป็นกลุ่ม "คาดว่าเจ้าประจำตัวในกลุ่มทำงานเหมือนกัน"

แบ่ง input ทั้งหมดเป็น equivalence groups — สมมติฐาน: (1) นักพัฒนาที่ตั้งใจดีอาจพลาดแบบกระทบทั้งคลาสของค่า (2) ไม่มีเหตุผลที่เขาจะตั้งใจ hard-code พฤติกรรมพิเศษให้ค่าใดค่าหนึ่งในคลาส

2 ขั้น: ① แบ่งค่า input เป็น equivalence groups ② เลือกค่าทดสอบจากแต่ละกลุ่ม (หยิบตัวแทน 1 ตัวต่อกลุ่ม — เพราะสมมติว่าในกลุ่มพฤติกรรมเหมือนกัน)

สูตรหา equivalence classes:

  • input กำหนดเป็น ช่วงค่า (range เช่นตัวเลข/ตัวอักษร) → 1 กลุ่ม valid + 2 กลุ่ม invalid (น้อยกว่าช่วง / เกินช่วง)
  • input กำหนดเป็น ค่าเดียว (เช่น security code ตัวเฉพาะ) → 1 valid + 2 invalid
  • input กำหนดเป็น เซตค่า (เช่นชื่อวัน/เดือน) → 1 valid + 1 invalid
  • input เป็น Boolean → 1 valid + 1 invalid

2.2) Boundary Testing

📐 กรณีพิเศษของ equivalence — จับ "ขอบ"

โฟกัสค่าที่ขอบของ equivalence classes — ฐานคิด: นักพัฒนามักมองข้ามเคสพิเศษที่ขอบ (ตัวอย่างเรื่องจริง: Microsoft Zune leap year bug)

เลือก "ขอบ" หรือ outlier เช่น: ศูนย์, ค่า min/max, เซตว่าง, สตริงว่าง, null · สับสน > กับ >= · palindromes (สร้าง FSM จำกลับไม่ได้) ฯลฯ

2.3) Control-flow Testing (white-box)

ชนิด coverageความหมาย
Statement coverageทุก statement ถูกexecute อย่างน้อย 1 ครั้งโดย test case ใด test case หนึ่ง
Edge (branch) coverageทุก edge (กิ่งของ control flow) ถูก traverse อย่างน้อย 1 ครั้ง
Condition coverageทุก condition ให้ผล TRUE และ FALSE อย่างน้อยครั้งละครั้งใน test case ใดก็ได้
Path coverageทุกเส้นทาง (path) ที่แตกต่างของโปรแกรมถูก traverse อย่างน้อยครั้งละครั้ง (แพงสุด เส้นทางโตเร็วมาก)

โครง control graph: a; = เส้นเดียว · a; b; = สองกล่องต่อกัน · if a then b; = กิ่ง true เข้า b กิ่ง false ข้าม · if a then b else c; = สองกิ่ง · while a do b; = วนย้อน — และ Exceptions/Concurrency ก็เป็น control flow รูปหนึ่ง

2.4) State-based Testing (นิยมกับ OOP)

📐 นิยาม + ตัวอย่าง Safe Home

นิยามชุดabstract states ที่ object มีได้ แล้วทดสอบโดยเทียบ state จริงกับ state ที่คาด · state ของ object = constraint บนค่า attributes (เพราะ method ใช้ attribute คำนวณพฤติกรรม) — object ที่ไม่มี attribute ไม่มี state แต่ยัง unit-test ได้ · เตือน: state diagram เป็นสิ่งที่คน "คิดขึ้นมา" อาจไม่ครบ/ไม่ถูก (เหมือน equivalence classes)

5 สถานะของระบบล็อก:

  1. Locked ≡ (lockDeviceArmed == true) && (numOfAttempts == 0)
  2. Accepting ≡ (armed == true) && (0 < numOfAttempts < maxNumOfAttempts) — กำลังนับพยายาม (อาจเถียงได้ว่า Locked เป็น sub-state ของ Accepting)
  3. Unlocked ≡ (armed == false) && (numOfAttempts == 0)
  4. Blocked ≡ (armed == true) && (numOfAttempts == maxNumOfAttempts)
  5. Undefined ≡ ค่า attribute ที่ไม่เข้า 4 สถานะข้างบนเลย (บอกว่าโปรแกรมพัง — ควรไม่เกิด)

Events 2 ตัว: valid-key, invalid-key · transitions 5 เส้นที่ valid: Locked→Unlocked · Locked→Accepting · Accepting→Accepting (พยายามผิดซ้ำ ยังไม่เกิน) · Accepting→Unlocked · Accepting→Blocked (พยายามผิดจนเต็ม → sound-alarm)

3) Practical Unit Testing — Mock objects

📐 Driver vs Stub + วงจร 3 ขั้น

Test driver = ตัวจำลองส่วนที่เรียกใช้ component ที่ทดสอบ (ด้านบน) · Test stub = ตัวจำลองคอมโพเนนต์ที่ถูกเรียกใช้ (ด้านล่าง) — ต้องมี mock เพราะ: ① ตัวจริงยังไม่มีให้ใช้ ② mock ง่ายตรวจ fault เจอง่าย (mock ไม่ใช่แหล่ง bug)

unit ที่จะทดสอบเรียกว่า fixture — วงจร unit testing: ① สร้าง fixture + driver + stub(s) ② driver invoke operation บน fixture ③ ประเมินว่า actual state == expected state

ชื่อ method ทดสอบ: <methodName>_<startingState>_<expectedResult> เช่น checkKey_anyState_invalidKeyRejected(), enterKey_accepting_toBlocked() — ตรวจด้วย assert methods ของ JUnit/xUnit: assertTrue, assertEquals(expected, actual), assertNull ฯลฯ

4) Integration Testing — วิธีประกอบโมดูล

📐 ประเด็นหลัก: ประกอบทีละยูนิตแล้ว "จับตัวการ" ที่มีปัญหาให้เร็ว

Horizontal Integration:

  • "Big bang" — รวมทุกอย่างครั้งเดียวจบ → ปัญหา: จำกันยากว่าหน่วยไหนก่อ integration fault
  • Bottom-up — ทดสอบจาก Level-1 (ล่าง) ขึ้นไป ทีละก้อน (test Logger → +PhotoSObsrv → …) · ข้อดี: mock น้อยมาก · ข้อเสีย: ผู้ใช้ไม่เห็น functionality จนช้ามาก
  • Top-down — เริ่ม Level-4 (บนสุด Controller) ลงไป ใช้ stub แทนชั้นล่างที่ยังไม่มี
  • Sandwich — ผสมบวกล่างและบนลงประกบกลาง

Vertical Integration: หั่นระบบแนวตั้งตาม use case (user story) แล้ว integrate ในแต่ละสไลซ์ก่อน (ใช้เทคนิค horizontal ในสไลซ์) — ตาม TDD: outer loop = ทำ acceptance test ผ่าน, inner loop = ทำ unit test ผ่าน, ระหว่างกลาง Refactor (วงจร Red-Green-Refactor ของ story)

💡 เกร็ดจากสไลด์ท้ายบท — Honeypots (ความปลอดภัย)

Honeypot = กับดักหลอกเพื่อตรวจจับและศึกษาการโจมตีเครือข่าย (ส่วนของ security testing) — ผู้ใช้: Attackers (untrusted — script kiddies 95% ใช้มัลแวร์จากเน็ต ป้องกันง่าย / advanced 5% แกะระบบได้ ป้องกันยาก) กับ Researchers (trusted แต่อาจลบไฟล์ผิดพลาด) → ต้อง refine access control แยกสิทธิ์ตามประเภท

🎯 แนวข้อสอบของบทนี้

🎯 จับคู่ Testing — ออกแน่นอน (รีวิวรุ่นพี่ + NotebookLM ยืนยัน)
  • จับคู่ 7 ระดับ: Unit / Integration / Function / Quality / System / Acceptance / Installation ↔ คำอธิบาย — คีย์: "โดดเดี่ยว" (Unit), "รวมโมดูล" (Integration), "Functional Req" (Function), "Non-functional" (Quality), "ระบบสมบูรณ์+System Spec" (System), "ลูกค้ายอมรับ" (Acceptance), "สภาพแวดล้อมผู้ใช้จริง" (Installation)
  • จับคู่เทคนิค: equivalence groups (Equivalence), ค่า 0/min/max/null (Boundary), statement/edge/path coverage (Control-flow), states+transitions (State-based)
  • เขียนตอบ "จะทดสอบระบบอย่างไร" จากโปรเจกต์: เดินตามระดับ + black/white box + เขียน test case ตัวอย่าง (ดูเฉลยเต็มหน้าติว Final)
  • Driver vs Stub: driver เรียกของที่ทดสอบ (บน) / stub ถูกเรียก (ล่าง)
  • Equivalence classes จากโจทย์: ให้กฎ range/ค่าเดียว/เซต/boolean → นับกลุ่ม

🏋️ โจทย์ซ้อมมือ (8 ข้อ)

ข้อ 1●○○

จับคู่ (แนวข้อสอบตรงจากรุ่นพี่): จับประเภทการทดสอบกับคำอธิบาย: (1) Unit test (2) Integration test (3) Function test (4) Quality test (5) System test (6) Acceptance test (7) Installation test — กับคำอธิบาย: (ก) ลูกค้าทดสอบยอมรับ requirement ทั้งหมด (ข) ตรวจ Non-functional requirements (ค) ตรวจ Functional requirements (ง) ต่อโมดูลเข้าด้วยกันทดสอบ (จ) ตรวจแต่ละโมดูลแบบโดดเดี่ยว (ฉ) ตรวจในสภาพแวดล้อมใช้งานจริงของผู้ใช้ (ซ) ตรวจระบบรวมเทียบ System Specification

เฉลย
  1. (1)→(จ) Unit test — โมดูลเดี่ยวโดดเดี่ยว (ของ developer, white box)
  2. (2)→(ง) Integration test — รวมโมดูลแล้วทดสอบ
  3. (3)→(ค) Function test — ตอบสนอง Functional Requirements
  4. (4)→(ข) Quality test — ตอบสนอง Non-functional Requirements (คุณภาพ)
  5. (5)→(ซ) System test — ระบบสมบูรณ์เทียบ System Spec
  6. (6)→(ก) Acceptance test — ลูกค้ายอมรับ (black box โดยลูกค้า)
  7. (7)→(ฉ) Installation test — ติดตั้งใน environment จริงของผู้ใช้
ข้อ 2●○○

เติมคำ: "Testing shows the ______, not the ______ of bugs." — ใครพูด และแปลว่าอะไรในทางปฏิบัติ?

เฉลย
  1. เติม: "Testing shows the presence, not the absence of bugs." — Edsger W. Dijkstra
  2. ความหมาย: การทดสอบพิสูจน์ได้แค่ว่า "มีบั๊ก" — ไม่เคยพิสูจน์ได้ว่า "ไม่มีบั๊กเหลืออยู่เลย"
  3. ในทางปฏิบัติ: ระบบจริงจังไม่มีทางทดสอบครบทุก input (10,000 รหัส 4 หลัก + เคสเศษ ๆ) — เราจึงลดเป้าเป็นหา fault ที่ critical ให้เร็วที่สุดแทน
ข้อ 3●●○

ออกแบบ equivalence classes: ระบบ CS-Hospital รับ "อายุผู้ป่วย" ต้องอยู่ระหว่าง 1–120 ปี / "เลขบัตรประชาชน" ต้องเป็น 13 หลักพอดี / "เบอร์โทร" เป็นตัวเลข 9 หรือ 10 หลัก — ให้ equivalence classes แต่ละกรณีและเสนอค่าทดสอบ

เฉลย
  1. อายุ (range): valid = 1–120 · invalid = น้อยกว่า 1 (เช่น 0, -5) · invalid = มากกว่า 120 (เช่น 150) — รวม 3 กลุ่ม + ขอบ 1, 120 (boundary)
  2. เลขบัตร (ค่าเดียว — 13 หลักพอดี): valid = 13 หลัก · invalid = 12 หลัก · invalid = 14 หลัก — 3 กลุ่ม
  3. เบอร์โทร (เซตของ 2 ความยาว): valid = 9 หลัก หรือ 10 หลัก · invalid = ความยาวอื่น (8 หลัก, 11 หลัก) — 2 กลุ่ม (ตามกฎ "เซตค่า" = 1 valid + 1 invalid)
  4. เสริม boundary: อย่าลืม 1, 120, 13 หลักพอดี, ศูนย์ (0), เซตว่าง/สตริงว่าง, null — ขอบคือจุดที่ dev พลาดบ่อย
ข้อ 4●●○

State-based: ระบบล็อกอยู่ state "Accepting" ที่ numOfAttempts = maxNumOfAttempts − 1 — (ก) ถ้าผู้ใช้ใส่ key ผิดอีกเกิดอะไร (ข) ถ้าใส่ key ถูก (ค) ระบุ event, guard, action จาก transition ที่ (ก)

เฉลย
  1. (ก) numOfAttempts เต็ม max → transition Accepting → Blocked + sound-alarm
  2. (ข) ใส่ถูก → Accepting → Unlocked + signal-success (ตัวนับกลับ 0 ตามนิยาม Unlocked)
  3. (ค) แยก label: event = invalid-key · guard = [numOfAttempts = maxNumOfAttempts] · action = sound-alarm
  4. เทียบ transition ที่ยังไม่เต็ม: guard [count < max] → อยู่ Accepting→Accepting (signal-failure แต่ยังไม่ blocked)
ข้อ 5●●○

Mock objects: แยก test driver กับ test stub ต่างกันอย่างไร ทำไมต้องมี mock และ unit ที่ถูกทดสอบเรียกว่าอะไร

เฉลย
  1. Test driver = จำลองส่วนที่เรียกใช้ operation บน component ที่ทดสอบ (ตัวเรียก — อยู่ด้านบน)
  2. Test stub = จำลอง component ที่ถูกเรียกใช้โดยตัวที่ทดสอบ (ตัวถูกเรียก — ด้านล่าง)
  3. ทำไมต้อง mock: ① ตัวจริงยังไม่พร้อม/ไม่มี ② mock ง่าย ไม่เป็นแหล่ง fault → จับ bug ของตัวที่ทดสอบได้ง่าย
  4. unit ที่ทดสอบ = fixture — วงจร: สร้าง fixture+driver+stub → driver invoke → เทียบ actual vs expected state
ข้อ 6●●●

เทียบ Integration: Big bang มีปัญหาอะไร / Bottom-up ข้อดี-ข้อเสีย / Top-down ใช้อะไรแทนชั้นล่าง / ระบบที่ทำงานตาม user story ใหญ่ ๆ หลายตัวควรใช้แบบไหน

เฉลย
  1. Big bang: รวมหมดครั้งเดียว → แยกตัวการที่ก่อ integration fault ยากมาก
  2. Bottom-up: ข้อดี = ต้อง implement mock น้อยมาก / ข้อเสีย = ผู้ใช้ไม่เห็น functionality ใด ๆ จนช่วงท้ายพัฒนา
  3. Top-down: เริ่มจากบน (Controller) ใช้ test stub แทนชั้นล่างที่ยังไม่ถูกพัฒนา
  4. โจทย์ story ใหญ่: ใช้ Vertical Integration — หั่นแนวตั้งตาม use case/user story แล้ว integrate ในสไลซ์ก่อน (ใช้ horizontal ข้างใน) + วงจร TDD: acceptance test (outer loop) + unit test (inner loop) + refactor
ข้อ 7●●●

เขียน test case (โยงข้อสอบ Final): สำหรับระบบ CS-Hospital เขียน test case 1 ชุดในรูปแบบของสไลด์ (Test-case ID, Use Case Tested, Pass/fail criteria, Input data, Test procedure + expected result) โดยเลือกฟังก์ชัน "ค้นหาประวัติผู้ป่วย"

ข้อ 8●●○

Control-flow: ความต่าง statement / edge / condition / path coverage — และอะไรแพงสุดทำยากสุด เพราะอะไร

เฉลย
  1. Statement: ทุกคำสั่งรันผ่าน ≥ 1 ครั้ง (หยุดง่ายสุด)
  2. Edge: ทุกกิ่ง (branch) ของ control flow เดินผ่าน ≥ 1 ครั้ง
  3. Condition: ทุก condition ออกทั้ง TRUE และ FALSE ≥ ครั้งละครั้ง
  4. Path: ทุกเส้นทางเฉพาะเจาะจงของโปรแกรม ≥ 1 ครั้ง — แพงสุด เพราะจำนวน path โตแบบเลขชี้กำลังเมื่อมีวง/กิ่งซ้อน ทำจริงไม่ได้เต็ม 100%
