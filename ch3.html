บทที่ 3 — Software Quality

"ซอฟต์แวร์ดี" แปลว่าอะไร? บทนี้ตอบด้วยศัพท์ 16 คำ — Correctness, Reliability, Robustness ฯลฯ ซึ่งเป็นหัวข้อจับคู่ข้อสอบที่รุ่นพี่เจอตรง ๆ ("ให้นิยามมาแล้วเติมชื่อ Quality ที่ถูกต้อง")

🎯 จุดประสงค์ 📖 บทเรียน 🎯 แนวข้อสอบ 🏋️ โจทย์ซ้อมมือ

🎯 เรียนจบบทนี้ คุณต้องทำสิ่งเหล่านี้ได้

  • แยก External กับ Internal qualities ได้ และอธิบายความเชื่อมโยง (verifiability internal → reliability external)
  • แยก Product กับ Process qualities ได้
  • จำนิยาม 16 คุณภาพ แล้วจับคู่กับประโยคอธิบายได้ (แนวข้อสอบจับคู่ตรง ๆ)
  • อธิบาย 3 ประเภทของ Maintenance ตาม Ch3 (Corrective 20% / Adaptive / Perfective) — ทางไปบทที่ 11
  • บอกได้ว่าระบบ 4 ประเภท (Information-based / Real-time / Distributed / Embedded) ใส่ใจคุณภาพอะไรเป็นพิเศษ

📖 บทเรียน

🗺️ ที่มาที่ไป — วิศวกรแต่ละสาขาสร้างอะไร?

สไลด์เปิดด้วยคำถามสนุก ๆ: วิศวกรโยธา → สร้างสะพาน · วิศวกรไฟฟ้า → สร้างวงจร · วิศวกรอวกาศ → สร้างเครื่องบิน · วิศวกรซอฟต์แวร์ → สร้าง "ระบบซอฟต์แวร์"

แต่คำถามที่ยากกว่าคือ: สะพานดี = ทนน้ำทนแดด รับน้ำหนักได้ — แล้ว ซอฟต์แวร์ดี = ? คำตอบไม่มีคำเดียว แต่มี "ศัพท์ 16 คำ" ที่วิศวกรซอฟต์แวร์ทั้งโลกใช้คุยกันเรื่องคุณภาพ — นั่นคือเนื้อหาของบทนี้ และมันออกสอบจับคู่ทุกปี

อุปมาที่จะใช้ทั้งบท: ซอฟต์แวร์เหมือนรถยนต์ — วิ่งตรงตามที่บอกไว้ (Correctness) · เอาออกถนนทุกวันไม่สตาร์ทไม่ขึ้น (Reliability) · ชนหลุมก็ไม่พังทั้งคัน (Robustness) · เร่งได้ไว (Performance) · ใช้ง่ายไม่ต้องอ่านคู่มือ (User Friendliness) · เปิดฝากระโปรงซ่อมง่าย (Repairability/Maintainability) · เปลี่ยนเครื่องยนต์ใหม่ก็ยังวิ่งได้ (Portability/Adaptability)

1) External vs Internal Qualities — มองจากด้านไหน?

📐 นิยาม + ความเชื่อมโยงที่อาจารย์เน้น

External qualities = คุณภาพที่ ผู้ใช้มองเห็น (visible to the users) — ผู้ใช้คือคนที่ "สนใจ" คุณภาพพวกนี้ เช่น ใช้งานได้สม่ำเสมอไหม (reliability) ใช้ง่ายไหม

Internal qualities = คุณภาพที่นักพัฒนาเป็นคนสนใจ (concern the developers) — เกี่ยวกับ "โครงสร้างของซอฟต์แวร์" เป็นหลัก และมีหน้าที่ "ช่วยให้เกิดคุณภาพภายนอก"

ประโยคที่อาจารย์เขียนไว้ (ออกสอบได้): "The internal quality of verifiability is necessary to achieve the external quality of reliability" — โครงสร้างที่ตรวจสอบง่าย (internal) คือสิ่งจำเป็นที่ทำให้ระบบเชื่อถือได้ในสายตาผู้ใช้ (external)

2) Product vs Process Qualities — คุณภาพของ "ของ" หรือของ "วิธีทำ"

📐 คู่ที่สอง

Process = กระบวนการที่ใช้ผลิตผลิตภัณฑ์ซอฟต์แวร์ — ถ้า process ต้องการการวางแผน test data อย่างรอบคอบก่อนออกแบบ ผลลัพธ์คือผลิตภัณฑ์ดีขึ้น

Product = ตัวผลิตภัณฑ์ซอฟต์แวร์ — ซึ่งไม่ใช่แค่โค้ด แต่รวม object code, requirements, design, source code, test data ด้วย

ความเชื่อมโยง: Process qualities กับ product qualities ใกล้ชิดกันมาก (closely related) — เช่นกระบวนการที่ดีทำให้ product reliability สูงขึ้น

อุปมา: Process = สูตรและวิธีทำขนม, Product = ขนมจานนั้น — สูตรบอกให้ตวงนิ่งเวลาอบนิ่ง (process quality) ขนมออกมาอร่อยทุกแกงทุกเตา (product quality)

3) 16 คุณภาพ — 🎯 ตารางจับคู่ข้อสอบ (สำคัญที่สุดของบท)

🎯 รีวิวรุ่นพี่บอกเป๊ะ: "ให้นิยามหรือประโยคอธิบาย Software Quality มาแล้วให้เติมชื่อที่ถูกต้อง"

อ่านตารางนี้ให้ครบ จุดสำคัญคือจำ "คีย์เวิร์ดในนิยาม" — โจทย์จะเอาคีย์เวิร์ดมาตั้งประโยค เช่นเห็น "probability ... over a specified time interval" → Reliability ทันที

คุณภาพคีย์เวิร์ดในนิยามอธิบายแบบเข้าใจง่าย
1. Correctnessfunctional requirements specificationsโปรแกรม "ทำงานถูกต้องเชิงฟังก์ชัน" ตาม spec หรือไม่ — ขึ้นกับว่าเราเขียน spec ชัดแค่ไหน (rigorous) · ต้องบอกได้ไม่กำกวมว่าโปรแกรมตรง spec หรือไม่
2. Reliabilityprobability + operate as expected + specified time"โอกาสที่ซอฟต์แวร์จะทำงานตามคาดตลอดช่วงเวลาที่กำหนด" — ถ้าความผิดพลาดไม่ร้ายแรง โปรแกรมที่ไม่ 100% ถูกก็อาจยัง reliable อยู่ได้ · SE จะเป็นวิศวกรรมแท้จริงเมื่อทำ reliability ได้เทียบเท่าสินค้าวิศวกรรมอื่น
3. Robustnessจัดการ input แปลก ๆ (ill-formatted)"เข้มแข็ง" ต่อสถานการณ์ที่ไม่คาดคิด — ระบบที่ใช้โดยมือใหม่ต้องรับมือ input เพี้ยน ๆ ได้ แต่ embedded system จาก sensor อาจไม่ต้อง · สัมพันธ์แนบแน่นกับ correctness
4. Performancetoo slow / too big / memoryกระทบ usability: ช้า → ผลิตภาพลด · ใหญ่ → รันยาก · กิน RAM → แอปอื่นพัง · ประเมินด้วยวิเคราะห์ complexity ของอัลกอริทึม + 3 วิธี: Measurement, Analysis, Simulation
5. User Friendlinesseasy to use, menus vs commandsใช้ง่าย — มือใหม่/คนไม่ใช่โปรแกรมเมอร์อยากได้ menu ไม่ใช่พิมพ์ command · เมาส์/หน้าต่างดีกว่าคำสั่งอักษรตัวเดียว · อย่าลืม: correctness และ performance ก็ส่งผลต่อ user friendliness ด้วย
6. Verifiabilityverified easily, SW monitorsตรวจสอบได้ง่าย — วิธีเพิ่มคือใช้ software monitors (โค้ดที่ฝังเข้าไปเฝ้าดู performance/correctness) · เป็น internal quality ที่จำเป็นต่อ reliability (external)
7. MaintainabilitySW evolution, 3 ประเภทซ่อมคำว่า "ซ่อมบำรุง" ไม่ค่อยเหมาะกับซอฟต์แวร์ อาจารย์ชอบใช้คำว่า SW evolution — แบ่ง 3 ประเภท: Corrective (แก้ error ที่หลุดไป ~20% ของต้นทุน), Adaptive (ปรับให้เข้ากับ environment ใหม่ เช่น OS/DB ใหม่), Perfective (ปรับปรุงให้ดีขึ้น เพิ่มฟังก์ชัน ปรับ performance) → ลงลึกอีกทีในบทที่ 11
8. RepairabilityRAS, standard parts, modulesซ่อมง่าย — ยืมแนวคิด RAS (Repairability, Availability, Serviceability) จาก hardware · ใช้ standard parts ลดต้นทุน · เปลี่ยนชิ้นส่วนเดียวง่ายกว่าเปลี่ยนทั้งคัน → ผลิตภัณฑ์ที่มี well-designed modules ซ่อมง่ายกว่า · เลือกโครงสร้างโมดูล+interface ให้ถูก ลดการเชื่อมข้ามโมดูล
9. Evolvabilitymodified over time, documentedพัฒนาต่อยอดได้เรื่อย ๆ — ซอฟต์แวร์จะถูกแก้เพิ่มฟังก์ชันใหม่/แก้ฟังก์ชันเดิมตลอดเวลา · ถ้าการแก้ไม่ถูกจดบันทึก (documented) การแก้ครั้งหน้าจะยากขึ้นเรื่อย ๆ · การแก้ต้องศึกษา design เดิมอย่างรอบคอบ + บันทึกการเปลี่ยนทั้งใน design และ requirements spec
10. Reusabilityreuse, reduce costsนำกลับมาใช้ใหม่ — แก้ผลิตภัณฑ์เดิมเป็นเวอร์ชันใหม่ หรือใช้สร้างผลิตภัณฑ์อื่นด้วยการแก้เล็กน้อย · ลดต้นทุนผลิต · เช่นนำ requirements spec เก่ามา reuse แทนเขียนใหม่
11. Portabilitydifferent environments/platformsย้ายที่อยู่ได้ — รันบนสภาพแวดล้อม/แพลตฟอร์ม (OS) อื่นได้ เช่นโปรแกรมเดียวกันรันได้ทั้ง Windows และ macOS
12. Understandabilityeasy to understand, internalอ่านเข้าใจง่าย — design ที่เข้าใจง่าย · เป็น internal quality · ช่วยบรรลุ evolvability และ verifiability (โค้ดที่อ่านรู้เรื่อง = แก้ง่าย ตรวจง่าย)
13. Interoperabilitycoexist + cooperate with other systemsอยู่ร่วมและร่วมมือกับระบบอื่นได้ — หลาย vendor ทำ integrated products ที่มีหลายฟังก์ชันต้องคุยกัน (เช่นแอปธนาคารเรียก PromptPay)
14. Productivityprocess quality, SW reuseคุณภาพเชิง performance ที่ใช้กับ process (ไม่ใช่ product!) — SW reuse เป็นเทคนิคที่เพิ่ม productivity รวมขององค์กร · แต่พัฒนาโมดูล reusable ยากกว่าโมดูลใช้เอง
15. Timelinessdeliver on timeส่งทันเวลา — คุณภาพที่เกี่ยวกับ process: ความสามารถส่งมอบผลิตภัณฑ์ตรงเวลา
16. Visibilitydocumented steps + current statusมองเห็นได้ — กระบวนการพัฒนาจะ visible ถ้าทุกขั้นตอนและสถานะปัจจุบันถูกจดบันทึกชัดเจน · product จะ visible ถ้ามีโครงสร้างชัด ฟังก์ชันเข้าใจง่าย เอกสารเข้าถึงง่าย · เป็นทั้ง internal และ external quality · ช่วยให้ SEng ชั่งน้ำหนักผลของการกระทำและตัดสินใจได้

4) คุณภาพตามประเภทระบบ — 4 แบบระบบที่ใส่ใจคนละคุณภาพ

ประเภทระบบคืออะไร + ตัวอย่างคุณภาพที่ใส่ใจเป็นพิเศษ
Information-Based Systems
(ระบบจัดการสารสนเทศ)		หัวใจคือ database ใช้ transaction สร้าง/ดึง/แก้/ลบ — ธนาคาร, ระบบห้องสมุด, ระบบบุคลากรData integrity (ข้อมูลจะเสียหายไหม?) · Security (ป้องกันการเข้าถึงโดยไม่ได้รับอนุญาต?) · Data availability (เงื่อนไขไหนทำให้ข้อมูลใช้ไม่ได้?) · Transaction performance
Real-Time Systemsต้องตอบสนองเหตุการณ์ภายในช่วงเวลาที่กำหนดอย่างเข้มงวด — ระบบเฝ้าดูอุณหภูมิโรงงาน, ซอฟต์แวร์จัดการคลิกเมาส์Response time คือส่วนหนึ่งของความถูกต้อง (correctness) — ตอบเร็วเกินก็ผิดเท่ากับช้าเกิน! เช่นคลิกแรกประมวลผลไวเกิน จะไม่จับ double-click ได้
Distributed Systemsคอมโพเนนต์รันบนคอมพิวเตอร์หลายเครื่อง — คำถาม: กระจาย data? processing? หรือทั้งคู่?ทนการแบ่งเครือข่าย (partitioning — สองกลุ่มเครื่องคุยกันไม่ได้) · ทนเครื่องล่มเป็นตัว ๆ (failure of individual computers) · ทางแก้: replicate ข้อมูลเดียวกันไว้หลายเครื่องเพื่อเพิ่ม reliability
Embedded SystemsSW เป็น 1 ในหลายคอมโพเนนต์ มักไม่มี interface กับมนุษย์ แต่คุยกับอุปกรณ์อื่นและควบคุมมัน — เครื่องบิน, หุ่นยนต์, ไมโครเวฟความต่างจากระบบอื่น = interface กับอุปกรณ์ ไม่ใช่มนุษย์ · เช่นตู้ขายของอัตโนมัติหยอดเหรียญ, ระบบเฝ้าดูผู้ป่วยโรงพยาบาลที่เก็บประวัติ (จำตัวอย่าง CS-Hospital ไว้เชื่อมข้อเขียน!)
💡 ความสัมพันธ์คำถาม Q1–Q3 ที่สไลด์ทิ้งไว้ (Correctness, Reliability, Robustness)

ทั้งสามเกี่ยวข้องกันเป็นลูกโซ่: Correctness = ทำตาม spec ถูกต้องในกรณีปกติ · Reliability = ทำงานตามคาดต่อเนื่องในช่วงเวลาที่วัด (ผิดเล็กน้อยแต่ไม่รบกวนผู้ใช้ก็ยัง reliable ได้) · Robustness = เมื่อเจอสิ่งที่ spec ไม่ได้ครอบคลุม (input เพี้ยน สถานการณ์แปลก) ระบบไม่พังทั้งระบบ — พูดรวม ๆ: ถูกต้องในกรณีปกติ (correctness) → เชื่อถือได้เมื่อใช้ยาว (reliability) → ไม่พังเมื่อโลกไม่เป็นตามแผน (robustness)

🏋️ โจทย์ซ้อมมือ (8 ข้อ)

ข้อ 1●○○

เติมคำ (แนวข้อสอบตรง): (1) "The probability that SW can operate as expected over a specified time interval" คือคุณภาพใด (2) "The ability of a system to coexist and cooperate with other systems" คืออะไร (3) "The ability to run a system in the different environments or platform" คืออะไร

เฉลย
  1. (1) Reliability — คีย์ "probability" + "operate as expected" + "specified time interval"
  2. (2) Interoperability — คีย์ "coexist and cooperate with other systems"
  3. (3) Portability — คีย์ "different environments or platform (OS)"
ข้อ 2●○○

เติมคำ: "The internal quality of ______ is necessary to achieve the external quality of ______" — เติมให้สมบูรณ์

เฉลย
  1. ช่องแรก: Verifiability (internal — โครงสร้างที่ตรวจสอบได้ง่าย)
  2. ช่องสอง: Reliability (external — ผู้ใช้เชื่อถือได้ว่าระบบทำงานตามคาด)
  3. เหตุผล: ถ้าโครงสร้างตรวจสอบยาก (ทดสอบไม่ได้) เราจะไม่มีทางมั่นใจได้เลยว่าระบบจะทำงานตามคาดเมื่อใช้จริง — ตรวจไม่ได้ = เชื่อไม่ได้
ข้อ 3●○○

จำแนกสถานการณ์ (แนว 3 ประเภท maintenance): (a) แอปพังเมื่อผู้ใช้พร้อมกันมาก — หาสาเหตุโค้ดแล้วแก้ (b) องค์กรเปลี่ยน OS server เป็นเวอร์ชันใหม่ — ต้องปรับระบบ (c) ลูกค้าอยากได้ฟีเจอร์ชำระเงินด้วย QR — ทำเพิ่ม

เฉลย
  1. (a) Corrective — แก้ error ที่พบหลังส่งมอบ (คีย์: พัง/แก้ bug)
  2. (b) Adaptive — ปรับตัวกับ environment ที่เปลี่ยน (คีย์: OS ใหม่ / DB ใหม่)
  3. (c) Perfective — ปรับปรุงเพิ่มฟังก์ชัน/คุณภาพใหม่ (คีย์: add new function)
ข้อ 4●●○

จำแนกระบบ (แนว 4 ประเภทระบบ): (a) ระบบห้องสมุดที่หัวใจอยู่ที่ฐานข้อมูลและ transaction (b) ระบบตรวจจับการคลิกเมาส์สองครั้งติดกัน ต้องวัดเวลาแม่น (c) ระบบสำรองข้อมูลเหมือนกันไว้ 3 เครื่อง ทนเครื่องล่ม (d) ระบบในตู้ขายน้ำที่คุยกับเครื่องอ่านเหรียญ ไม่มีหน้าจอให้คนกด

เฉลย
  1. (a) Information-Based System — หัวใจ database + transactions, สนใจ data integrity/security/availability
  2. (b) Real-Time System — คีย์: เวลาตอบสนองเข้มงวด ตอบเร็วไปก็ผิด (ไม่จับ double-click)
  3. (c) Distributed System — คีย์: replicate ข้อมูลหลายเครื่อง ทน failure ของเครื่องแต่ละตัว
  4. (d) Embedded System — คีย์: ไม่มี interface กับมนุษย์ คุยกับอุปกรณ์อื่น (เหรียญ) และควบคุมมัน
ข้อ 5●●○

ตัวเลข: วิธีประเมิน Performance มีกี่วิธี อะไรบ้าง และผลกระทบ 3 แบบของระบบที่ performance แย่คืออะไร

เฉลย
  1. ประเมินด้วย การวิเคราะห์ complexity ของอัลกอริทึม + 3 วิธี: Measurement (วัดจริง), Analysis (วิเคราะห์), Simulation (จำลอง)
  2. ช้าเกิน → ลด productivity ของผู้ใช้
  3. ใหญ่เกิน → รันยาก
  4. กินหน่วยความจำเยอะ → กระทบแอปอื่นที่กำลังรัน
ข้อ 6●●●

เทียบคู่: Correctness กับ Reliability ต่างกันอย่างไร และทำไม "โปรแกรมที่มี bug เล็ก ๆ ก็ยังอาจ reliable ได้"

เฉลย
  1. Correctness = โปรแกรมตรง functional spec ทุกข้อ (มองเทียบกับเอกสาร)
  2. Reliability = ความน่าจะเป็นที่จะทำงานตามคาดตลอดช่วงเวลาที่กำหนด (มองพฤติกรรมตามเวลาจริง)
  3. ทำไม bug เล็กยัง reliable ได้: สไลด์บอก "ถ้าความผิดพลาดของ error ไม่ร้ายแรง (ไม่ serious) โปรแกรมที่ไม่ถูก 100% ก็ยัง reliable อยู่ได้" — เช่นทายผิดพลาดในส่วนที่ผู้ใช้ไม่เจอ/ไม่กระทบการใช้งาน ผู้ใช้ก็ยังมั่นใจว่าระบบ "ทำงานตามคาด"
  4. สรุปสั้น: correctness วัดกับ spec, reliability วัดกับประสบการณ์ผู้ใช้ในเวลาจริง — เกณฑ์คนละแบบ
ข้อ 7●●●

ลักไก่: Productivity, Timeliness และ Visibility เป็นคุณภาพของอะไร — Product หรือ Process? และ Visibility เป็น internal หรือ external?

เฉลย
  1. Productivity = คุณภาพเชิง performance ที่ใช้กับ Process (ของทีม/วิธีทำงาน ไม่ใช่ของตัวโปรแกรม)
  2. Timeliness = เกี่ยวกับ Process — ความสามารถส่งมอบตรงเวลา
  3. Visibility = ทั้งสองอย่าง (both internal and external) — process จะ visible เมื่อทุกขั้น+สถานะถูกจดบันทึก / product จะ visible เมื่อโครงสร้างชัด เอกสารเข้าถึงง่าย
  4. ประโยชน์ของ visibility: ให้วิศวกรชั่งผลของการกระทำ (weigh the impact) และนำทางการตัดสินใจ
ข้อ 8●●●

โยงข้อสอบเขียน: ข้อสอบรุ่นพี่ถามเรื่องระบบ CS-Hospital — ถ้าให้คุณบอกว่าระบบจัดการผู้ป่วยนี้ต้องใส่ใจคุณภาพใดเป็นพิเศษ 3 อย่าง พร้อมเหตุผล จะตอบอย่างไร?

แนวคำตอบ
  1. มองประเภทระบบก่อน: CS-Hospital เก็บข้อมูลผู้ป่วยในฐานข้อมูล มี transaction สร้าง/ดึง/แก้ → เป็น Information-Based System
  2. คุณภาพที่ต้องเน้น 1: Data integrity + Security — ข้อมูลผู้ป่วยเป็นความลับทางการแพทย์ ต้องไม่เสียหายและไม่รั่วไหลให้คนนอกเข้าถึง
  3. 2: Data availability / Reliability — แพทย์ต้องเข้าถึงประวัติผู้ป่วยได้ทุกเมื่อเวลาฉุกเฉิน ระบบล่ม = เสี่ยงชีวิตผู้ป่วย
  4. 3: Interoperability — ระบบต้องส่งต่อผลวินิจฉัยไปทีมแพทย์เฉพาะทางผ่านช่องทางออนไลน์ (LINE/Email) ต้องคุยกับระบบ/บริการอื่นได้
  5. ปิดท้าย (ได้คะแนนเพิ่ม): เพราะส่วน "ส่งต่อผลให้ทีมแพทย์" อาจต้องทำงานแบบ real-time จึงอาจกล่าวถึง performance/response time ของการแจ้งเตือนด้วย
