บทที่ 11 — Software Maintenance

บทปิดท้าย = หัวข้อจับคู่ที่รุ่นพี่ยืนยันออกชัวร์: Corrective / Adaptive / Perfective / Preventive (สัดส่วน 21% / 25% / 50% / 4%) บวกกระบวนการ maintenance และ "วางแผน Maintenance จากโปรเจกต์" ที่ออกเขียนตอบทุกปี

🎯 จุดประสงค์ 📖 บทเรียน 🎯 แนวข้อสอบ 🏋️ โจทย์ซ้อมมือ

🎯 เรียนจบบทนี้ คุณต้องทำสิ่งเหล่านี้ได้

  • นิยาม Maintenance: "กระบวนการแก้ไขระบบซอฟต์แวร์หลังส่งมอบ เพื่อ correct faults / improve performance / adapt สิ่งแวดล้อมเปลี่ยน"
  • จำแนก 4 ประเภทจากสถานการณ์ + ท่องสัดส่วน 21/25/50/4 ได้ (แนวจับคู่ตรง)
  • เทียบการพัฒนา (development) กับการบำรุงรักษา (maintenance) ได้ 5 บรรทัด
  • บอกจุดเน้น maintenance ในแต่ละช่วงชีวิตผลิตภัณฑ์ (Introductory / Growth / Maturity / Decline)
  • เดิน กระบวนการ maintenance 5 ขั้น: Change requests → Impact analysis → Release planning → Change implementation → System release
  • บอกปัจจัยที่กระทบ maintainability + ต้นทุน (team stability, contractual responsibility, staff skills, program age/structure)
  • เขียน "แผน Maintenance จากโปรเจกต์" ตามโครงข้อสอบได้

📖 บทเรียน

🗺️ ที่มาที่ไป — ซอฟต์แวร์ "ไม่จบ" ตอนส่งมอบ

บทที่ 1 เราเห็นกฎ Law of Continuing Change — ซอฟต์แวร์ต้องเปลี่ยนตลอด · บทนี้คือ "หน้าที่การงาน" ที่ตามมา

นิยาม: Software maintenance = กระบวนการแก้ไขระบบซอฟต์แวร์หรือ component หลังการส่งมอบ (after delivery) เพื่อ (1) correct faults (แก้ผิดพลาด) (2) improve performance หรือคุณลักษณะอื่น (3) adapt to a changed environment (ปรับกับสภาพแวดล้อมใหม่)

การเปลี่ยนอาจเล็ก (แก้ coding error) กว้างขึ้น (แก้ design error) หรือใหญ่ (แก้ specification error / รองรับ requirement ใหม่)

ตัวเลขสำคัญจากกราฟ: ต้นทุนรวมยุคหลังมี Software Maintenance กินสัดส่วนสูงขึ้นเรื่อย ๆ จนแพงกว่าการพัฒนา (Hardware แพงน้อยลง ซอฟต์แวร์แพงขึ้น 1955→1985) — ตัวอย่าง System 1/System 2 ในกราฟสไลด์แสดงว่าต้นทุน maintenance สะสมทับพัฒนาครั้งเดียวได้อีกเป็นเท่าตัว

อุปมา: ซื้อรถ — เงินก้อนแรก (development) จ่ายครั้งเดียว แต่น้ำมัน ยาง บำรุงรักษา (maintenance) จ่ายต่อทุกเดือนอีก 10 ปี รวมแพงกว่าค่าตัวหลายเท่า

1) 🎯 Kinds of Maintenance — 4 ประเภท (จับคู่ข้อสอบชัวร์ที่สุด)

ประเภทสัดส่วนคีย์เวิร์ดอธิบาย + ตัวอย่าง
Corrective21% (สไลด์ Ch3 ใช้ ~20%)"แก้บั๊ก" หลังส่งมอบแก้ไขerrors — แก้ข้อผิดพลาดที่พบหลังส่งมอบ หรือผิดพลาดที่เกิดระหว่าง maintenance เอง · เช่นระบบคิด VAT เกินเมื่อยอดเฉพาะช่วง, แอปพังเมื่อคนเข้าพร้อมกันเยอะ
Adaptive25%"สิ่งแวดล้อมเปลี่ยน" ทั้ง HW/SWปรับระบบให้เข้ากับสิ่งแวดล้อมที่เปลี่ยน (hardware และ software ทั้งคู่) · เช่นอัปเดตให้รองรับ OS ใหม่, DB engine ใหม่, เปลี่ยน cloud provider
Perfective50% — เยอะสุด!"ผู้ใช้อยากได้เพิ่ม/ดีขึ้น"ปรับให้ตอบสนอง requirement ผู้ใช้ที่เปลี่ยน — เพิ่มฟังก์ชันใหม่ ปรับปรุงให้ใช้ดีขึ้น/เร็วขึ้น · เช่นเพิ่มช่องทางจ่าย QR, ปรับ UI ให้ง่ายขึ้น
Preventive4% — น้อยสุด"ป้องกันล่วงหน้า เพิ่ม maintainability"ปรับปรุงให้maintainability ของระบบสูงขึ้น เพื่อกันปัญหาอนาคต · เช่น refactoring โครงสร้างโค้ด เพิ่มเอกสาร/คอมเมนต์ ทำ automated test เพิ่ม

2) Development vs Maintenance — ทำงาน "คนละจังหวะ"

หัวข้อDevelopment (พัฒนา)Maintenance (บำรุงรักษา)
เชื่อมโลกจริงnot directly linked to the real world — อิสระdirectly driven by the real world — ถูกสั่งด้วยเหตุจริงตลอด
อิสระ vs ถูกมัดfreedom — เลือกได้constrained by existing system — มัดมือกับระบบเดิม
defectdefects มี no immediate effect (ยังไม่ถึงผู้ใช้)defects disrupt production — ผู้ใช้ที่ใช้อยู่จริงโดนทันที!
methodsเลือก method ทันสมัยได้system ไม่ได้ใช้ method ปัจจุบัน
standardsบังคับ standards ได้มีแต่ shifting standards (ถ้ามี)
📐 จุดเน้น Maintenance ตามช่วงชีวิตผลิตภัณฑ์ (Shift over Time)
  • Introductory stage: เน้น user support (ช่วยผู้ใช้เริ่มใช้)
  • Growth stage: เน้น correcting faults (จุดติดบั๊กเยอะ เพราะคนใช้เยอะขึ้น)
  • Maturity: เน้น enhancements (เพิ่มเติมปรับปรุง)
  • Decline: เน้น technology changes (ตามเทคโนโลยีที่เปลี่ยน)

3) ปัญหา · เครื่องมือ · กระบวนการ

📐 Major Causes of Maintenance Problems (3 ข้อ) + เครื่องมือ 4 กลุ่ม

สาเหตุหลัก 3 ข้อ: ① Unstructured code (โค้ดไม่มีโครง แก้ครั้งเดียวรู้เรื่อง ครั้งสองเละ) ② Insufficient domain knowledge (ไม่รู้เขตธุรกิจที่ระบบรองรับ) ③ Insufficient documentation (เอกสารไม่พอ)

เครื่องมือบำรุงรักษา 4 กลุ่ม: ① ช่วยการรับรู้ (reformatters จัดหน้าตาโค้ด) ② มองโครงสร้างนิ่ง (static structure) ③ มองพฤติกรรมขณะรัน (dynamic behavior) ④ ส่องประวัติเวอร์ชัน (version history)

วิเคราะห์ evolution 2 แนว: Version-centered (ศึกษา diff ระหว่างเวอร์ชันติดกัน) / History-centered (ศึกษาจากมุมมอง เช่น component ไหนถูกแก้พร้อมกันบ่อย)

💡 Architectural Evolution + UI Distribution (เกร็ดสไลด์)

ความจำเป็นย้าย legacy รวมศูนย์ → client-server: ① ต้นทุน HW — server ถูกกว่า mainframe ② ผู้ใช้คาดหวัง GUI ③ ต้องเข้าระบบจากหลายที่ห่างกัน (distributed access)

User Interface Distribution: ถ้าระบบเดิมแยก UI กับ application ชัด → ปรับกระจาย UI ไป PC ได้ตรง ๆ · ถ้าไม่ชัด → ใช้ screen management middleware แปลหน้าจอข้อความเก่าเป็น GUI

4) อะไรกระทบ Maintainability + ปัญหาการจัดการ + Prediction

ปัจจัยใจความ
Application ageโปรแกรมเก่ามักเขียนแย่กว่า ("software rust?") และถูก patch รอบนาทมากกว่า
Sizeวัดใน KLOC, จำนวนไฟล์ input/output — ใหญ่ = ยาก
Programming language4GL ควรได้โค้ด maintainable กว่า 3GL
Processing environmentfiles ยากกว่า databases / real-time ยากกว่า batch
Analysis & design methodologiesซอฟต์แวร์ที่ออกแบบดี = บำรุงรักษาง่ายกว่ามาก
Structured programmingหลักฐานว่าช่วยจริงมีขัดแย้งกัน (conflicting evidence)
Modularizationแกนกลางเทคนิค OO — ชิ้นเล็กครบในตัว (self-contained) ดูแลง่ายกว่า
Documentation generationดูแลเอกสารแพงเท่ากันกับดูแลโค้ด
End-user involvementผู้ใช้จริงมีส่วนร่วมมาก → maintenance ลดลง (ตามนักวิจัยบางส่วน)
Maintenance managementการจัดตารางและทัศนคติผู้บริหารกระทบ productivity
📐 ปัญหาการจัดการ (Problems in Managing Maintenance) 5 ข้อ
  • Changing priorities — คำขอ maintenance ยุ่งวุ่นวาย งานยาวจนงานใหม่วิ่งเข้ามาก่อนงานเก่าจบ
  • Inadequate testing methods — เวลาทดสอบไม่พอ ขาด test data ครบ ไม่มีเกณฑ์เข้มตอน sign-off
  • Performance measurement difficulties — วัดผลงานรายคน/กลุ่มยังไง?
  • เอกสารไม่ครบ/ไม่มี — อบรมคนใหม่ใช้เวลานาน โปรแกรมเมอร์เอาแต่ติดอยู่กับซอฟต์แวร์เดิม
  • ตาม business ที่เปลี่ยนเร็ว — HW/SW เก่าล้า (obsolete)

Maintenance Prediction: ประเมินว่าส่วนไหนจะ "แพง" — ระบบที่couple แน่น (tightly coupled) ต้องแก้ทุกครั้งที่ environment เปลี่ยน · ปัจจัย: จำนวน+ซับซ้อนของ interfaces, requirement ที่ล่องหนเปลี่ยน (volatile), business process ที่ใช้ระบบ · งาน maintenance ส่วนใหญ่เอาแรงไปกองที่component ไม่กี่ตัว · ซับซ้อนขึ้นกับ: control structures / data structures / ขนาด procedure-module

ชี้วัด maintainability จาก process measurements 4 ตัว: ① จำนวนคำขอ corrective ② เวลาเฉลี่ย impact analysis ③ เวลาเฉลี่ย implement แต่ละคำขอ ④ จำนวนคำขอค้าง — ถ้าเหล่านี้เพิ่มขึ้นเรื่อย ๆ = maintainability กำลังถดถอย

⚡ Maintenance Cost Factors — 4 ตัว (จับคู่ได้)
  • Team stability — ทีมเดิมทำต่อเนื่อง → ต้นทุนลด (รู้ระบบอยู่แล้ว)
  • Contractual responsibility — ผู้พัฒนาไม่มีภาระสัญญาดูแลต่อ → ไม่มีแรงจูงใจออกแบบให้แก้ง่ายในอนาคต
  • Staff skills — ทีม maintenance มักน้องใหม่+domain knowledge จำกัด
  • Program age and structure — ยิ่งเก่าโครงยิ่งถดถอย เข้าใจยาก แก้ยาก

🎯 แนวข้อสอบของบทนี้

🎯 จับคู่ Maintenance + เขียนแผน — ออกชัวร์
  • จับคู่สถานการณ์ → 4 ประเภท: พัง/แก้บั๊ก = Corrective · OS/DB ใหม่ = Adaptive · เพิ่มฟังก์ชัน/ใช้ง่ายขึ้น = Perfective · refactor/เพิ่มเอกสารกันปัญหาอนาคต = Preventive · จำสัดส่วน 21/25/50/4
  • เขียนตอบ "จะวางแผน Maintenance อย่างไร": เดินโครงกระบวนการ 5 ขั้น + ระบุ 4 ประเภทจะใช้เมื่อไหร่ + ชี้วัด 4 ตัว → เฉลยเต็มที่หน้า ติว Final
  • เทียบ Development vs Maintenance 5 บรรทัด (โดยเฉพาะ "defects disrupt production")
  • ช่วงชีวิต: Introductory=user support / Growth=correcting / Maturity=enhancements / Decline=technology
  • Cost factors 4 ตัว และสัญญาณ maintainability ถดถอย (คำขอ corrective เพิ่ม ฯลฯ)

🏋️ โจทย์ซ้อมมือ (6 ข้อ)

ข้อ 1●○○

จำแนก (แนวข้อสอบตรง): (a) ผู้ใช้รายงานว่าโอนเงินข้ามธนาคารคิดค่าธีผิดเงื่อนไขบางเคส ทีมเข้าไปแก้โค้ด (b) บริษัทอัปเกรดฐานข้อมูลเป็นรุ่นใหม่ ทีมปรับ SQL และ driver ให้รองรับ (c) ผู้ใช้ขอปุ่ม export รายงานเป็น Excel เพิ่ม (d) ทีมใช้เวลา 2 สัปดาห์แยกฟังก์ชันที่วุ่นวายออกเป็นโมดูลและเขียนเอกสารเพิ่ม

เฉลย
  1. (a) Corrective — แก้ error ที่พบหลังส่งมอบ (คีย์: คิดผิด/bug)
  2. (b) Adaptive — สิ่งแวดล้อม (DB) เปลี่ยน ระบบปรับตาม
  3. (c) Perfective — requirement ผู้ใช้ใหม่ เพิ่มฟังก์ชัน (สัดส่วน 50% เยอะสุดจริง)
  4. (d) Preventive — เพิ่ม maintainability/โครงสร้างกันปัญหาอนาคต (4% น้อยสุด)
ข้อ 2●○○

นิยาม/ตัวเลข: เขียนนิยาม Software maintenance ตามสไลด์ และเรียงสัดส่วน 4 ประเภทจากมากไปน้อยพร้อมตัวเลข

เฉลย
  1. นิยาม: กระบวนการแก้ไขระบบซอฟต์แวร์หรือ component หลังส่งมอบ เพื่อ correct faults, improve performance หรือคุณลักษณะอื่น, หรือ adapt สิ่งแวดล้อมที่เปลี่ยน
  2. เรียง: Perfective 50% → Adaptive 25% → Corrective 21% → Preventive 4%
  3. จำทริค: "ครึ่งงานคือผู้ใช้อยากได้เพิ่ม (P50) สี่ส่วนร้อยแรกเป็นปรับสภาพแวดล้อม (A25) แก้บั๊ก (C21) ส่วนกันปัญหาล่วงหน้าแค่สี่เปอร์เซ็นต์ (P4)"
ข้อ 3●●○

เทียบ: เมื่อพัฒนา (development) พบ defect กับเมื่อ maintenance พบ defect ต่างกันอย่างไร และอีก 2 ความต่างเด่นระหว่างสองช่วง

เฉลย
  1. Development: defect มี "no immediate effect" — ระบบยังไม่เปิดใช้ แก้ได้เงียบ ๆ
  2. Maintenance: defect "disrupt production" — ผู้ใช้ใช้งานจริงอยู่ บั๊กทำร้ายธุรกิจทันที ต้องเร่งแก้ + ระวังเวลาหยุดระบบ
  3. ความต่างเด่นอื่น: development มี freedom (ไม่ผูกโลกจริงตรง) / maintenance ถูก driven ด้วยเหตุจริงและติดคาระบบเดิม (constrained by existing system)
  4. อีกความต่าง: standards — พัฒนาบังคับ standard ได้ / maintenance เจอ shifting standards ถ้ามี
ข้อ 4●●○

เรียงช่วงชีวิต: จับจุดเน้นกับช่วง: Introductory / Growth / Maturity / Decline กับ: correcting faults / user support / technology changes / enhancements

เฉลย
  1. Introductory → user support (ช่วยให้เริ่มใช้ได้)
  2. Growth → correcting faults (คนใช้เยอะ เจอบั๊กเยอะ)
  3. Maturity → enhancements (เสถียรแล้ว ต่อยอดความสามารถ)
  4. Decline → technology changes (ตามเทคโนโลยีที่ล้า)
ข้อ 5●●●

เขียนตอบโยง Final (สำคัญ!): "จากโปรเจกต์ที่คุณทำ (เว็บ CS-Hospital) คุณจะวางแผน Maintenance อย่างไร" — เขียนโครงคำตอบ 5 ขั้นของกระบวนการ + แผนครอบ 4 ประเภท + ตัวชี้วัด

แนวคำตอบ (โครงที่ใช้สอบได้)
  1. เปิดด้วยกระบวนการ 5 ขั้น: ① เปิดช่องรับ Change requests จากพยาบาล/แพทย์/ผู้ดูแลระบบ (แยก fault repair, platform adaptation, enhancement) ② ทำ Impact analysis ทุกคำขอ — ดูโมดูล/schema ใดกระทบ ประเมินความเสี่ยง (เช่นแก้ตาราง Patient กระทบรายงานทุกใบ) ③ Release planning — จัดคิวงานเป็นรอบเช่นรายเดือน กำหนดเวลาหยุดบริการขั้นต่ำ ④ Change implementation — แก้บนสำเนา ทดสอบ (unit → system → acceptance โดยผู้ใช้จริง) ⑤ System release — ปล่อยเวอร์ชัน + เอกสาร + แจ้งผู้ใช้
  2. แผนครอบ 4 ประเภท: Corrective — มีช่องทางแจ้งปัญหา + SLA แก้ด่วนเคสรบกวนการรักษา · Adaptive — ติดตามอัปเดต OS/Browser/DB ทดสอบ compatibility ทุกไตรมาส · Perfective — เก็บ backlog ฟีเจอร์ใหม่จากผู้ใช้ (เช่นรายงานใหม่) ประเมินทุกรอบ · Preventive — จัดเวลา refactoring + ดูแลเอกสาร/test เพิ่มความ maintainable
  3. ตัวชี้วัด (4 process measurements): นับจำนวนคำขอ corrective ต่อเดือน / เวลาเฉลี่ย impact analysis / เวลาเฉลี่ย implement คำขอ / จำนวนคำขอค้าง — ถ้าโตต่อเนื่องแปลว่า maintainability ถดถอย ต้องจัด preventive เพิ่ม
  4. ปิดท้ายคะแนนเต็ม: อ้าง cost factors — เก็บทีมเดิม (team stability) + ออกแบบโมดูล แยก business policy ให้แก้ง่าย (จากบทที่ 6) — ลดต้นทุนระยะยาว
ข้อ 6●●●

วิเคราะห์: บริษัท A ส่งงานแล้วหมดสัญญา (ไม่มีภาระบำรุงรักษา) บริษัท B พัฒนาและดูแลเอง — หลัง 5 ปี ระบบของ A แก้ทุกฟีเจอร์แพงมาก ระบบ B แก้ง่าย — อธิบายด้วย Maintenance Cost Factors

เฉลย
  1. สาเหตุหลัก = Contractual responsibility: ทีม A ไม่มีสัญญาผูกดูแลต่อ → "no incentive to design for future change" — ไม่มีแรงจูงใจออกแบบให้แก้ง่ายในอนาคต
  2. เสริม = Program age and structure: 5 ปีโครงสร้างถดถอย (ถ้าไม่มี preventive) + patch งั้นงี้ จนเข้าใจยาก
  3. ทีม B ได้เปรียบจาก: Team stability (คนเดิมรู้ระบบ) + Staff skills ที่สะสม domain knowledge ต่อเนื่อง
  4. บทเรียน: ตอนเขียนข้อสอบ "วางแผน maintenance" — บอกให้ชัดว่าโครงสร้างโมดูล+เอกสารที่ดีตอนพัฒนา = ลดต้นทุน maintenance ระยะยาว (เชื่อมจาก Ch3 maintainability และ Ch6 business policy แยกจุดเปลี่ยน)
