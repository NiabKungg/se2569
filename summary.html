บทที่ 1 — บทนำสู่วิศวกรรมซอฟต์แวร์ (เปิดบทเต็ม)
  • 1968 NATO เสนอ "Software Engineering" แก้ Software Crisis · 1975 ICSE นิยามชัด
  • นิยาม SE: สร้างซอฟต์แวร์ ใหญ่/ซับซ้อน ด้วย ทีมวิศวกร — Programming = implement blueprint ของ SE
  • Software Crisis: 1970 Size · 1980 Quantity · 1990 Quality · 1990-E Interface
  • ประเภทซอฟต์แวร์ 8 แบบ (จับคู่!): System (บริการโปรแกรมอื่น: OS, driver, compiler) · Application (ธุรกิจ: data gathering→analysis→control) · Eng & Sci (number crunching) · Embedded (ฝังเครื่องใช้) · Product-line (ขายตลาดหลวง: Word) · Web-based (WebApps) · AI (non-numerical, pattern recognition) · Mobile (native/web/hybrid)
  • SE View: Methodology (Waterfall/Spiral/OO) · Technique (OOP/Algo/CASE) · Environment (PC/OS/Internet) + Project Management + SW Development
  • SDLC 5 ขั้น: Requirements → Design → Coding+Module Testing → Integration+System Testing → Delivery+Maintenance
  • Process activities: S-D-V-E Specification / Development / Validation / Evolution · ต้นทุน: พัฒนา 60% + ทดสอบ 40%
บทที่ 2 — หลักการวิศวกรรมซอฟต์แวร์ (เปิดบทเต็ม)
  • Method = guideline กว้าง / Technique = technical+mechanical / รวมกัน = Methodology / Tool = support ทุกชั้น
  • พีระมิดจากล่าง: Principles → Methods/Techniques → Methodologies → Tools ("Principles คือฐานของทุกอย่าง")
  • 7 หลักการ: Rigor & Formality (Formality เข้มกว่า — ใช้กฎคณิต) · Separation of Concerns (แยก: Time/Qualities/Views/Parts) · Modularity (Decomposability top-down divide&conquer + Composability bottom-up) · Abstraction (มองสาระ ละรายละเอียด — กรณีพิเศษของ SoC) · Anticipation of Change (แยกซอฟต์แวร์จากสินค้าอุตสาหกรรม → maintainability) · Generality (ใช้หลายกรณี แต่แพงกว่า) · Incrementality (early subsets → early feedback)
บทที่ 3 — คุณภาพซอฟต์แวร์ (เปิดบทเต็ม)
  • External = ผู้ใช้เห็น / Internal = นักพัฒนาดูโครงสร้าง — คีย์: "internal verifiability จำเป็นต่อ external reliability"
  • Product (โค้ด+req+design+test data) vs Process (วิธีผลิต — ใกล้ชิด product quality)
  • 16 คุณภาพ คีย์เวิร์ด: Correctness (ตรง spec) · Reliability (probability+time) · Robustness (ทน input แปลก) · Performance (ช้า/ใหญ่/แรม — ประเมินด้วย Measurement/Analysis/Simulation) · User Friendliness (menu ดีกว่า command) · Verifiability (SW monitors) · Maintainability (Corrective 20%/Adaptive/Perfective) · Repairability (RAS, standard parts) · Evolvability (documented หรือแก้ยากขึ้น) · Reusability · Portability (คนละ OS) · Understandability (ช่วย evolvability+verifiability) · Interoperability (coexist+cooperate) · Productivity (process!) · Timeliness (process) · Visibility (documented steps+status — internal+external)
  • 4 ระบบ: Information-based (integrity/security/availability/transaction perf) · Real-time (เวลาตอบ = correctness — เร็วไปก็ผิด!) · Distributed (partition + เครื่องล่ม — แก้ด้วย replication) · Embedded (ไม่มี interface มนุษย์ — ตู้ขายของ, monitor ผู้ป่วย)
บทที่ 4 — งานพัฒนาซอฟต์แวร์ (เปิดบทเต็ม)
  • 13 งาน: Feasibility (cost-benefit) → Requirements (→spec) → UI design → Architectural (→arch design+module specs) → Detailed (→module designs) → Programming (→code) → Integration ("the build" → complete system) → Verification → Validation → Production (ใช้จริง+อบรม) → Maintenance → Documentation → Project management
  • 🎯 Verification = "Are we building the product RIGHT?" (มุมนักพัฒนา, unit+system testing) · Validation = "Are we building the RIGHT product?" (มุมลูกค้า, acceptance testing) — Boehm
  • Unit test inputs: unit spec + unit code + expected results · Acceptance: สาธิต→sign-off หรือรายการ fault
  • Documentation: ผู้ใช้ = "what" (ติดตั้ง/ใช้) / นักพัฒนา = "how" (spec, design, code, comments, test results, plan)
บทที่ 5 — การจัดการโครงการซอฟต์แวร์ (เปิดบทเต็ม)
  • ยากเพราะ: ผู้ใช้ไม่รู้ requirement · requirement เปลี่ยน · right man right job · สื่อสารทีม · เทคโนโลยีเปลี่ยน
  • ควบคุม 3 อย่าง: Quality · Cost · Delivery / Characteristics: Time-Task-Cost-Quality
  • แผน 5 แบบ: Quality / Validation / Configuration mgmt / Maintenance (พยากรณ์งาน+ต้นทุน — ใช้ตอบข้อสอบ!) / Staff development
  • Milestone = จุดสิ้นสุด activity / Deliverable = ผลงานส่งลูกค้า
  • Brooks: "Adding people to a late project makes it later" (communication overhead) — วางแผนต้องมี contingency
  • Life cycle: Initiation → Planning → Execution → Closing / ฟังก์ชันบริหาร P-O-S-D-C: Planning, Organizing, Staffing, Directing, Controlling
  • Control เครื่องมือ: WBS (หั่นงานเป็นทวี) · Gantt (แท่งเริ่ม-จบ — จำกัด: dependency ไม่ชัด / ไม่บอกผล delay / ไม่เหมาะใหญ่ซับซ้อน) · PERT = เวลา (AOA) vs CPM = ต้นทุน
บทที่ 6 — วิศวกรรมความต้องการ (เปิดบทเต็ม)
  • RE 3 ขั้น: Gathering (elicitation) → Analysis → Specification (ชัด/สม่ำเสมอ/ครบ)
  • ลูกค้าให้ "problem statement" ไม่ใช่ requirements — เราต้องวิเคราะห์แปลง (Problem domain → Requirements → Specification → โปรแกรม/Solution domain)
  • ⚡ "Requirements are not simply desires!" = desires ปรับด้วย constraints (physical/social/legal/financial) + threats
  • Problem analysis: หาสาเหตุก่อนเขียน requirement (Traffic: จราจรแปรปรวน/ไม่คุ้นเส้น/นิสัยออกสาย)
  • User Story: "As a [role], I can [capability], [business-goal]" — เขียนโดยลูกค้า · acceptance test เขียนพร้อม story · sizing เป็น points · ไม่มี priority (เรียงตามตำแหน่ง to-do list)
  • Sizing 5 ขั้น: แบ่งเล็กคล้ายกัน → ขนาดสัมพัทธ์ → รวม → velocity → duration = size ÷ velocity (1 point = 2 วัน ตัวอย่าง)
  • Business policies ต้องระบุชัด (เช่น ผิด 3 ครั้ง = block) — ไม่ปล่อยให้ programmer hard-code เอง
  • 🎯 FR = "ระบบต้องทำอะไร" / NFR = "ทำดีแค่ไหน" ตาม FURPS+: Functionality(Security), Usability, Reliability, Performance, Supportability + อื่น ๆ — เขียน NFR ต้องมีเกณฑ์วัด
  • Acceptance test ทำโดยลูกค้าตลอดโปรเจกต์ · UI requirement: วาดมือ ไม่ทำ mockup หรู
บทที่ 7 — สถาปัตยกรรมซอฟต์แวร์ (เปิดบทเต็ม)
  • นิยาม: ชุดการตัดสินใจ high-level กำหนดโครงสร้าง (ส่วน+ความสัมพันธ์) — ทำเนิ่น ๆ แก้ยาก · ไม่ใช่ phase
  • Decompose เพราะ: divide&conquer / reuse / ไม่ reinvent wheel / decoupling / ได้เปรียบกลยุทธ์
  • Views: Module (decomposition/dependency/layered/class) + Component-Connector (process/concurrency/shared data/client-server)
  • องค์ประกอบสไตล์: Components + Connectors + Interfaces + Configurations
  • 🎯 สไตล์: Client/Server (client=triggering, server=reactive) · Central Repository (DB กลาง) · Layered (UI/Logic/Technical — ลด coupling เพิ่ม reusability) · P2P (เท่าเทียม) · Microservices (เล็กอิสระ) · MVC (Model ข้อมูล+logic / View แสดง / Controller รับ input — Model oblivious) · REST (stateless, URI นาม + HTTP method กริยา: POST create/GET read/PUT update/DELETE delete) · Pipe-and-Filter (UNIX: ls | grep | more)
  • ระบบจริง = ผสมหลายสไตล์ (Safe Home: Central Repository + Tiered)
  • 🎯 Schema: ER + crow's foot — entity/PK/FK/1:N · โจทย์สอบ = อ่านหา "สิ่งที่เก็บข้อมูล" เป็นตาราง
บทที่ 8 — โมเดลกระบวนการซอฟต์แวร์ (เปิดบทเต็ม)
  • Waterfall ดี: task อิสระ / ควบคุมง่ายแม้ใหญ่ / จบตามเวลา — จำกัด: ออกแบบหมดก่อน coding / เอกสารเยอะ / ผู้ใช้รอจนจบ / ใช้ tool ใหม่ไม่ได้
  • Spiral (Boehm, TRW) = waterfall+prototype วนเฟสเล็ก + risk analysis นำทุกเฟส — ลด risk คุมงบ progress ชัด / วง: Alternatives-Risk-Prototype-Design/Validation-Planning + cost axis / คนเกี่ยวข้อง review ท้ายทุกวง
  • Prototyping — ต้นแบบให้ผู้ใช้เช็ก req แก้ซ้ำ · ไม่ดีกับใหญ่ · ใช้ RAD Tool
  • RAD — incremental, 60–90 วัน, ใช้เมื่อ req well-understood + scope constrained / 5 เฟส: Business → Data → Process modeling → Application generation (4GL) → Testing & turnover (reuse → ทดสอบน้อยลง)
  • Incremental (design รวมก่อน พัฒนาเฟสเล็ก — ต่างจาก Waterfall ที่ห้ามหั่น) / Evolutionary = Prototyping + Incremental (หลักมาก่อน)
  • RUP — use case driven, architecture centric, iterative+incremental / เฟส I-E-C-T: Inception (ขอบเขต+วิสัยทัศน์) / Elaboration (แผน+สถาปัตยกรรม+prototype) / Construction (Implementation+Testing) / Transition (ส่งมอบ+อบรม+บำรุง) / Workflows: core 7 (Business modeling, Requirement, Analysis→Use case Diagram&Spec, Design, Implementation, Testing, Deployment) + supporting 3 (Config & Change mgmt, PM, Environment)
  • XP — Planning (user stories, cost สัปดาห์) / Design (KIS, CRC cards, spike solution, refactoring) / Coding (โมดูลย่อย+ทดสอบทันที, pair programming, continuous integration) / Test (unit รวม → Universal Testing Suite → acceptance) / 10 practices: incremental planning, small releases, simple design, test-first, refactoring, pair programming, collective ownership (ใครก็แก้ได้), continuous integration, sustainable pace (ไม่ OT หนัก), on-site customer
  • Scrum — จัดการ iterative / 3 เฟส: outline planning → sprint cycles (2–4 สัปดาห์, product backlog, selection กับลูกค้า ทีมโดด คุยผ่าน scrum master, จบ review) → closure / scrum master: จัดประชุมรายวัน ตาม backlog จด decision วัด progress ปกป้องทีมจาก distractions / ประโยชน์: ชิ้นเล็กจัดการง่าย · req ไม่เสถียรไม่ขวาง · ทีมเห็นทุกอย่าง · ส่งตรงเวลา+feedback · ความไว้ใจ
  • 🎯 งาน→Model: req ชัดคงที่=Waterfall / ใหญ่เสี่ยง=Spiral / req กำกวม=Prototyping / ด่วน scope จำกัด=RAD / ส่งเป็นก้อน=Incremental/Evolutionary / ใหญ่+UML=RUP / เล็ก agile=XP / จัดการทีม iterative=Scrum
บทที่ 9 — Use Cases (เปิดบทเต็ม)
  • ใช้กับ Functional Requirements analysis+specification · 3 องค์ประกอบ: actors + diagram + scenarios
  • Actor 4 แบบ: Initiating (เริ่ม, ชื่อเดิม primary/user) · Participating (ร่วมไม่เริ่ม) = Supporting (ช่วย) + Offstage (แค่ถูกแจ้ง เช่น Police) · บ้าน/ประตูไม่ใช่ actor
  • Diagram: actor นอกกรอบ · ellipse + ชื่อ verb phrase · system boundary · base vs subroutine use cases · «initiate» / «participate»
  • 🎯 «include» (ตอบ No ทั้ง 4: ไม่ optional / ฐานไม่สมบูรณ์ถ้าขาด / ไม่ conditional / ไม่เปลี่ยนพฤติกรรมฐาน) vs «extend» (Yes ทั้ง 4) — DRY: ตัดซ้ำเป็น subroutine
  • 🎯 Login กับดัก: BAD = Login เป็น ellipse ศูนย์กลางพัวพัน / GOOD = subroutine «include» (AuthenticateUser) หรือยุบเป็น precondition
  • Generalization: Resident←Tenant/Landlord · ManageUsers←AddUser/RemoveUser (ลูกศรชี้หาตัว general)
  • Traceability matrix 3 ประโยชน์: REQ ครบ / ไม่มี UC ลอย / จัดลำดับงาน (PW)
  • โครงเขียน UC: UC-# (verb phrase) / Related REQs / Initiating Actor / Goal / Participating Actors / Preconditions / Postconditions / Main scenario (สลับ → actor สั่ง, ← system ตอบ) / Extensions (เลขขั้น+ตัวอักษร เช่น 2a)
  • SSD = sequence diagram ระหว่าง actor↔system / Activity: initial→action→decision[guard]→merge→final / UC มี limitation: ผู้ใช้แทนผู้รับประโยชน์จริง → ดูทั้งสองมุม / UI: วาดมือก่อน prototype / Risk: Intolerable-ALARP-Acceptable + abuse case
บทที่ 10 — การทดสอบซอฟต์แวร์ (เปิดบทเต็ม)
  • "Testing shows the presence, not the absence of bugs" — Dijkstra
  • fault=defect=bug / TDD = ทุกขั้นเริ่มจากแผน verify / test case = input เฉพาะ + expected output / test = กลุ่ม test cases
  • White-box = ดูโครงสร้างโค้ด (developer) / Black-box = ดู input space จาก spec (customer)
  • 🎯 7 ระดับ: Unit (โดดเดี่ยว, white-box, dev) → Integration (ต่อโมดูล) → Function (FR) → Quality (NFR) → System (ระบบสมบูรณ์เทียบ System Spec) → Acceptance (ลูกค้า, black-box) → Installation (สภาพแวดล้อมจริง)
  • Coverage: specification coverage (input space — acceptance) vs code coverage (unit)
  • เทคนิค black-box: Equivalence (range→1 valid+2 invalid / ค่าเดียว→1+2 / เซต→1+1 / boolean→1+1) · Boundary (0/min/max/empty/null/>>=)
  • เทคนิค white-box: Control-flow (statement/edge/condition/path coverage — path แพงสุด) · State-based (4 สถานะ: Locked-Accepting-Unlocked-Blocked + events valid/invalid-key; ครอบ state ทุกอัน + transition valid ทุกเส้น + trigger invalid ทุกแบบ)
  • Mock: driver (จำลองตัวเรียก) / stub (จำลองตัวถูกเรียก) / unit ที่ทดสอบ = fixture / วงจร: set up → act → verify / ชื่อเทส: method_state_expected (checkKey_anyState_invalidKeyRejected) / JUnit asserts
  • Integration: Big bang (จับตัวการยาก) / Bottom-up (mock น้อย แต่ผู้ใช้เห็นช้า) / Top-down (บนลง + stub) / Sandwich / Vertical = หั่นตาม use case + inner loop (unit test) / outer loop (acceptance) + refactor
บทที่ 11 — การบำรุงรักษาซอฟต์แวร์ (เปิดบทเต็ม)
  • นิยาม: แก้ไขระบบ หลังส่งมอบ เพื่อ correct faults / improve performance / adapt environment — ต้นทุนสะสมแพงกว่าพัฒนา
  • 🎯 4 ประเภท: Corrective 21% (แก้ error) / Adaptive 25% (สภาพแวดล้อม HW/SW เปลี่ยน: OS/DB ใหม่) / Perfective 50% (req ผู้ใช้เปลี่ยน เพิ่มฟังก์ชัน) / Preventive 4% (เพิ่ม maintainability กันอนาคต)
  • Dev vs Maint: dev อิสระไม่ผูกโลกจริง / maint ถูก driven จริง + ติดระบบเดิม + defects disrupt production + standards เลื่อนลอย
  • ช่วงชีวิต: Introductory=user support / Growth=correcting faults / Maturity=enhancements / Decline=technology changes
  • สาเหตุปัญหา 3 ข้อ: unstructured code / ขาด domain knowledge / ขาด documentation · เครื่องมือ 4 กลุ่ม / evolution: version-centered vs history-centered
  • กระบวนการ 5 ขั้น: Change requests → Impact analysis → Release planning → Change implementation → System release (3 ชนิดคำขอ: fault repair / platform adaptation / system enhancement)
  • Maintainability กระทบโดย: อายุ / ขนาด (KLOC) / ภาษา (4GL>3GL) / environment / ออกแบบดี / modularization / เอกสาร (แพงเท่าโค้ด) / end-user involvement / management
  • สัญญาณ maintainability ถดถอย: คำขอ corrective เพิ่ม / เวลา impact analysis / เวลา implement / คำขอค้าง — โตเรื่อย = ถดถอย
  • Cost factors: team stability (ทีมเดิมถูกลง) / contractual responsibility (ไม่ผูกดูแล = ไม่ออกแบบให้แก้ง่าย) / staff skills / program age+structure

  • Use case: actor นอกกรอบ / ellipse กริยา / boundary / «include» AuthenticateUser — ห้าม Login พัวพัน
